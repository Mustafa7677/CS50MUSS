1Аудару

Идея

Айгерімнен Данаға 300 аудару: екі өзгеріс:

BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
UPDATE accounts SET balance = balance + 300 WHERE id = 3;
COMMIT;

Транзакция: бір бүтін ретінде орындалатын операциялар тобы. ACID қасиеттері:

  • Atomicity: не бәрі, не ештеңе
  • Consistency: шектеулер мен инварианттар сақталады
  • Isolation: параллель транзакциялар бір-біріне кедергі жасамайды
  • Durability: COMMIT болған соң, сервер құласа да деректер сақталады

Түйсік

Банкоматтан ақша алу: шоттан шегерілді, бірақ ақша шықпай қалды: қабылданбайды. Не екеуі де, не ешқайсысы.

Есептеп көрейік

Бастапқы баланстар: 1000, 500, 200: барлығы 1700. Аударымнан кейін: 700, 500, 500: барлығы бәрібір 1700. Бұл: инвариант: жүйедегі ақша аударымнан пайда болмайды да, жоғалмайды да.

Бірнеше сұранысты ; арқылы бір жолда жазып, бірден орындауға болады.

Нақты әлемде

Kaspi, Halyk: әр аударым транзакция. Тіпті «лайк басу» да көбіне транзакция: лайк жазбасы + санауыштың өсуі.

⚠ Жиі қате: екі UPDATE-ті транзакциясыз орындау. Арасында сервер құласа не қате шықса, ақша бір шоттан кетіп, екіншісіне келмейді.

Енді сен

Айгерімнен (id 1) Данаға (id 3) 300 аудар: BEGIN … COMMIT ішінде.

300 бір шоттан кетті, бірақ ешқайда келмеді. Транзакция мұндай аралық күйді сақтауға жол бермейді.

2ROLLBACK

Идея

ROLLBACK: транзакциядағы барлық өзгерісті болдырмау. BEGIN-нен кейінгі әр UPDATE, INSERT, DELETE жойылады, деректер BEGIN сәтіндегі күйге оралады.

Түйсік

Мәтін редакторындағы «барлық өзгерістерді болдырмау»: соңғы сақталған нұсқаға (COMMIT) қайтасың.

Есептеп көрейік

BEGIN;
UPDATE accounts SET balance = 0;      -- WHERE ұмытылды!
SELECT SUM(balance) FROM accounts;    -- 0: апат
ROLLBACK;
SELECT SUM(balance) FROM accounts;    -- 1700: құтқарылды

Транзакция ішінде өзгерістерді өзің көресің, бірақ COMMIT-ке дейін олар түпкілікті емес.

Іште қалай жұмыс істейді? Дерекқор өзгерістерді алдымен журналға (WAL: write-ahead log) жазады. ROLLBACK: журналдағы өзгерістерді елемеу, COMMIT: журналға «бекітілді» белгісін жазу.

Нақты әлемде

Өндірістік дерекқорда қолмен UPDATE не DELETE жасамас бұрын тәжірибелі инженерлер әрдайым BEGIN жазады, нәтижені SELECT-пен тексереді, сосын ғана COMMIT.

💡 Түйін: BEGIN: тәуекелді әрекеттің алдындағы ең арзан сақтандыру.

Енді сен

BEGIN жаз, бір шоттың балансын өзгерт, нәтижені қара, сосын ROLLBACK жаса.

Өзіңді тексер

COMMIT-тен кейін ROLLBACK жасасақ не болады?

Жауабы мен түсіндірмесі

Дұрыс жауап: Ештеңе: ашық транзакция жоқ, бекітілген өзгерістер қайтарылмайды

COMMIT: нүкте. Одан кейін өзгерісті тек жаңа транзакциямен (кері операциямен) түзетуге болады.

WAL (write-ahead log) не үшін керек?

Жауабы мен түсіндірмесі

Дұрыс жауап: Өзгерістерді алдымен журналға жазып, құлағаннан кейін дұрыс күйді қалпына келтіру үшін

Журнал: атомарлық пен беріктіктің негізі: сервер қайта іске қосылғанда, бекітілген транзакциялар қайта қолданылады, бекітілмегендері тасталады.

3Сервер құлады

Идея

Ең қатал сынақ: транзакция ортасында сервер құлайды (электр өшті). Бірінші UPDATE орындалды, екіншісі: жоқ. Сервер қайта қосылғанда не болады?

Түйсік

Аяқталмаған транзакция ешқашан болмаған сияқты: қалпына келтіру барысында дерекқор журналды оқып, COMMIT белгісі жоқ өзгерістерді тастайды.

Есептеп көрейік

BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 1;

Осы сәтте «Сервер құлады» батырмасын бас. Нәтиже: Айгерімде қайтадан 1000, жалпы сома 1700. 300 «ауада жоғалмады».

Ал COMMIT-тен кейін құласа: өзгерістер сақталады (durability): COMMIT дискіге (журналға) жазылмайынша клиентке «сәтті» деп жауап берілмейді.

Нақты әлемде

Дерекқорлар COMMIT кезінде fsync шақырады: ОС-тан деректерді дискіге шынымен жазуды талап етеді. Ол баяу (миллисекундтар), сондықтан кейбір жүйелер «топтық commit» қолданады: бірнеше транзакцияны бір fsync-пен бекітеді.

⚠ Жиі қате: «кэштегі жазу = сақталды». Дискінің өз кэші бар; электр өшсе, ол жоғалуы мүмкін. Нақты дерекқорлар мұны ескереді.

Енді сен

Транзакцияны бастап, бір шоттан ақшаны шегер де, COMMIT-сіз «Сервер құлады» бас. Жалпы сома 1700 қалуы керек.
