Keys & Constraints

Дерекқор қате деректерді өзі қабылдамайды: PRIMARY KEY, NOT NULL, FOREIGN KEY.

  1. Бірегей кілт
  2. Сыртқы кілт

1Бірегей кілт

Идея

Шектеулер (constraints): дерекқор өзі тексеретін ережелер. Қате дерек ешқашан сақталмайды, тіпті бағдарламада қате болса да:

  • PRIMARY KEY: бірегей және бос емес
  • NOT NULL: мән міндетті
  • FOREIGN KEY: басқа кестедегі бар жолға сілтеу керек
  • CHECK: кез келген шарт (мысалы balance >= 0)

Түйсік

Шектеулер: бағдарламаның «соңғы қорғаныс сызығы». Сайтта, мобильді қосымшада, әкімшінің скриптінде: бәрінде бір ереже қайталанбайды, ол дерекқордың өзінде тұр.

Есептеп көрейік

INSERT INTO students (id, name, city, year) VALUES (1, 'Арман', 'Тараз', 1)

id = 1 әлдеқашан бар (Айгерім) → PRIMARY KEY шектеуі: жол қосылмайды.

Шектеусіз дерекқорда екі «1-студент» болар еді, ал WHERE id = 1 енді екі адамды қайтарар еді.

Нақты әлемде

Көп компания «тексеруді кодта жасаймыз» деп шектеулерді қоймайды. Нәтиже: жылдар өткен соң миллиондаған қайшы жол, оны тазалау: айлар. Шектеуді басынан қою арзан.

💡 Түйін: дерекқор: көп бағдарлама бөлісетін ортақ қор. Ережені бір жерде, ең төмен деңгейде ұста.

Енді сен

Бар id-мен студент қосып көр: дерекқор не дейді?

Симуляцияны ашу

Өзіңді тексер

Неге «бірегейлікті» тек бағдарлама кодында тексеру жеткіліксіз?

Жауабы мен түсіндірмесі

Дұрыс жауап: Екі сұраныс бір мезгілде тексеріп, екеуі де «бос» деп шешіп, екеуі де жазуы мүмкін

Бұл: race condition (7-сабақ). Тек дерекқордың бірегей индексі параллель жазуларды атомарлы түрде тексереді.

SQL-де NULL = NULL өрнегінің нәтижесі қандай?

Жауабы мен түсіндірмесі

Дұрыс жауап: NULL (белгісіз)

NULL: «белгісіз мән». Екі белгісізді салыстырудың нәтижесі де белгісіз. Сондықтан NULL-ді IS NULL арқылы тексереді.

2Сыртқы кілт

Идея

FOREIGN KEY (сыртқы кілт): enrollments.student_id міндетті түрде students.id-ге сілтеуі керек. Бұл: сілтемелік тұтастық (referential integrity).

Екі бағытта тексеріледі:

  1. Қосқанда: жоқ студентке жазылу қосуға болмайды
  2. Жойғанда: оған жазылулар сілтеп тұрған курсты жоюға болмайды (әйтпесе «жетім» жолдар қалады)

Түйсік

Кітапхана: жоқ оқырманға кітап беруге болмайды, ал кітабы бар оқырманды тізімнен сызып тастауға болмайды.

Есептеп көрейік

INSERT INTO enrollments (student_id, course_id, grade) VALUES (99, 1, 90)

→ 99-студент жоқ → FOREIGN KEY қатесі.

DELETE FROM courses WHERE id = 1

→ 7 жазылу сілтейді → FOREIGN KEY қатесі.

Нақты дерекқорларда жою әрекетін таңдауға болады: ON DELETE CASCADE (тәуелді жолдарды да жою), SET NULL, RESTRICT (біздегідей: тыйым).

Нақты әлемде

CASCADE ыңғайлы, бірақ қауіпті: бір клиентті жою оның барлық тапсырыстарын, төлемдерін, журналдарын жоюы мүмкін. Сондықтан көп жүйе жоюдың орнына «жұмсақ жою» (deleted_at бағаны) қолданады.

⚠ Жиі қате: тест деректерін тазалау үшін FK шектеулерін өшіру: және қайта қосуды ұмыту.

Енді сен

FOREIGN KEY шектеуін іске қос: жоқ студентке жазылу қос, не жазылуы бар курсты жоюға тырыс.

Өзіңді тексер

ON DELETE CASCADE болса, курсты жойғанда не болады?

Жауабы мен түсіндірмесі

Дұрыс жауап: Оған жазылулар да автоматты түрде жойылады

CASCADE: тәуелді жолдарды «тізбекпен» жою. SET NULL: сілтемені бос ету, RESTRICT: тыйым.

«Жетім» жол (orphan row) деген не?

Жауабы мен түсіндірмесі

Дұрыс жауап: Жоқ жолға сілтейтін сыртқы кілті бар жол

Мысалы жойылған студенттің жазылуы. Мұндай жолдар JOIN-да жоғалып кетеді, есептерді бұрмалайды. FK оларға жол бермейді.
