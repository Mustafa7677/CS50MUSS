Rate Limiting: 429 & Retry-After

Бір клиент серверді сұраныспен көміп тастамауы үшін: сырғымалы терезе, 429 жауабы, Retry-After және неге шек әр клиентке бөлек.

3D симуляцияны ашу Дәрісті оқу

Кино-түсіндіру: сабақтың өзегі бір минуттық мультфильмде. Мәтіні төменде.

Фильмнің мәтіні (сабақтың қадамдарынан құрастырылған)
  1. Сұрақ. Серверде «минутына 5 сұраныс» шегі тұр. Бір минут ішінде алты рет сұрасаң, алтыншысына не болады?
  2. Бейне. Банкоматтағы күндік шек. Картаңда ақша бар, бірақ бір күнде белгілі сомадан артық шеше алмайсың. Бұл сені жазалау үшін емес, біреу картаңды ұрласа, зиянды шектеу үшін.
  3. Болжа. Серверде «минутына 5 сұраныс» шегі тұр. Бір минут ішінде алты рет сұрасаң, алтыншысына не болады? Жауап: Сервер 429 Too Many Requests береді және қашан қайта…. Шектеуші сұранысты маршрутқа да, дерекқорға да жеткізбейді. Ол бірден 429 қайтарады және Retry-After тақырыбымен күту уақытын айтады.
  4. Көр. 1-қадам, «Минутына бес». Сервердің күші шексіз емес. Бір клиент (қате жазылған скрипт, бот, шабуылшы) секундына мыңдаған сұраныс жіберсе, басқалардың бәрі күтіп қалады.
  5. Көр. 2-қадам, «Әр клиентке бөлек». Шек кімге қойылады? Біздің модельде кілт: token, ал token жоқ болса «anon». Нақты жүйелерде бұл API кілті, пайдаланушы id-і не IP адрес болады.
  6. Көр. Нақты әлемде: Жақсы клиент 429 алғанда Retry-After-ты құрметтейді және қайта жіберуді бірден емес, кідіріспен жасайды (exponential backoff, Cloud зертханасында көрдің).
  7. Түйін. Бір клиент серверді сұраныспен көміп тастамауы үшін: сырғымалы терезе, 429 жауабы, Retry-After және неге шек әр клиентке бөлек.
  8. Түйін. Жиі қате: Шек неге әр клиентке бөлек саналуы керек? Жауап: «Серверде жад аз болғандықтан». Дұрысы: «Бір клиенттің шектен асуы басқа клиенттерге кедергі болмауы үшін». Бүкіл сайтқа бір ортақ шек болса, бір бот барлығына қызметті жабады. Шектеудің…

1Минутына бес

Идея

Сервердің күші шексіз емес. Бір клиент (қате жазылған скрипт, бот, шабуылшы) секундына мыңдаған сұраныс жіберсе, басқалардың бәрі күтіп қалады. Rate limiting әр клиентке «уақыт бірлігінде N сұраныстан артық емес» деген шек қояды.

Шектен асқан сұранысқа сервер 429 Too Many Requests жауабын береді және Retry-After тақырыбымен қанша секундтан кейін қайта келуге болатынын айтады.

Түйсік

Банкоматтағы күндік шек. Картаңда ақша бар, бірақ бір күнде белгілі сомадан артық шеше алмайсың. Бұл сені жазалау үшін емес, біреу картаңды ұрласа, зиянды шектеу үшін.

Есептеп көрейік

Біздің шектеуші сырғымалы терезе қолданады: әр сұраныс келгенде соңғы 60 секундта осы клиенттен қанша сұраныс қабылданғанын санайды.

  • 1-ден 5-ке дейін: санауыш 1/5, 2/5 ... 5/5, бәрі өтеді.
  • 6-сы: терезеде онсыз да 5 бар, сондықтан 429.
  • Retry-After = ең ескі сұраныстың терезеден шығуына қалған секунд.

Маңыздысы: 429 жауабы маршрутқа да, SQL-ға да жетпейді. Шектеуші ең алдында тұр, сондықтан артық сұраныс серверге арзанға түседі.

Нақты әлемде

GitHub API бір сағатқа белгілі сұраныс санын береді, Telegram боттарына секундына шек қойылған, ал кіру бетінде құпиясөзді теру әрекеттері шектеледі: бұл құпиясөзді іріктеп табуды (brute force) мүмкін емес етеді.

⚠ Шекті тек клиенттің браузерінде қою пайдасыз: шабуылшы браузерді мүлде қолданбайды. Шек серверде тұруы керек.

Енді сен

Сұранысты бес рет жібер де, Rate limiter кезеңіндегі санауышты бақыла. Сосын алтыншысын жібер.

3D симуляцияда орында

  • GET /api/users сұранысын бес рет жібер: бәрі 200
  • Алтыншысы: 429 Too Many Requests және Retry-After

Өзіңді тексер

Клиент шектен асқанда сервер қай статусты береді?

Жауабы мен түсіндірмесі

Дұрыс жауап: 429 Too Many Requests

429 нақты осы жағдайға арналған: сен танылдың, рұқсатың бар, бірақ тым жиі сұрап жатырсың.

Шектеуші неге маршрут пен дерекқордан бұрын тұрады?

Жауабы мен түсіндірмесі

Дұрыс жауап: Артық сұраныс қымбат жұмысқа жетпей, бірден арзан 429 алуы үшін

Шектеудің мақсаты серверді қорғау. Егер артық сұраныс SQL-ға дейін жетсе, қорғаныс кеш болады.

2Әр клиентке бөлек

Идея

Шек кімге қойылады? Біздің модельде кілт: token, ал token жоқ болса «anon». Нақты жүйелерде бұл API кілті, пайдаланушы id-і не IP адрес болады.

Кілт дұрыс таңдалмаса, екі түрлі қате шығады:

  • Тым кең кілт (барлығына бір шек): бір бот бүкіл сайтты баршаға жабады.
  • Тым тар кілт (әр сұранысқа жаңа кілт): шабуылшы әр сұранысқа жаңа token жасап, шекті айналып өтеді.

Түйсік

Дүкендегі «бір адамға екі қорап» ережесі. Ол кезекте тұрған әр адамға бөлек қолданылады. Бірақ бір адам киімін ауыстырып, қайта кезекке тұрса, ереже бұзылады: сондықтан «адамды» дұрыс тану маңызды.

Есептеп көрейік

Анонимдіге 429 келді, Retry-After шамамен 60 с. Осы сәтте:

  • secret-123: оның терезесі бос, 1/5, жауап 200.
  • anon: уақытты жылжытпасаң, әлі 429.
  • Уақыт +60 с: ескі сұраныстар терезеден шықты, anon қайтадан 1/5, жауап 200.

Нақты әлемде

Жақсы клиент 429 алғанда Retry-After-ты құрметтейді және қайта жіберуді бірден емес, кідіріспен жасайды (exponential backoff, Cloud зертханасында көрдің). Ал 429-ды елемей, бірден қайталай беретін клиент өз жағдайын тек нашарлатады: оның әр әрекеті терезеге кірмейді, бірақ серверді бәрібір жүктейді.

⚠ IP бойынша шек қоюда абай бол: бір мектептің немесе бір мобильді оператордың жүздеген пайдаланушысы сыртқа бір IP-мен шығуы мүмкін.

Енді сен

Token өрісіне secret-123 жаз да, сұра. Сосын token-ді өшіріп, уақытты Retry-After-қа дейін жылжыт та, қайта сұра.

3D симуляцияда орында

  • Token-мен (secret-123) сұра: сенің шегің басқа адамның шегіне тиіспейді
  • Retry-After уақыты өткенше күт те, анонимді сұранысты қайта жібер: 200
Симуляцияны ашу

Алдымен болжа

Анонимді клиент шекке жетті. Енді сол серверге secret-123 token-імен сұрасаң не болады?

Жауабы мен түсіндірмесі

Дұрыс жауап: 200: шек әр клиентке бөлек саналады

Шектеуші сұранысты кім жібергенін (token, IP, API кілті) кілт ретінде алады. Біреудің шегі басқаның шегіне әсер етпейді.

Өз сөзіңмен түсіндір

Неге бір клиент шекке жеткенде басқа клиент әлі 200 алады, ал күткен соң анонимді клиент қайта өтеді?

Жақсы түсіндірмеде болатын ойлар
  • шек әр клиентке бөлек саналады
  • терезе сырғиды: ескі сұраныстар шығады
  • Retry-After қанша күтуді айтады

Өзіңді тексер

Шек неге әр клиентке бөлек саналуы керек?

Жауабы мен түсіндірмесі
