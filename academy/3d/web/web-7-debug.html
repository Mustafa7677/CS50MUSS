1Сайт ашылмайды

Идея

Debugging: болжау емес, жүйелі іздеу. Жүйелі әдіс:

  1. Симптомды нақты сипатта: «бет ашылмайды» емес: «DNS_PROBE_FINISHED_NXDOMAIN».
  2. Гипотеза: қай кезеңде сынды?
  3. Тексер: бір нәрсені өзгерт, нәтижені бақыла.
  4. Қайтала.

Қате хабарларын оқы

NXDOMAIN              → DNS: мұндай домен жоқ
ERR_CONNECTION_TIMED_OUT → сервер жауап бермейді (өшірулі / брандмауэр)
ERR_SSL_PROTOCOL_ERROR → TLS/сертификат мәселесі
404 / 500             → сервер бар, мәселе қосымшада

Хабар қай кезеңді атайды: сол кезеңнен баста.

Есептеп көрейік

Кезеңдер тізімінде браузер «DNS сұрауы» кезеңінде тоқтады. Демек TCP, HTTP, сервер коды: әзірге кінәлі емес. Тек DNS жазбаларын тексер.

⚠ Жиі қате: бірден кодты өзгертуге кірісу. Алдымен мәселенің қай деңгейде екенін анықта.

2404 Not Found

Идея

Енді DNS, TCP, TLS жұмыс істейді: сервер жауап береді. Бірақ 404 Not Found: сервер бар, бірақ сұралған жол бойынша маршрут жоқ.

Тексеру жолы

  1. Қандай жол сұралды? → /
  2. Серверде қандай маршруттар бар? → /home
  3. Сәйкессіздік: басты бет қате жолда тұр.

Шешім нұсқалары

  • маршруттың жолын /-ге өзгерту;
  • немесе /-ден /home-ға redirect (301) жасау.

Нақты әлемде

404 көбінесе сайтты қайта құрылымдағанда пайда болады: ескі сілтемелер интернетте қалады. Сондықтан ірі сайттар ескі адрестерден жаңасына 301 redirect қояды: әйтпесе іздеу жүйесіндегі орнын жоғалтады.

💡 Түйін: 404: «сен жоқ нәрсені сұрадың». Сервер дұрыс жұмыс істеп тұр.

3500 Internal Server Error

Идея

500 Internal Server Error: сервер кодының өзінде қате (exception). Клиент дұрыс сұрады; мәселе: серверде. Мұнда маршрут «crash» түрінде: код undefined-тың қасиетін оқуға тырысып құлайды.

Нақты әлемде қалай іздейді

  1. Логтар: сервер қатенің stack trace-ін жазады: файл, жол, функция.
  2. Қайталау: сол сұрауды қайта жіберіп, қате тұрақты ма тексер.
  3. Соңғы өзгеріс: көбінесе 500 жаңа deploy-дан кейін пайда болады.
  4. Мониторинг: Sentry сияқты жүйелер әр 500-ді бірден хабарлайды.

Есептеп көрейік

TypeError: Cannot read properties of undefined (reading 'price')
    at handler (products.js:12)

12-жолда product.price: бірақ product табылмаған. Түзету: тексеріс қосу немесе 404 қайтару.

⚠ Жиі қате: пайдаланушыға stack trace-ті көрсету. Бұл шабуылдаушыға кодтың ішкі құрылымын ашады. Клиентке: жалпы хабар, логқа: толық мәлімет.

4Баяу API

Идея

Сұрау жұмыс істейді, бірақ баяу. Өнімділік мәселесінде басты ереже: алдымен өлше, сосын оңтайландыр. Кезеңдер тізімінде уақыттың қай жерге кететінін тап.

Есептеп көрейік

DNS + TCP + TLS + HTTP ≈ 330 мс
SQL сұрауы            ≈ 1200 мс  ← мәселе осында

SQL: SELECT * FROM orders WHERE user_id = 7: «2000 жол қаралды (толық сканерлеу)». Бұл 6-сабақтағы жағдай! Индекс → ~260 жол → ~160 мс.

Неге «алдымен өлше»

Интуиция жиі алдайды: желіні не кодты оңтайландыруға бір апта жұмсап, нақты баяулықтың 80%-ы бір SQL сұрауында болғанын кейін білесің. Профайлер: debugging-тің өнімділіктегі нұсқасы.

💡 Түйін: «Premature optimization is the root of all evil»: Дональд Кнут. Өлшемей оңтайландырма.

Тереңірек: N+1 сұраныс және Амдаль заңы

Классикалық баяулық:

posts = db.query("SELECT * FROM posts LIMIT 50")      -- 1 сұраныс
for p in posts:
    p.author = db.query("SELECT * FROM users WHERE id = ?", [p.author_id])   -- 50 сұраныс

51 сұраныс × 2 мс желі = 102 мс. JOIN не WHERE id IN (…) арқылы: 1-2 сұраныс, ~4 мс. Бұл N+1 мәселесі, ORM-дерде өте жиі.

Амдаль заңы: нені оңтайландыру керегін айтады. Жұмыстың f бөлігін s есе жылдамдатсақ:

жалпы жылдамдау = 1 / ((1 − f) + f/s)

Сұраныстың 90%-ы: база, 10%-ы: код. Кодты 10 есе жылдамдатсақ: 1/(0.9 + 0.01) ≈ 1.1×. Базаны 10 есе: 1/(0.1 + 0.09) ≈ 5.3×.

Сабақ: алдымен өлше (profiler, trace), сосын ең үлкен бөлікті түзет. Болжам бойынша оңтайландыру: уақыт ысырабы.
