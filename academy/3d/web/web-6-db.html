Databases

SQL арқылы деректерді оқу, қосу, өзгерту, өшіру және индекстің жылдамдыққа әсері.

3D симуляцияны ашу Дәрісті оқу

  1. SELECT
  2. INSERT, UPDATE, DELETE
  3. Индекс

1SELECT

Идея

Реляциялық дерекқор: кестелер жиыны. Әр кестенің бағандары (id, name, city) және жолдары (жазбалар) бар. SQL: дерекқордан не керек екенін сипаттайтын тіл: «қалай іздеу» емес, «не керек» дейсің, қалай табуды дерекқор өзі шешеді.

SELECT

SELECT name, city        -- қай бағандар
FROM users               -- қай кестеден
WHERE city = 'Алматы'    -- қандай шартпен
ORDER BY name            -- қалай сұрыптау
LIMIT 10                 -- қанша жол

Есептеп көрейік

users кестесінде 8 жол. WHERE id >= 3 AND id < 6 → id 3, 4, 5 → 3 жол.

💡 Түйін: SQL 50 жылдан аса уақыт бойы өзгермей келе жатқан, әлемдегі ең кең таралған тілдердің бірі. Бір рет үйрен: мансап бойы қолданасың.

Енді сен

WHERE шарты бар SELECT орында. Мысалы: SELECT name, city FROM users WHERE city = 'Алматы'.

3D симуляцияда орында

  • WHERE шарты бар SELECT орында

SELECT * FROM users WHERE id > 5: users-те id 1…8. Неше жол қайтады?

Жауабы мен түсіндірмесі

Дұрыс жауап: 3

id > 5 шартына тек 6, 7 және 8 сәйкес келеді, сондықтан 3 жол қайтады.

SQL-дің «декларативті» болуы нені білдіреді?

Жауабы мен түсіндірмесі

Дұрыс жауап: Сен не керек екенін сипаттайсың, ал қалай табуды дерекқор шешеді

SQL-де циклдер жазбайсың: нәтижені сипаттайсың. Жоспарды query optimizer құрады.

2INSERT, UPDATE, DELETE

Идея

Деректермен жұмыстың төрт негізгі әрекеті: CRUD:

Create → INSERT INTO users (name, city) VALUES ('Арман', 'Тараз')
Read   → SELECT * FROM users WHERE id = 2
Update → UPDATE users SET city = 'Астана' WHERE id = 2
Delete → DELETE FROM users WHERE id = 3

Әрбір HTTP маршрут көбінесе осылардың біріне сәйкес келеді: POST → INSERT, GET → SELECT, PUT → UPDATE, DELETE → DELETE.

Есептеп көрейік

UPDATE users SET city = 'Астана': WHERE жоқ. 8 жолдың бәрінің қаласы Астана болады!

⚠ Жиі қате: WHERE-сіз UPDATE не DELETE. Нақты компанияларда мұндай бір жол бүкіл клиенттер базасын өшірген оқиғалар бар. Сондықтан алдымен сол WHERE-мен SELECT жасап, нені өзгертетініңді көр.

Транзакциялар

Ақша аударымы: екі UPDATE (біреуінен алу, екіншісіне қосу). Олар бірге орындалуы керек: біреуі сәтсіз болса, екіншісі де болмауы керек. Мұны транзакция кепілдейді (BEGIN … COMMIT).

Тереңірек: SQL injection және параметрлер

Қате:

db.query("SELECT * FROM users WHERE name = '" + name + "'")

Пайдаланушы name ретінде ' OR '1'='1 жазса, сұраныс:

SELECT * FROM users WHERE name = '' OR '1'='1'

барлық пайдаланушы қайтады. '; DROP TABLE users; --: кесте жойылады.

Мәселенің түбі: дерек пен код араласты. Шешімі: параметрлер:

db.query("SELECT * FROM users WHERE name = ?", [name])

Сұраныс құрылымы алдымен талданады, мән кейін дерек ретінде ғана қосылады: ол ешқашан SQL болып оқылмайды. Біздің зертхананың қозғалтқышы да осылай жұмыс істейді (? орындары).

Бұл қағида кең: HTML-ге мәтін қосқанда (XSS), shell командасына (command injection): әрдайым деректі кодтан бөл.

Енді сен

INSERT, UPDATE және DELETE-ті кемінде бір реттен орында.

3Индекс

Идея

Индекссіз WHERE user_id = 7 дерекқорды әр жолды тексеруге мәжбүрлейді: толық сканерлеу, O(n). Индекс: бағанның сұрыпталған көшірмесі (әдетте B-tree): керекті мәнді бинарлық іздеумен табады, O(log n).

Есептеп көрейік

2000 жол:

толық сканерлеу: 2000 тексеріс
индекс: log₂(2000) ≈ 11 қадам + табылған ~250 жол

1 000 000 жолда: миллион vs шамамен 20 қадам. Айырма: секундтар мен миллисекундтар.

Бағасы

Индекс тегін емес:

  • қосымша жад;
  • әр INSERT/UPDATE индексті де жаңартады: жазу баяулайды.

Сондықтан индекс жиі іздейтін бағандарға ғана жасалады.

💡 Түйін: 7-сабақтағы «баяу API» мәселесінің шешімі дәл осы бір жол болады.

Тереңірек: B-tree индексі неге соншалық жылдам

Индекссіз WHERE id = 42: толық сканерлеу: N жолдың бәрін тексеру, O(N).

Сұрыпталған тізімде екілік іздеу: O(log₂ N): 10⁶ жол → 20 салыстыру. Бірақ дискіде әр салыстыру: бір дискіні оқу, ал ол қымбат.

B-tree: әр түйінде жүздеген кілт бар ағаш (бір түйін = бір диск беті, мысалы 8 КБ). Тармақталу f ≈ 500 болса, биіктігі:

h = ⌈log_f N⌉:   N = 10⁹,  f = 500  →  log 10⁹ / log 500 ≈ 9 / 2.7 ≈ 3.3  →  4 деңгей

Миллиард жолдан 4 бет оқып табамыз. Түбір мен жоғарғы деңгейлер жадта тұрады, сондықтан іс жүзінде 1-2 дискіні оқу.

Бағасы:

  • әр INSERT/UPDATE/DELETE индексті де жаңартады: жазу баяулайды
  • қосымша орын
  • селективтілік: WHERE gender = 'F' (жолдардың 50%-ы) үшін индекс пайдасыз: бәрібір жартысын оқимыз; оптимизатор толық сканерлеуді таңдайды

Ереже: жиі іздейтін және мәндері әр түрлі бағандарға индекс қой.

Енді сен

Алдымен индекссіз ізде (2000 жол қаралады), сосын CREATE INDEX ON orders (user_id) орындап, қайта ізде. «Қаралған жолдар» санын салыстыр.

3D симуляцияда орында

  • orders бойынша толық сканерлеуді көр
  • Индекс жасап, сол сұрауды жылдам орында
Симуляцияны ашу

Жауабы мен түсіндірмесі

Дұрыс жауап: 20

log₂(1 000 000) ≈ 20. Бинарлық іздеу әр қадамда қалған жолдарды екіге бөледі.

Неге барлық бағанға индекс қоймаймыз?
