CORS: жауапты кім оқи алады

CORS: Who May Read the Answer

Бөтен сайттың скрипті API-ге сұраныс жібере алады, бірақ жауапты оқи ала ма? Origin, preflight және CORS-тың нені қорғамайтыны.

3D симуляцияны ашу Дәрісті оқу

  1. Бөтен бет
  2. Алдын ала сұрау

1Бөтен бет

Идея

Same-origin policy: браузердің негізгі қорғанысы. Бір сайттың скрипті басқа origin-нің (протокол + хост + порт) жауабын оқи алмайды. Әйтпесе кез келген бет сенің атыңнан банкке сұраныс жіберіп, жауабын (шотыңды) оқып алар еді, себебі браузер cookie-ді өзі тіркейді.

CORS (Cross-Origin Resource Sharing): серверге «мына origin-дерге менің жауабымды оқуға болады» деп айтуға мүмкіндік беретін тақырыптар:

Access-Control-Allow-Origin: https://inside.kz

Ең маңызды тұс

CORS оқуды бұғаттайды, жіберуді емес. Қарапайым сұраныс (GET, токенсіз форма POST) серверге жетеді және орындалады. Тыйым тек соңында, браузерде болады: жауап скриптке берілмейді.

Модельде evil.kz-тен:

  • GET /api/users: сервер 200 қайтарды, браузер жауапты бермеді;
  • POST /api/users: браузер жауапты бермеді, бірақ дерекқорға жаңа жол қосылды (201).

Яғни CORS серверді қорғамайды. Өзгеріс жасайтын сұраныстарды CSRF токендері мен SameSite cookie қорғауы керек (Senior деңгейде).

Нақты әлемде

Консольдағы «blocked by CORS policy» қатесі: ең жиі кездесетін фронтенд қателерінің бірі. Оны браузерде «өшіру» мүмкін емес, тек сервер өз тақырыптарын түзетеді. Access-Control-Allow-Origin: * токен не cookie бар сұраныстарға жұмыс істемейді.

Енді сен

evil.kz бетінен GET, сосын POST жібер. Сервердің жауап кодына және браузердің шешіміне қара.

3D симуляцияда орында

  • evil.kz бетінен GET /api/users: сервер 200 берді, бірақ браузер жауапты бермеді
  • evil.kz бетінен POST /api/users: жауап бұғатталды, бірақ жазба бәрібір қосылды (201)
Симуляцияны ашу

Алдымен болжа

evil.kz бетіндегі скрипт https://api.inside.kz/api/users-ке fetch жібереді. API тек inside.kz-ке рұқсат береді. Сервер не істейді?

Жауабы мен түсіндірмесі

Дұрыс жауап: Сұранысты орындап, 200 қайтарады; ал браузер жауапты скриптке бермейді

Қарапайым GET-те браузер сұранысты жібереді, сервер оны әдеттегідей орындайды. Тыйым соңында, браузерде: Access-Control-Allow-Origin жоқ болса, жауап evil.kz скриптіне берілмейді.

Өзіңді тексер

Origin неден тұрады?

Жауабы мен түсіндірмесі

Дұрыс жауап: Протокол, хост және порт

https://inside.kz мен http://inside.kz әр түрлі origin: протоколы басқа. api.inside.kz та inside.kz-тен бөлек.

evil.kz-тен келген қарапайым POST сервердегі деректі өзгерте ме?

Жауабы мен түсіндірмесі

Дұрыс жауап: Иә: сервер сұранысты орындайды, браузер тек жауапты жасырады

CORS: оқуға тыйым. Өзгерістен CSRF токені мен SameSite cookie қорғайды.

Консольда «blocked by CORS policy». Қай жерде түзету керек?

Жауабы мен түсіндірмесі

Дұрыс жауап: Серверде: Access-Control-Allow-Origin тақырыбын қосу

Рұқсат беретін: ресурстың иесі, яғни сервер. Браузер тек соны орындайды.

2Алдын ала сұрау

Preflight

Кейбір сұраныстар қауіптірек: PUT, DELETE, Authorization тақырыбы, JSON денесі. Олар үшін браузер алдымен алдын ала сұрау (preflight) жібереді:

OPTIONS /api/secret
Origin: https://evil.kz
Access-Control-Request-Method: GET
Access-Control-Request-Headers: authorization

Сервер рұқсат берсе (Access-Control-Allow-Origin, Allow-Headers), браузер негізгі сұранысты жібереді. Бермесе: жібермейді, сервер ештеңе орындамайды.

Неге екі түрлі ереже?

Қарапайым сұраныстар (форма, сурет, сілтеме) веб CORS-тан бұрын да болған: оларды тоқтату ескі сайттарды бұзар еді. Ал жаңа, қуатты сұраныстар үшін браузер серверден алдын ала сұрайды.

Бағасы

Preflight: қосымша бір айналым (RTT). Модельде ол 2 × кідіріс қосады. Сондықтан Access-Control-Max-Age тақырыбымен браузерге preflight жауабын кэштеуге рұқсат береді.

Нақты әлемде

  • Фронтенд (app.inside.kz) мен API (api.inside.kz) бөлек тұрса, API сол бір origin-ді нақты тізімдейді.
  • * тек ашық, токенсіз деректерге.
  • Әзірлеуде (localhost:3000 → localhost:8080) де порттары әр түрлі болғандықтан CORS керек.

Енді сен

evil.kz-тен токенмен сұра (preflight сәтсіз), сосын API-ге shop.kz-ті қосып, сол беттен сұра.

3D симуляцияда орында

  • Token-мен сұраныс: OPTIONS сәтсіз, негізгі сұраныс мүлде кетпейді
  • shop.kz-ке рұқсат бер де, сол беттен token-мен сұра: 200 және оқылады
Симуляцияны ашу

Алдымен болжа

evil.kz скрипті енді Authorization тақырыбымен (token) сұраныс жібереді. API evil.kz-ке рұқсат бермейді. Сұраныс серверге жете ме?

Жауабы мен түсіндірмесі

Дұрыс жауап: Жоқ: браузер алдымен OPTIONS сұрайды, рұқсат болмаса негізгі сұранысты мүлде жібермейді

Токені бар не PUT/DELETE сияқты «қарапайым емес» сұраныс алдында браузер preflight жібереді. Сервер бұл origin-ге рұқсат бермесе, негізгі сұраныс жіберілмейді.

Өзіңді тексер

Браузер қашан preflight (OPTIONS) жібереді?

Жауабы мен түсіндірмесі

Дұрыс жауап: Бөтен origin-ге қарапайым емес сұраныс кезінде: PUT, DELETE, Authorization

Қарапайым GET пен форма POST-қа preflight жоқ, қалғанына бар.

Preflight сәтсіз болса, негізгі сұраныс не болады?

Жауабы мен түсіндірмесі

Дұрыс жауап: Жіберілмейді: сервер ештеңе орындамайды

Бұл қарапайым сұраныстан айырмашылығы: preflight негізгі сұранысты алдын ала тоқтатады.

Неге Access-Control-Allow-Origin: * токен не cookie бар сұраныстарға жарамайды?

Жауабы мен түсіндірмесі

Дұрыс жауап: Браузер оны credentials бар сұраныстарда қабылдамайды: кез келген сайт сенің атыңнан оқымауы үшін

Credentials бар болса, сервер нақты origin-ді атауы керек. Бұл кездейсоқ «бәріне ашып қою» қатесінен қорғайды.
