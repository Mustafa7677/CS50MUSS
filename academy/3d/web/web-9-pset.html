Есептер жинағы: full-stack

Problem Set: full-stack

SQL сұраныстар, өз API-ің және event loop болжамы. Тек спецификация мен автотексеруші.

3D симуляцияны ашу Дәрісті оқу

  1. 1-есеп: SQL
  2. 2-есеп: өз API-ің
  3. 3-есеп: event loop

11-есеп: SQL

Спецификация

Дерекқорда екі кесте бар: users (id, name, city) және orders (id, user_id, item, price): 2000 жол. Үш сұраныс жаз. Автотексеруші сенің соңғы SELECT нәтижеңді эталон сұраныстың нәтижесімен жол-жолымен салыстырады (баған реті мен артық бағандар маңызды емес, ал жол реті маңызды).

  1. Астана мен Алматыдан басқа қалалардағы пайдаланушылардың аттары, алфавит бойынша.
  2. 3-пайдаланушының ең қымбат 5 тапсырысы, бағасы кемуі бойынша.
  3. 5-пайдаланушының барлық тапсырыстары: бірақ дерекқор 2000 жолдың бәрін қарамауы керек (индекс арқылы).

Синтаксис еске салғыш

SELECT бағандар FROM кесте
  WHERE шарт AND шарт
  ORDER BY баған [ASC|DESC]
  LIMIT n
CREATE INDEX ON кесте (баған)

Салыстыру: = != < > <= >=. Мәтін: бір тырнақшада: 'Алматы'.

⚠ Жиі қате: ORDER BY жоқ сұраныстың реті: «кездейсоқ». Ол бүгін дұрыс шығуы мүмкін, ертең: жоқ. Рет керек болса, оны әрдайым айт.

Енді сен

Үш сұранысты жазып, әрқайсысын орында.

3D симуляцияда орында

  • 1: Астана мен Алматыдан тыс пайдаланушылар, алфавитпен
  • 2: 3-пайдаланушының ең қымбат 5 тапсырысы
  • 3: 5-пайдаланушының тапсырыстары индекс арқылы
Симуляцияны ашу
Кеңес
  • 1: SELECT name FROM users WHERE city != 'Алматы' AND city != 'Астана' ORDER BY name
  • 3: алдымен CREATE INDEX ON orders (user_id)

Өзіңді тексер

«ORDER BY price DESC LIMIT 5» мен «LIMIT 5» сосын сұрыптау: айырмашылығы бар ма?

Жауабы мен түсіндірмесі

Дұрыс жауап: Иә: SQL алдымен бәрін сұрыптап, сосын 5-ін алады; керісінше болса: кездейсоқ 5 жолдың ішіндегі ең қымбаттары

SELECT-тің логикалық реті: FROM → WHERE → ORDER BY → LIMIT. Сондықтан «ең қымбат 5» дұрыс шығады. Алдымен кез келген 5 жолды алып, сосын сұрыптасақ: ол «ең қымбат» емес.

user_id бойынша индекс бар. Қай сұраныс одан пайда көрмейді?

Жауабы мен түсіндірмесі

Дұрыс жауап: WHERE price > 1000

Индекс тек өзі салынған баған бойынша іздегенде көмектеседі. price бойынша индекс жоқ: толық сканерлеу. Үшінші сұраныста индекс user_id = 5 жолдарын тауып береді, price шарты солардың ішінде ғана тексеріледі.

22-есеп: өз API-ің

Спецификация

Мобильді қосымша командасы сенен endpoint сұрайды:

GET /api/users/:id/orders   →   200, сол пайдаланушының ең қымбат 5 тапсырысы (JSON массив, бағасы кемуі бойынша)

Неге бәрі емес? Әр пайдаланушыда ≈ 250 тапсырыс: телефонға 15 КБ жіберудің мәні жоқ. Нақты API-лер деректі беттеп (pagination) береді: LIMIT пен ORDER BY осы үшін. Бұл: жеке деректер, сондықтан:

  • token-сіз сұрау → 401
  • дұрыс token-мен (secret-123) → 200

Автотексеруші

  1. /api/users/N/orders сұрауына 200 және денесінде дәл N-пайдаланушының ең қымбат 5 тапсырысы, дұрыс ретпен.
  2. Маршрут қорғалған: token-сіз 401, кейін token-мен 200.

Ойлан

  • Маршрут жолындағы :id: параметр. SQL ішінде ол :id болып қолданылады, сервер оны параметр ретінде қояды (SQL injection жоқ).
  • Неге 401, 404 емес? 404: «мұндай ресурс жоқ». Бірақ ресурс бар, тек сен кім екеніңді дәлелдемедің.

Енді сен

Маршрутты құр, тексер, сосын қорға.

3D симуляцияда орында

  • GET /api/users/N/orders → N-нің ең қымбат 5 тапсырысы
  • Token-сіз 401, сосын token-мен 200
Симуляцияны ашу
Кеңес
  • Маршрут: GET, жол /api/users/:id/orders, түрі SQL, SELECT * FROM orders WHERE user_id = :id ORDER BY price DESC LIMIT 5. Сосын «Token керек» қосқышын қос.

Өзіңді тексер

Пайдаланушы кірген, бірақ басқа біреудің тапсырыстарын сұрап тұр. Дұрыс жауап қандай?

Жауабы мен түсіндірмесі

Дұрыс жауап: 403 Forbidden

Сервер оны таниды (401 емес), бірақ бұл деректерге рұқсаты жоқ: 403. Кейбір жүйелер ресурс барын жасыру үшін әдейі 404 қайтарады. Ал 200: қауіпсіздік қатесі (IDOR).

Неге SQL ішінде :id параметрін қолданамыз, жолды жай қосып жазбаймыз?

Жауабы мен түсіндірмесі

Дұрыс жауап: Параметр дерек ретінде ғана қойылады: «2 OR 1=1» сияқты мән SQL болып орындалмайды

/api/users/2 OR 1=1/orders сияқты сұрау жолды қосқан кодта бүкіл кестені ашар еді. Параметрлер деректі кодтан бөледі: SQL injection-нан қорғаудың негізгі тәсілі.

33-есеп: event loop

Спецификация

Екі жаңа бағдарлама: «кірістірілген кезектер» және «жарыс». Әрқайсысының шығысын іске қоспай болжа.

Ережелер (басқа ештеңе керек емес)

  1. Синхронды код соңына дейін орындалады.
  2. Сосын microtask кезегі (Promise.then) толық босатылады: орындалу кезінде қосылған microtask-тар да.
  3. Сосын бір macrotask (setTimeout, желі жауабы): және қайтадан 2-қадам.
  4. Таймерлер кезегі уақыт бойынша: 0 мс-тық таймер 50 мс-тық таймерден бұрын, қай ретпен жазылғанына қарамастан.
  5. fetch жауабы желі кешігуінен кейін келеді; оның .then-і: сол кезде орындалады.

Әдіс

Қағаз ал. Үш баған сыз: стек, microtask-тар, macrotask-тар (уақытымен). Әр жолды «орында» да, кезектерді жаңартып отыр. Бұл: «trace table», бағдарламашының негізгі құралы.

Енді сен

Екі бағдарламаның ретін де дұрыс болжа. Қателессең: «Болжамды тазалау» да, trace table-ды қайта тексер.

3D симуляцияда орында

  • «Кірістірілген кезектер» ретін дұрыс болжа
  • «Жарыс» ретін дұрыс болжа
Симуляцияны ашу

Өзіңді тексер

«Кірістірілген кезектер»-де неге 4 саны 2-ден бұрын шығады?

Жауабы мен түсіндірмесі

Дұрыс жауап: 4: microtask, 2: macrotask; синхронды кодтан кейін алдымен microtask-тар толық босатылады

Синхронды: 1, 6. Microtask: 4 (ол 5-ке таймер қояды). Macrotask кезегі: [2-нің таймері, 5-тің таймері]. 2 шығады → оның ішіндегі Promise 3-ті microtask-қа қояды → ол бірден орындалады. Соңында 5. Нәтиже: 1 6 4 2 3 5.

«Жарыс»-та B неге A-дан бұрын, бірақ C-дан кейін?

Жауабы мен түсіндірмесі

Дұрыс жауап: C: 0 мс таймер; fetch жауабы 20 мс-та келеді; A: 50 мс таймер

Синхронды: E. Microtask: D. Сосын уақыт бойынша macrotask-тар: C (0 мс), желі жауабы (20 мс) → B, A (50 мс). Нәтиже: E D C B A.
