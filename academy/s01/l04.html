S01·04Software Architecture

API жобалау және нұсқалау

  • орта
  • ≈ 50 мин
  • 3 мақсат
  • 5 тапсырма

нұсқа 1.0.0 · тексеру: author-checked

Кино-түсіндіру: сабақтың өзегі бір минуттық мультфильмде. Мәтіні төменде.

Фильмнің мәтіні (сабақ қадамдарынан құрастырылған)
  1. Сұрақ. API - модульдер (не командалар, не компаниялар) арасындағы уәде . Оны жариялаған соң сіз клиенттерді көрмейсіз: мобильді қосымшаның ескі нұсқасы жылдар бойы жұмыс істеуі мүмкін.
  2. Жол. 1-қадам. Келісімшартты жазу: міндетті кіріс өрістері R және кепілденген шығыс өрістері O.
  3. Жол. 2-қадам. Өзгерісті сипаттау: R мен O қалай өзгерді?
  4. Жол. 3-қадам. Критерийді тексеру: R₂ ⊆ R₁ және O₁ ⊆ O₂.
  5. Жол. 4-қадам. Бұзатын өзгеріс болса: жаңа нұсқа (MAJOR) шығарып, ескісін ауыспалы кезеңге қалдыру.
  6. Жол. 5-қадам. Үйлесімді болса: MINOR не PATCH, клиенттерге хабарлау.
  7. Тексер. Қай өзгеріс кері үйлесімді? Жауап: Сұрауға міндетті емес locale өрісін (әдепкі мәні 'kk') қосу.. Дұрыс: R өзгерген жоқ (міндетті емес өріс R-ге кірмейді).
  8. Түйін. Үйлесімділік критерийі. C₂ = (R₂, O₂) C₁ = (R₁, O₁)-ге кері үйлесімді ⇔ R₂ ⊆ R₁ және O₁ ⊆ O₂.
  9. Түйін. Жиі қате: Өрістің атын «тазалық үшін» бір нұсқада өзгерту. Дұрысы: Кеңейту → көшіру → қысқарту үлгісі және MAJOR нұсқа.

AОқу мақсаттары

  • API келісімшартын «міндетті кіріс өрістері» мен «кепілденген шығыс өрістері» жиындары ретінде модельдеу.
  • Кері үйлесімділік шартын (R₂ ⊆ R₁ және O₁ ⊆ O₂) дәлелдеу және өзгерістерді жіктеу.
  • Семантикалық нұсқалауды (MAJOR.MINOR.PATCH) өзгеріс түріне қарай дұрыс қолдану.

BАлғышарттар

  • Қабаттар және тәуелділікті аудару

CҰғымға кіріспе

API - модульдер (не командалар, не компаниялар) арасындағы уәде. Оны жариялаған соң сіз клиенттерді көрмейсіз: мобильді қосымшаның ескі нұсқасы жылдар бойы жұмыс істеуі мүмкін. Сондықтан Senior инженердің ең маңызды сұрағы: «бұл өзгеріс бар клиенттерді сындыра ма?»

Келісімшартты екі жиынмен модельдейміз: сервер талап ететін өрістер R және сервер кепілдейтін жауап өрістері O. Сервер кірісте жомарт, шығыста қатаң болуы керек: жаңа нұсқа аз талап етіп, көп кепілдесе - ескі клиенттер жұмысын жалғастырады. Бұл интуицияны дәл шартқа айналдырып, дәлелдейміз.

DАкадемиялық теория

Анықтама

Келісімшарт және үйлесімділік

Келісімшарт C = (R, O): R - сұраудағы міндетті өрістер, O - жауаптағы кепілденген өрістер. Клиент k C-ға сай: ол R-дегі барлық өрісті жібереді (Sk ⊇ R) және тек O-дағы өрістерді оқиды (Uk ⊆ O). C₂ C₁-ге кері үйлесімді: C₁-ге сай әр клиент C₂-ге де сай.

Теорема

Үйлесімділік критерийі

C₂ = (R₂, O₂) C₁ = (R₁, O₁)-ге кері үйлесімді ⇔ R₂ ⊆ R₁ және O₁ ⊆ O₂.

Дәлелдеу

Дәлелдеу

(⇐) k C₁-ге сай: Sk ⊇ R₁ ⊇ R₂ және Uk ⊆ O₁ ⊆ O₂ - k C₂-ге де сай. (⇒) R₂ ⊄ R₁ болсын: r ∈ R₂ \ R₁ бар. S = R₁ жіберетін клиент C₁-ге сай, бірақ r жоқ - C₂-ге сай емес. O₁ ⊄ O₂ болсын: o ∈ O₁ \ O₂ бар. U = O₁ оқитын клиент C₁-ге сай, бірақ o-ны алмайды. ∎ Салдар: жаңа міндетті емес кіріс өрісі және жаңа жауап өрісі - үйлесімді; жаңа міндетті өріс, өрісті жою не атын өзгерту - бұзатын өзгеріс.

Ескерту

Семантикалық нұсқалау

MAJOR.MINOR.PATCH: бұзатын өзгеріс - MAJOR++ (қалғаны 0), үйлесімді жаңа мүмкіндік - MINOR++ (PATCH = 0), тек қате түзету - PATCH++. Нұсқа нөмірі - клиентке берілген қысқа хабар: «жаңартсам, сынам ба?»

EКөрнекі түсіндірме

v2 жауапқа өріс қосты - үйлесімді. v3 жаңа міндетті кіріс (currency) талап етеді, v4 status өрісінің атын state деп өзгертті - екеуі де ескі клиенттерді сындырады.

FҚадамдап қорыту

Анимациялық түсіндіру: қадамдар кезекпен ашылады. «Ойнату» не → пернесі.

  1. Келісімшартты жазу: міндетті кіріс өрістері R және кепілденген шығыс өрістері O.
  2. Өзгерісті сипаттау: R мен O қалай өзгерді?
  3. Критерийді тексеру: R₂ ⊆ R₁ және O₁ ⊆ O₂.
  4. Бұзатын өзгеріс болса: жаңа нұсқа (MAJOR) шығарып, ескісін ауыспалы кезеңге қалдыру.
  5. Үйлесімді болса: MINOR не PATCH, клиенттерге хабарлау.

GЖұмыс мысалдары

HИнтерактивті эксперимент

v3 енді amount-ты міндетті етпейді. Бұл үйлесімді ме? Критерий бойынша иә - бірақ сервер amount жоқ сұрауды қалай өңдейді? Үйлесімділік тек өрістер емес, мағына да екенін көрсететін мысал ойлап табыңыз.

IЖаттығулар

JМатематикалық пайымдау

Теорема API жобалауды «тәжірибе» деңгейінен «тексерілетін ереже» деңгейіне көтереді: келісімшартты машина оқитын түрде (OpenAPI, protobuf) сақтасаңыз, үйлесімділікті CI автоматты тексере алады. Бірақ критерий тек құрылымды тексереді; өрістің мағынасын өзгерту (amount енді тиынмен емес, теңгемен) - құрылымы бірдей, бірақ бұзатын өзгеріс. Сондықтан нұсқалау - техникалық та, коммуникациялық та жұмыс.

KЖиі қателер

  • Өрістің атын «тазалық үшін» бір нұсқада өзгерту.
    Себебі: Барлық ескі клиент бір сәтте сынады.
    Түзету: Кеңейту → көшіру → қысқарту үлгісі және MAJOR нұсқа.
  • Мағынаны өзгертіп, нұсқаны өзгертпеу (бірлік, уақыт белдеуі, валюта).
    Себебі: Құрылым бірдей болғандықтан тесттер өтеді, ал деректер үнсіз бұзылады.
    Түзету: Мағына өзгерісі - бұзатын өзгеріс; жаңа өріс атауы не жаңа нұсқа.

LМеңгеруді бағалау

Барлық сұраққа дұрыс жауап берсеңіз, сабақ «меңгерілді» деп белгіленеді. Тексеру браузерде өтеді: бұл оқу тексерісі, емтихан емес.

MРефлексия

NТереңірек

Honors

  • Екі JSON Schema файлын салыстырып, бұзатын өзгерістерді тізетін құрал жазыңыз (міндетті өрістер, типтер, enum мәндері).

Research
