    Масштабтау, қауіпсіздік

    Курстың соңғы лекциясы: сайтымыз мыңдаған қолданушыға төтеп беруі үшін не істеу керек және оны қарақшылардан қалай қорғауға болады. Соңында қорытынды жобаңыз күтіп тұр.

    ▶ Түпнұсқа бейнежазба мен материалдар (ағылшынша)
    Бұл апта не туралы

    Осы кезге дейін сайттарымыз тек өз компьютеріміздің ішінде жұмыс істеп келді. Бүгін екі үлкен сұраққа жауап іздейміз: сайтымызға бір мезгілде мыңдаған адам кірсе, ол шыдай ма? (масштабтау) және біреу сайтымызды бұзғысы келсе, не болады? (қауіпсіздік). Қауіпсіздік мысалдарының көбін бетте-ақ «▶» батырмасымен қауіпсіз түрде іске қосып көре аласыз. Лекция соңында қорытынды жобаның сипаттамасы бар.

    Бұл бет сөзбе-сөз аударма емес. Лектор аудиторияда қалай түсіндірсе, біз де солай баяндаймыз: мағынасы мен кодтың бәрі түпнұсқадағыдай, тек әңгіме ана тілімізде жүреді.

    Кіріспе

    Ең алдымен, жүріп өткен жолымызға көз жүгіртейік. Біз HTML мен CSS арқылы қарапайым беттер жасадық. Git пен GitHub арқылы кодтағы өзгерістерді қадағалап, басқалармен бірге жұмыс істеуді үйрендік. Python-мен танысып, Django арқылы веб-қосымшалар жаздық, ал Django модельдері арқылы мәліметті сайтымызда сақтадық. Кейін JavaScript келіп, беттерді тірілтті, анимация мен React интерфейстерді жақсартты. Соңғы аптада бағдарламалық жасақтаманың жақсы тәжірибелері мен оларға көмектесетін технологияларды (тестілеу, CI/CD) талқыладық.

    Бүгін, соңғы лекцияда, екі үлкен тақырып бар: веб-қосымшаны үлкейту (масштабтау) және оны қорғау. Екеуі де «сайт бар» дегеннен «сайт нағыз өмірде жұмыс істейді» дегенге өтетін көпір.

    Масштабталу

    Қазір біздің барлық қосымшамыз тек өз компьютерімізде жүріп тұр. Бірақ ертең оны интернеттегі кез келген адам ашсын десек, қосымшаны серверде (server) іске қосу керек. Сервер дегеніміз - қосымшаларды жүргізуге арнайы бөлінген нақты құрылғы, яғни компьютер.

    Серверді екі жолмен ұстауға болады. Біріншісі - өз ғимаратыңызда (on-premise): серверлерді өзіңіз сатып аласыз, орнатасыз, күтесіз. Екіншісі - бұлтта (cloud): серверлер Amazon немесе Google сияқты басқа компанияның иелігінде, сіз оның орнын жалға аласыз. Екі жолдың да артықшылығы мен кемшілігі бар. Төрт өлшем бойынша салыстырайық:

    • Икемділік (customization). Өз серверіңізде бәрін қалағаныңызша баптай аласыз. Бұлтта бұл еркіндік азырақ.
    • Білім (expertise). Қосымшаны бұлтқа қою әлдеқайда оңай. Өз серверлеріңізді күту үшін мықты маман керек.
    • Баға (cost). Бұлт компаниялары пайда табуы керек, сондықтан олар өз серверін күтуге кеткен шығыннан қымбатырақ ақы алады. Бірақ керісінше, өз серверлеріңізді сатып алу бастапқыда өте қымбат, оларды орнататын маман да керек.
    • Масштабталу (scalability). Бұлтта үлкейту оңайырақ. Мысалы, сайтқа күніне 500 адам кіретін болсын, ал бір күні 500 000 кірді делік. Өз серверіңіз болса, жаңа серверлерді тапсырыс беріп, орнатуыңыз керек, ал сол аралықта көп қолданушы сайтқа кіре алмай қалады. Бұлт компаниялары серверді икемді жалға береді, сіз сайтыңыздағы жүктемеге қарай төлейсіз.

    Қолданушы осы серверге HTTP сұрауын жібергенде, сервер жауап қайтаруы тиіс. Бірақ шын мәнінде сервер бір мезгілде бір ғана сұрау алмайды, олар көп келеді:

    Міне, масштабталу мәселесі осы жерден басталады. Бір сервер бір мезгілде тек белгілі бір санды сұрауды ғана көтере алады. Сондықтан жалғыз сервер шаршап қалған кезде не істейміз деп алдын ала ойлануымыз керек. Өз ғимаратымызда ұстайық па, бұлтта ма, бәрібір бір сервер құлап қалмай қанша сұрау көтеретінін білуіміз қажет. Мұны салыстырмалы сынақ (benchmarking) құралдары өлшейді, мысалы Apache Bench.

    Масштабтау тәсілдері

    Серверіміз қанша сұрау көтеретінін білген соң, оны үлкейтудің жолын таңдаймыз. Екі негізгі тәсіл бар:

    1. Тік масштабтау (vertical scaling). Сервер әлсіреген кезде одан күштірек серверді сатып аламыз немесе жасаймыз. Бұл жол ұзаққа бармайды: жалғыз сервер қаншалықты қуатты болса да, оның шегі бар.
    2. Көлденең масштабтау (horizontal scaling). Сервер әлсіреген кезде тағы бірнеше сервер алып, сұрауларды солардың арасына бөлеміз. Мұны былай елестетіңіз: бір ұста қанша күшті болса да, көп ұсталы шеберхана көбірек жұмыс бітіреді.

    Жүктемені бөлу

    Көлденең масштабтауға көшкенде жаңа сұрақ туады: қай сұрау қай серверге барады? Оны шешетін құрылғы жүктеме бөлгіш (load balancer) деп аталады. Ол кіріп келе жатқан сұрауларды ұстап алып, серверлердің біріне жолдайды:

    Бөлу әдістері

    Қай серверге жіберуді шешудің бірнеше жолы бар. Үшеуін қарастырайық:

    • Кездейсоқ (random). Ең қарапайымы: бөлгіш серверді жай ғана кездейсоқ таңдайды.
    • Кезекпен (round-robin). Бөлгіш серверлерді кезекпен ауыстырып отырады. Үш сервер болса, бірінші сұрау A-ға, екіншісі B-ға, үшіншісі C-ға, төртіншісі қайтадан A-ға барады.
    • Ең аз қосылым (fewest connections). Бөлгіш қазір ең аз сұрау өңдеп жатқан серверді іздеп, жаңа сұрауды соған береді. Сонда бір сервер артық жұмыстан қажымайды. Бірақ мұның бір кемшілігі бар: әр серверде қанша сұрау барын санау кездейсоқ таңдаудан гөрі көбірек уақыт алады.

    Мұны өзіңіз көрсеңіз жақсы түсінесіз. Төменде үш әдісті кішкентай модельмен салыстырамыз. Сұраулар бірінен соң бірі келеді, әрқайсысы серверде бірнеше «такт» жұмыс істейді (кейбірі ұзақ, кейбірі қысқа), ал біз әр серверде бір мезгілде ең көп қанша сұрау жиналғанын санаймыз:

    const servers = ["A", "B", "C"];
// Әр сұрау серверде қанша такт жұмыс істейді (барлық әдіске бірдей сұраулар)
const durations = [5, 1, 1, 6, 1, 2, 7, 1, 1, 5, 1, 2, 6, 1, 1, 7, 2, 1, 5, 1];

// 1) Кездейсоқ
function random(busy) {
    return Math.floor(Math.random() * servers.length);
}

// 2) Кезекпен
let next = 0;
function roundRobin(busy) {
    const i = next;
    next = (next + 1) % servers.length;
    return i;
}

// 3) Ең аз қосылым: қазір ең аз сұрау өңдеп жатқан сервер
function fewest(busy) {
    const counts = busy.map(list => list.length);
    return counts.indexOf(Math.min(...counts));
}

function simulate(name, pick) {
    const busy = [[], [], []];     // әр серверде әлі бітпеген сұраулардың қалған уақыты
    const peak = [0, 0, 0];        // әр серверде бір мезгілде ең көп қанша сұрау болды
    for (const d of durations) {
        const i = pick(busy);
        busy[i].push(d);
        peak[i] = Math.max(peak[i], busy[i].length);
        // бір такт өтті: барлық сұрау бір қадам жақындайды
        for (let k = 0; k < busy.length; k++) {
            busy[k] = busy[k].map(t => t - 1).filter(t => t > 0);
        }
    }
    console.log(name, "ең көп жүктеме:", servers.map((s, i) => s + "=" + peak[i]).join(" "));
}

simulate("кездейсоқ ", random);
next = 0;
simulate("кезекпен  ", roundRobin);
simulate("ең аз қос.", fewest);

    Кездейсоқ әдіс әр жолы әртүрлі нәтиже береді: кейде бір сервер ауырлап кетеді. Кезекпен әдіс сұрау ұзақтығын ескермейді, сондықтан ұзақ сұраулар кездейсоқ бір серверге жиналып қалуы мүмкін. Ал ең аз қосылым әдісі жүктемені көбіне теңестіреді, бірақ әр қадамда санау керек. Бұл мысал өте дөрекі, бірақ ойды көрсетеді: «ең жақсы» әдіс жоқ, әрқайсысының өз бағасы бар.

    Сессия мәселесі

    Көлденең масштабтағанда тағы бір ұсақ, бірақ қиын мәселе шығады. Қолданушы бір серверде жүйеге кірді делік, сессиясы сол серверде сақталды. Келесі сұрауын бөлгіш басқа серверге жіберді, ал ол сервер бұл адамды танымайды! Қолданушы қайтадан деректерін енгізе беруі керек пе? Әрине, жоқ. Бұл мәселені шешудің де бірнеше жолы бар:

    • Жабысқақ сессиялар (sticky sessions). Қолданушы сайтқа алғаш кірген кезде бөлгіш оның қай серверге түскенін есте сақтап, келесі жолдары да сол серверге жібереді. Қауіпті жері: бір серверге жабысып қалған қолданушылар тым көп болып кетсе, сол сервер құлап қалуы мүмкін.
    • Дерекқордағы сессиялар (database sessions). Барлық сессия барлық серверге қолжетімді ортақ дерекқорда сақталады. Қолданушы қай серверге түссе де, оның мәліметі бар. Кемшілігі: дерекқордан оқу мен оған жазуға қосымша уақыт пен есептеу қуаты кетеді.
    • Клиент жағындағы сессиялар (client-side sessions). Мәліметті серверде емес, қолданушының өз браузерінде, cookie ретінде сақтаймыз. Кемшіліктері: қолданушы жалған cookie жасап, басқа адам болып кіріп кетуі мүмкін (қауіпсіздік мәселесі), және cookie әр сұраумен бірге алға-артқа жіберіледі (есептеу мен трафик мәселесі).

    Жүктемені бөлудегідей, мұнда да ең жақсы жалғыз жауап жоқ. Таңдау нақты жағдайыңызға байланысты.

    Автомасштабтау

    Тағы бір мәселе: көптеген сайттарға кейбір уақытта басқа кездегіден әлдеқайда көп кіреді. Мысалы, бұрынғы «Is it New Year's?» («Жаңа жыл ма?») қосымшамызды іске қоссақ, оған желтоқсанның соңы мен қаңтардың басында адам көп кіреді, ал жылдың қалған уақытында азырақ. Қыстағы жүктемеге жететін серверлерді сатып алсақ, олар жылдың қалған уақытында бос тұрып, орын мен қуатты босқа жейді.

    Мұның шешімі - автомасштабтау (autoscaling), бұлттық есептеуде кең тараған идея: сайтыңыз пайдаланатын серверлер саны сұрау санына қарай өздігінен өсіп-кемиді. Той алдында үстелдер санын көбейтіп, тойдан кейін жинап қоятын мейрамхана сияқты.

    Бірақ автомасштабтау да мінсіз емес. Жаңа сервер керек екенін анықтауға және оны іске қосуға уақыт кетеді, ал сол кезде жүктеме өсіп кетуі мүмкін. Тағы бір мәселе: жұмыс істеп тұрған сервер қанша көп болса, соның біреуі істен шығу ықтималдығы да соншалықты жоғары.

    Сервердің істен шығуы

    Бірақ бірнеше сервердің бір пайдасы бар: ол жалғыз ақаулы нүктеден (single point of failure) құтқарады. Бұл - істен шықса, бүкіл сайтты құлататын құрылғы. Жалғыз сервер болса, ол дәл осындай нүкте. Ал көлденең масштабтағанда жүктеме бөлгіш әр серверге үнемі шағын «жүрегің соғып тұр ма?» сұрауларын (жүрек соғысы, heartbeat) жіберіп отырады. Жауап бермеген серверді құлады деп санап, оған жаңа сұрау жіберуді тоқтатады.

    Бірақ тоқтаңыз: енді жалғыз ақаулы нүкте жүктеме бөлгіштің өзіне ауысып кеткен жоқ па? Дұрыс байқадыңыз. Мұны да шешуге болады: негізгі бөлгіш құлап қалса, оның орнын басатын қосалқы бөлгіштер ұстаймыз.

    Ойланып көріңіз: жүрек соғысы (heartbeat) жоқ болса, не болар еді?

    Бөлгіш серверлердің құлағанын білмес еді де, сұраулардың бір бөлігін өлі серверге жіберіп отырар еді. Сонда әр үшінші қолданушы қателік көрер еді (үш сервер болып, біреуі құласа). Жүрек соғысы бөлгішке құлаған серверді жылдам «ұмытуға» мүмкіндік береді.

    Дерекқорларды масштабтау

    Сұрауларды өңдейтін серверлерді ғана емес, дерекқорды да ойлауымыз керек. Біз бұл курсте SQLite қолдандық, ол деректі серверде бір файлда сақтайды. Бірақ деректер көбейген сайын оларды бірнеше файлға, тіпті бөлек серверге бөлген тиімді болады. Сонда дерекқор серверінің өзі келіп жатқан сұрауларға шыдамай қалса, не істейміз? Бұл жерде де бірнеше әдіс бар:

    • Тік бөлу (vertical partitioning). Бұл SQL-ді бастағанда істегенімізге ұқсас: артық қайталанатын мәліметті бір кестеде ұстамай, бірнеше кестеге бөлеміз. (4-лекцияда flights кестесін flights және airports деп бөлгенімізді еске түсіріңіз.)
    • Көлденең бөлу (horizontal partitioning). Бір пішінді, бірақ әртүрлі мәліметі бар бірнеше кесте ұстаймыз. Мысалы, flights кестесін domestic_flights (ішкі рейстер) және international_flights (халықаралық рейстер) деп бөлуге болады. Сонда JFK-дан LHR-ға рейс іздегенде, ішкі рейстерге толы кестені аралап уақыт жоғалтпаймыз. Кемшілігі: бөлінген кестелерді кейін біріктіру (JOIN) қымбатқа түседі.

    Дерекқор репликациясы

    Дерекқорды масштабтап болған соң да бір мәселе қалады: жалғыз ақаулы нүкте. Дерекқор сервері құлап қалса, бүкіл деректіміз жоғалуы мүмкін. Жалғыз сервердің орнына бірнеше сервер қосқандай, дерекқордың да көшірмелерін жасаймыз, сонда біреуі істен шықса да қосымша тоқтамайды. Бұл репликация (replication) деп аталады. Ең танымал екі тәсілі бар:

    • Бір бастапқылы репликация (single-primary replication). Дерекқор көп, бірақ тек біреуі «негізгі» (primary). Негізгіден оқып та, оған жаза да аласыз, ал қалғандарынан тек оқисыз. Негізгі дерекқор жаңарғанда, қалғандары соған қарап жаңартылады. Кемшілігі: жазу жағынан жалғыз ақаулы нүкте әлі қалады.
    • Көп бастапқылы репликация (multi-primary replication). Барлық дерекқордан оқуға да, оған жазуға да болады. Бұл жалғыз ақаулы нүктені жояды, бірақ бір шығыны бар: енді барлық дерекқорды өзекті күйде ұстау әлдеқайда қиын, өйткені әрқайсысы қалғандарындағы өзгерістен хабардар болуы керек. Сондай-ақ қақтығыстар туындауы мүмкін:
      • Жаңарту қақтығысы (update conflict). Бір қолданушы бір дерекқорда жолды өзгертіп жатқанда, екіншісі басқа дерекқорда дәл сол жолды өзгертеді. Дерекқорлар синхрондалғанда қайсысы дұрыс?
      • Бірегейлік қақтығысы (uniqueness conflict). SQL дерекқорындағы әр жолдың бірегей идентификаторы болады. Екі түрлі дерекқорда екі бөлек жазбаға бірдей id беріліп кетуі мүмкін.
      • Жою қақтығысы (delete conflict). Бір қолданушы жолды жойып жатқанда, екіншісі сол жолды жаңартып жатуы мүмкін.
    Ойланып көріңіз: банк шотындағы қалдық үшін қай репликация қауіпті?

    Көп бастапқылы репликацияда екі бөлек дерекқорда бір шоттан бір мезгілде ақша шешілсе, екеуі де «қалдық жеткілікті» деп ойлауы мүмкін. Синхрондалғанда қалдық теріс болып қалады. Сондықтан мұндай деректерде көбіне бір бастапқылы схема таңдалады, ал көп бастапқылыға қақтығыстарды шешетін қосымша ережелер керек.

    Кэштеу

    Дерекқормен жұмыс істегенде есте ұстайтын нәрсе: дерекқорға әр жүгіну қымбат. Сондықтан оған шақыру санын азайтқымыз келеді. Мысалы, The New York Times сайтын алайық. Олардың барлық мақаласы бір дерекқорда болуы мүмкін, ал басты бетті біреу ашқан сайын дерекқорға сұрау жасалып, шаблон қайта құрастырылса, бұл ысырап болар еді: басты беттегі мақалалар секунд сайын өзгермейді ғой.

    Мұны кэштеу (caching) шешеді. Идея мынау: жақын арада қайта керек болады деп күтсек, ақпаратты қолжетімдірек жерге сақтап қоямыз. Мектептегі сөздікке ұқсас: сөзді қайта-қайта қалың сөздіктен іздегенше, үстелге жазып қоясыз.

    Кэшті бірнеше жерде жасауға болады. Біріншісі - қолданушының өз браузерінде. Сонда бет қайта ашылғанда серверге сұрау жіберудің өзі керек емес. Ол үшін HTTP жауабының тақырыбына мына жолды қосамыз:

    Cache-Control: max-age=86400

    Бұл браузерге былай дейді: бұл бетті соңғы 86400 секунд ішінде ашқан болсаң, серверге қайта сұрау жіберудің қажеті жоқ. (86400 секунд - дәл бір тәулік. Түпнұсқа конспектте қателесіп «миллисекунд» деп жазылған, ал max-age әрқашан секундпен өлшенеді.) Бұл әдіс қысқа мерзімде өзгермейтін файлдарға, мысалы CSS-ке жиі қолданылады.

    Бақылауды күшейту үшін жауап тақырыбына ETag та қосуға болады. Бұл құжаттың нақты нұсқасын білдіретін бірегей таңбалар тізбегі. Келесі сұраулар осы тегті өзімен бірге жібереді де, сервер оны ең соңғы құжаттың тегімен салыстырады. Екеуі өзгеше болғанда ғана құжат толық жіберіледі, әйтпесе «өзгеріс жоқ» деген қысқа жауап жеткілікті.

    Одан басқа, сервер жағында да кэш ұстаған пайдалы. Сонда барлық серверге қолжетімді ортақ кэш болады (суретте ортада). Django-ның өзінің кэш фреймворкі бар, ол кэшті жобаға қосуға мүмкіндік береді. Оның бірнеше режимі бар:

    • Көрініс бойынша кэштеу (per-view caching). Белгілі бір көрініс бір рет жүктелген соң, келесі көрсетілген уақыт ішінде функцияны қайта орындамай-ақ дәл сол бетті көрсете береді.
    • Шаблон бөлігін кэштеу (template-fragment caching). Шаблонның тек белгілі бөліктерін кэштейді. Мысалы, сирек өзгеретін навигация панелін әр жолы қайта құрудың қажеті жоқ.
    • Төмен деңгейлі кэш API (low-level cache API). Бұл ең икемді тәсіл: қалаған ақпаратыңызды кэшке сақтай аласыз.

    Django-да кэштеуді қалай орнату керегін мұнда егжей-тегжейлі қарастырмаймыз, қызықсаңыз құжаттамаға көз салыңыз.

    Ойланып көріңіз: кэштің қандай қауіпті жағы бар?

    Кэштегі ақпарат ескіріп қалуы мүмкін. Мысалы, жаңалық сайтында мақала түзетілген, ал кэштен әлі ескі нұсқа көрсетіліп тұр. Сондықтан кэштің «өмір сүру уақытын» (max-age) дұрыс таңдау керек: жиі өзгермейтін нәрсеге ұзақ, жиі өзгеретінге қысқа.

    Қауіпсіздік

    Енді сайтымыздың қауіпсіздігін қамтамасыз ету жайын қарастырамыз. Бұл кез келген бір ғана шара емес: қауіпсіздік курстағы барлық тақырыпқа дерлік тиіседі. Сондықтан біз курстың басынан бастап ретімен жүреміз.

    Git және GitHub

    Git пен GitHub-тың ең үлкен күшінің бірі - ашық бастапқы кодты бағдарламаны (open-source software) бөлісу мен оған үлес қосуды оңай ету. Ашық кодты интернеттегі кез келген адам көре алады және оған үлес қоса алады. Бірақ бұның кері жағы бар: бір кезде паролі немесе API-кілті бар файлды коммит жасап жіберсеңіз, бұл құпия мәліметтер бүкіл әлемге ашық болып қалуы мүмкін.

    Қате жасап қойсаңыз

    Құпия кілтті коммитке қосып, GitHub-қа жіберіп қойсаңыз, оны жай ғана жою жеткіліксіз: Git тарихында ол қала береді. Дұрыс жол - сол кілтті дереу ауыстыру (қызмет көрсетушінің сайтында ескі кілтті өшіріп, жаңасын жасау). Одан кейін ғана тарихты тазалаңыз. Алдын алу үшін құпияларды ешқашан кодқа жазбаңыз (төмендегі «Орта айнымалылары» бөлімін қараңыз).

    HTML және алаяқтық

    HTML-дан көптеген осалдықтар шығады. Ең кең тарағаны - фишинг (phishing attack). Бұл жағдайда қолданушы бір бетке барамын деп ойлайды, ал шын мәнінде басқа бетке түседі. Сайт жасаушы ретінде мұны толық болдырмай алмауымыз мүмкін, бірақ өзіміз интернетті пайдаланғанда оны әрдайым есте ұстауымыз керек. Мысалы, зиянкес мынадай HTML жазуы мүмкін:

    <!DOCTYPE html>
<html lang="en">
    <head>
        <title>Link</title>
    </head>
    <body>
        <a href="https://cs50.harvard.edu/">https://www.google.com/</a>
    </body>
</html>

    Сілтеменің көрінетін мәтіні Google сияқты, ал шын href мекенжайы мүлде басқа. Мұны төмендегі безендірілмеген үлгіден көріңіз (қауіпсіздік үшін сілтеме ешқайда апармайды, тек шын мекенжайын көрсетеді):

    <p>Банкке өту үшін мына сілтемені басыңыз:</p>
<p><a id="fake" href="https://cs50.harvard.edu/">https://www.google.com/</a></p>
<p id="out" style="color:#b3261e;font-weight:bold"></p>
<script>
  var a = document.getElementById("fake");
  a.addEventListener("click", function (e) {
    e.preventDefault();   // шын өтпейміз
    document.getElementById("out").textContent =
      "Көрінген мәтін: " + a.textContent + "  |  Шын мекенжай: " + a.href;
  });
</script>

    Тағы бір нәрсе: HTML қолданушыға сұрау барысында жіберіледі, яғни сайттың орналасуы мен стилін бәрі көре алады. Мысалы, қарақшы кез келген банктің сайтына кіріп, оның HTML-ін толық көшіріп алып, өз сайтына қойып, дәл сондай көрінетін сайт жасай алады. Сонан соң кіру формасын өзгертіп, барлық логин мен пароль өзіне келетіндей қылады. (Түпнұсқа лекцияда лектор бұл әдісті әдейі көрсетіп, студенттерден сілтемені басар алдында мекенжайды тексеретін-тексермейтінін байқаған. Сіз де әдетке айналдырыңыз!)

    Қалай қорғанамыз

    Сілтемені басар алдында тышқанды үстіне апарып, браузердің төменгі жолағындағы шын мекенжайды қарау; сайт мекенжайының жазылуын (мысалы, kaspi.kz орнына kaspl.kz) тексеру; сезімтал деректерді енгізер алдында қара құлыпты (HTTPS) көру.

    HTTPS

    Біз бұрын айтқандай, интернеттегі әрекеттердің көбі HTTP хаттамасымен өтеді, бірақ барған сайын көп операция HTTPS-ке көшуде. HTTPS - HTTP-дің шифрланған нұсқасы. HTTP немесе HTTPS пайдаланғанда ақпарат бір компьютерден екіншісіне бірнеше аралық сервер арқылы жетеді. Сіздің хатыңыз қабылдаушыға барғанша бірнеше пошта бөлімшесінен өтетін қағаз хат сияқты.

    Осы аралық берілістердің бәрінің қауіпсіз екеніне кепілдік беру көбіне мүмкін емес. Сондықтан тасымалданатын мәліметті шифрлау (encryption) өте маңызды. Бұл хабардағы таңбаларды өзгертіп, оны тек жіберуші мен қабылдаушы түсінетіндей, ал басқа ешкім түсінбейтіндей ету.

    Құпия кілтті криптография

    Бір тәсіл - құпия кілтті криптография (secret-key cryptography). Мұнда жіберуші мен қабылдаушының екеуінде де тек өздері білетін ортақ құпия кілт болады. Жіберуші хабарды осы кілтпен шифрлап жібереді, қабылдаушы сол кілтпен оны ашады (дешифрлайды). Бұл әдіс өте сенімді, бірақ практикада үлкен қиындық туғызады: екеуінде де кілт болу үшін алдымен кілтті қауіпсіз түрде алмасу керек, яғни бетпе-бет кездесу керек. Біз күн сайын жүздеген сайтпен жұмыс істейміз, олардың бәрімен жеке кездесу мүмкін емес.

    Ашық кілтті криптография

    Интернеттің қазіргідей жұмыс істеуіне мүмкіндік берген керемет жаңалық - ашық кілтті криптография (public-key cryptography). Мұнда екі кілт бар: біреуі ашық, оны кез келген адамға беруге болады, ал екіншісі жеке, оны құпия ұстау керек. (Кілт жұбын жасаудың бірнеше математикалық әдісі бар, олардың өзі бір курстың тақырыбы, сондықтан бұл жерде талқыламаймыз.) Кілттер жасалған соң, жіберуші қабылдаушының ашық кілтін тауып, хабарды сонымен шифрлайды. Қабылдаушы оны өзінің жеке кілтімен ашады. Шифрланған хабарды ұстап алған қарақшы оны аша алмайды, тіпті қабылдаушының ашық кілтін білсе де, өйткені ашу үшін жеке кілт керек.

    Қарапайым салыстырумен: ашық кілт - ашық тұрған пошта жәшігі. Кез келген адам оған хат сала алады, бірақ жәшікті тек кілті бар иесі ашады. HTTP орнына HTTPS пайдаланғанда, сұрауымыз дәл осылай ашық кілтті шифрлаумен қорғалатынын білеміз.

    Дерекқорлар

    Сұраулар мен жауаптардан бөлек, дерекқорымыздың да қауіпсіз болуын қадағалау керек. Бізге жиі сақтау қажет болатын нәрсе - пайдаланушылар туралы мәлімет: логиндер мен парольдер. Мынадай кестені елестетіңіз: бір бағанда username, екіншісінде password, парольдер ашық мәтінмен жазылған.

    Бірақ парольдерді ешқашан ашық мәтінмен (plaintext) сақтамаңыз. Бөгде адам дерекқорға қол жеткізсе, бәрі ашылып қалады. Орнына хэш-функцияны (hash function) қолданамыз. Ол кез келген мәтінді алып, оған ұқсамайтын, кездейсоқ көрінетін жолға айналдырады. Кестеде парольдің өзі емес, оның хэші (hash) тұрады. Мұны Python-да көруге болады. «Іске қосу» түймесін басыңыз:

    import hashlib

for password in ["qwerty", "qwerty1", "Qwerty"]:
    h = hashlib.sha256(password.encode()).hexdigest()
    print(password, "->", h)

    Байқадыңыз ба? Парольдер бір әріпке ғана өзгерсе де, хэштер мүлде басқа. Және хэштердің ұзындығы бірдей (64 символ), парольдің ұзындығына тәуелсіз. Енді ең маңызды нәрсе: хэш-функция бір бағытты (one-way). Ол парольді хэшке айналдыра алады, бірақ хэштен парольді кері қайтара алмайды. Сүт қатығына айналады, бірақ қатықтан сүтті қайта алу мүмкін емес сияқты.

    Бұдан не шығады? Пайдаланушы деректерін осылай сақтайтын компания пайдаланушылардың парольдерін білмейді. Пайдаланушы кіргісі келгенде, енгізген парольді қайтадан хэштеп, сақталған хэшпен салыстырады. Бұл жұмыстың бәрін Django біз үшін істеп қояды. Сонымен қатар, пайдаланушы парольді ұмытса, компания ескі парольді ешқашан айта алмайды, жаңасын жасатады. «Ескі паролін жібердім» деп жазған сайтты көрсеңіз, ол парольді ашық мәтінмен сақтап отыр деген сөз!

    Енді хэштеуге «тұз» (salt) қосып көрейік. Тұз - әр пайдаланушыға жеке кездейсоқ қосымша жол: бірдей парольдің хэштері де әртүрлі болады, және қарақшы алдын ала есептелген хэш кестелерін (rainbow table) пайдалана алмайды:

    import hashlib

def hash_password(password, salt=""):
    return hashlib.sha256((salt + password).encode()).hexdigest()

# Екі пайдаланушының паролі бірдей
print("тұзсыз :", hash_password("qwerty") == hash_password("qwerty"))
print(hash_password("qwerty"))

# Әр пайдаланушыда өз тұзы бар
a = hash_password("qwerty", "x7Gq")
b = hash_password("qwerty", "m2Zp")
print("тұзбен :", a == b)
print(a)
print(b)

# Кіру: енгізген парольді қайта хэштеп, салыстырамыз
def verify(password, salt, stored):
    return hash_password(password, salt) == stored

print(verify("qwerty", "x7Gq", a))
print(verify("qwerty!", "x7Gq", a))
    Нағыз жобада

    Бұл мысал - идеяны түсіндіру үшін. Нағыз қосымшада SHA-256-ны өзіңіз қолданбаңыз: Django парольді арнайы баяу алгоритммен (PBKDF2 және т.б.), кездейсоқ тұзбен хэштейді. Баяу болуы әдейі: қарақшыға миллиондаған болжамды тез тексеру қиындайды. Яғни User моделін және Django-ның кіру жүйесін пайдаланыңыз, парольді өзіңіз сақтамаңыз.

    Ойланып көріңіз: екі пайдаланушының хэштері бірдей болса, нені білеміз?

    Тұзсыз сақталған болса, екеуінің паролі бірдей екенін. Қарақшы бір хэшті «қолмен» бұзса, бірдей хэшті барлық жерде көреді. Тұз бұл мәселені шешеді: бірдей пароль әртүрлі хэш береді.

    Қандай ақпаратты жария етеміз?

    Кейде әзірлеуші ретінде өзіңіз шешуіңіз керек: қанша ақпаратты «ағызып» жіберуге дайынсыз? Мысалы, көп сайтта «парольді ұмыттым» беті болады: онда электрондық поштаны енгізесіз. Жіберген соң сіз екі түрлі хабар көрсетуіңіз мүмкін: «Хат жіберілді» немесе «Мұндай пошта жоқ».

    Бірақ байқаңыз: әртүрлі поштаны енгізіп көру арқылы кез келген адам қай пошта сайтта тіркелгенін біле алады. Бұл мүлде маңызсыз болуы мүмкін (сайтты пайдаланудың еш қаупі жоқ жерде). Бірақ белгілі бір сайтқа мүше екеніңіздің өзі қауіп төндіретін болса (мысалы, зорлық-зомбылыққа ұшырағандарға арналған қолдау қауымдастығы), бұл өте жауапсыз қадам. Мұндайда әрқашан бірдей хабар көрсеткен дұрыс: «Егер бұл пошта тіркелген болса, хат жібердік».

    Ақпарат тағы бір жолмен ағып кетуі мүмкін: жауаптың келу уақыты. Қате поштасы бар адамды қабылдамау, поштасы дұрыс, бірақ паролі қате адамды қабылдамаудан гөрі азырақ уақыт алуы ықтимал. Қарақшы осы айырмашылықты өлшеп, қай пошта тіркелгенін біле алады.

    SQL-инъекциясы

    Бұрын көргеніміздей, кодымызда тікелей жазылған SQL сұрауларын қолданған сайын SQL-инъекциясына (SQL injection attack) мұқият болуымыз керек. Мұнда қолданушы енгізген мәтін сұраудың бөлігіне айналып, оның мағынасын өзгертеді. Мұны Python-дағы кішкентай дерекқормен көрсетейік (ол браузердің ішінде, жадта ғана жұмыс істейді, ешқандай нақты дерекқорға тиіспейді):

    import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE users (username TEXT, password TEXT)")
db.execute("INSERT INTO users VALUES ('aigerim', 'secret1')")
db.execute("INSERT INTO users VALUES ('nurlan', 'secret2')")

def login_unsafe(username, password):
    # ҚАУІПТІ: қолданушы мәтінін сұраудың ішіне тікелей қоямыз
    query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
    print("Сұрау:", query)
    return db.execute(query).fetchall()

def login_safe(username, password):
    # ҚАУІПСІЗ: параметрлер сұраудан бөлек беріледі
    query = "SELECT * FROM users WHERE username = ? AND password = ?"
    return db.execute(query, (username, password)).fetchall()

print(login_unsafe("aigerim", "secret1"))
print(login_unsafe("aigerim", "қате"))

# Шабуылшы пароль орнына мынаны жазады:
attack = "' OR '1'='1"
print(login_unsafe("aigerim", attack))

print(login_safe("aigerim", attack))

    Қараңыз: шабуылшы парольді білмесе де, ' OR '1'='1 деп жазып, шартты «әрқашан ақиқат» етіп жіберді. Сұрау бұрын «логин мен пароль сәйкес келсін» дегенді білдірсе, енді «немесе бір тең бір» дегенді білдіреді, бұл әрқашан ақиқат. Нәтижесінде жүйе ішіне кіргізіп жібереді. Ал екінші нұсқада (? белгісімен) қолданушы мәтіні ешқашан SQL ретінде түсіндірілмейді, жай ғана мән болып қалады. Django ORM-ы мұны өзі істейді. Сондықтан тікелей SQL жазғанда әрқашан параметрленген сұрауды қолданыңыз.

    API-лер

    Біз JavaScript-ті API-лермен бірге бір беттік қосымшалар жасауға жиі қолданамыз. Өз API-ңызды жасасаңыз, оны қорғаудың бірнеше жолы бар:

    • API-кілттер (API keys). Сіз берген кілті бар API-клиенттердің сұрауын ғана өңдейсіз.
    • Сұрау жиілігін шектеу (rate limiting). Бір қолданушы белгілі уақыт ішінде жасай алатын сұрау санын шектейсіз. Бұл қызмет көрсетуден бас тарту шабуылынан (Denial of Service, DoS attacks) қорғайды: мұнда зиянкес API-ге сонша көп сұрау жібереді, сервер істен шығады. (Салыстырсақ, бір адам дүкенге мың рет кіріп-шығып, басқа сатып алушыларға жол бермей тастағандай.)
    • Маршрутты аутентификациялау (route authentication). Көп жағдайда барлық мәліметті барлығына ашқымыз келмейді. Сондықтан белгілі бір қолданушылар ғана белгілі бір деректі көре алатындай етеміз.

    Орта айнымалылары

    Парольді ашық мәтінмен сақтамайтынымыз сияқты, API-кілттерді де бастапқы кодқа жазбау керек (есіңізде болса, Git бөлімінде осы туралы айттық). Мұны болдырмаудың кең тараған жолы - орта айнымалылары (environment variables). Бұл операциялық жүйеде не сервер ортасында сақталатын айнымалылар. Енді кодқа мәтінді өзін емес, орта айнымалысына сілтемені жазамыз:

    import os

# Терминалда: export MY_API_KEY="abc123"
key = os.environ.get("MY_API_KEY", "орнатылмаған")
print("Кілт:", key)

    Кілт кодта жоқ, ол тек сіздің компьютеріңізде (не серверде) тұр. Сондықтан кодты GitHub-қа қойсаңыз да, кілт сыртқа шықпайды. Django жобаларында да SECRET_KEY сияқты баптауларды дәл осылай ортадан оқуға болады.

    JavaScript

    Зиянкестер JavaScript арқылы да бірнеше шабуыл жасай алады. Бірі - сайтаралық скрипттеу (cross-site scripting, XSS). Бұл жағдайда пайдаланушы өз JavaScript кодын жазып, оны сіздің сайтыңызда орындатады. Мысалы, бізде Django қосымшасы бар, жалғыз URL-мен:

    urlpatterns = [
    path("<path:path>", views.index, name="index")
]

    және жалғыз көріністі (view):

    def index(request, path):
    return HttpResponse(f"Requested Path: {path}")

    Бұл сайт қолданушыға оның қандай URL-ге барғанын айтады: /hello ашсаңыз, «Requested Path: hello» шығады. Бірақ енді қолданушы URL-дің ішіне JavaScript жазып, оны бетке енгізе алады: мысалы, адрес жолына <script>alert("Hi")</script> жазса, браузер ол кодты бет мазмұны деп қабылдап, орындайды. Бұл alert мысалы онша зиянды емес, бірақ DOM-ды өзгертетін не fetch арқылы сұрау жіберетін код қосу да одан қиын емес. Мысалы, зиянкес cookie-ді өз серверіне жібере алады.

    Мұны қауіпсіз түрде өз көзіңізбен көріңіз. Төмендегі бетте «URL» орнына жай айнымалы бар, ал alert орнына зиянсыз мәтін өзгереді. Біріншісі «аңғал» әдіс (innerHTML), екінші дұрыс әдіс (textContent):

    <p><b>Кіріс (қолданушы жазған мәтін):</b></p>
<pre id="inp"></pre>
<p><b>Қауіпті бет (innerHTML):</b></p>
<div id="unsafe" style="border:1px solid #b3261e;padding:6px"></div>
<p><b>Қауіпсіз бет (textContent):</b></p>
<div id="safe" style="border:1px solid #1f7a4d;padding:6px"></div>
<script>
  // "Шабуылшы" жіберген мәтін: сурет жүктелмейді, сондықтан onerror іске қосылады
  var path = '<img src="x" onerror="document.getElementById(\'hacked\').textContent = \'Шабуылшының коды орындалды!\'">';
  document.getElementById("inp").textContent = path;
  document.getElementById("unsafe").innerHTML = "Requested Path: " + path;
  document.getElementById("safe").textContent = "Requested Path: " + path;
</script>
<p id="hacked" style="color:#b3261e;font-weight:bold"></p>

    Қызыл жақтаудағы бетте шабуылшының коды орындалды (астында қызыл хабар шықты), ал жасыл жақтаудағы бет мәтінді жай мәтін ретінде көрсетті. Қорғану ережесі: қолданушыдан келген мәтінді ешқашан HTML ретінде түсіндірмеңіз, оны экрандаңыз (escape): < таңбасын &lt; деп өзгертіңіз. Django шаблондары мұны әдепкіде өздігінен істейді, ал жоғарыдағы HttpResponse(f"...") оны істемейді. Осы жаттығуды жаттығулар бөлімінде өзіңіз жасайсыз.

    Сайтаралық сұрауды жалған жасау (CSRF)

    Django-ның CSRF шабуылдарынан қорғанысын біз бұрын талқыладық, енді бұл қорғаныссыз не болатынын көрейік. Банктің yourbank.com деген, ақшаңызды шотыңыздан аударатын URL-і бар делік. Біреу осы аударымды жасайтын сілтемені оп-оңай жаза алады:

    <a href="http://yourbank.com/transfer?to=brian&amt=2800">
    Click Here!
</a>

    Бұл шабуыл сілтемеден де астыртынырақ болуы мүмкін. Сол URL-ді суреттің ішіне жасырсақ, браузер суретті жүктемек болғанда URL-ге өзі кіріп кетеді:

    <img src="http://yourbank.com/transfer?to=brian&amt=2800">

    Сондықтан күйді өзгертетін (ақша аудару, жазбаны жою) кез келген әрекетті қосымшаңызда тек POST сұрауымен қабылдау керек. Бірақ банк POST талап етсе де, жасырын форма өрістері арқылы пайдаланушыны алдап, сұрауды жібертуге болады. Мына форма тіпті түймені басуды да күтпейді, өздігінен жіберіледі!

    <body onload="document.forms[0].submit()">
    <form action="https://yourbank.com/transfer"
    method="post">
        <input type="hidden" name="to" value="brian">
        <input type="hidden" name="amt" value="2800">
        <input type="submit" value="Click Here!">
    </form>
</body>
    Бұл мысалдар неге бетте іске қосылмайды?

    Бұл код шын формаларды басқа сайтқа жібереді, сондықтан біз оны әдейі «▶» түймесінсіз қалдырдық. Тек оқып, идеясын түсінсеңіз жеткілікті.

    Бұл - сайтаралық сұрауды жалған жасау (cross-site request forgery, CSRF) шабуылының мысалы. Біз мұндай шабуылдардан CSRF-токен арқылы қорғанамыз: бетті жүктегенде бірегей токен жасап, оны форманың ішіне салып қоямыз, ал кейін тек жарамды токені бар формаларды қабылдаймыз. Шабуылшының беті бұл токенді білмейді, сондықтан оның жалған формасы қабылданбайды. Django-да бұл формаға бір жол қосу арқылы істеледі:

    <form action="/transfer" method="post">
    {% csrf_token %}
    <input type="text" name="to">
    <input type="number" name="amt">
    <input type="submit" value="Transfer">
</form>

    Әрі қарай не?

    Біз бұл курста Django және React сияқты көптеген веб-фреймворктерді талқыладық, бірақ байқап көруге тұрарлық басқалары да бар:

    • Сервер жағы: Express.js, Ruby on Rails, Flask және т.б.
    • Клиент жағы: AngularJS, React, Vue.js, React Native және т.б.

    Болашақта сайтыңызды интернетке орналастырғыңыз (deploy) келеді. Ол үшін де бірнеше қызмет бар: Amazon Web Services, GitHub (GitHub Pages), Heroku, Netlify, Google Cloud, Microsoft Azure және т.б.

    Біз көп жол жүріп өттік, бірақ веб-бағдарламалау әлемінде үйренетін нәрсе әлі көп. Кейде бәрі өте көп сияқты көрінуі мүмкін. Дегенмен ең жақсы үйрену жолы - жобаға кіріп кетіп, қаншалықты алысқа жете алатыныңызды көру. Сіздің веб-дизайн ұғымдарының берік негізі бар екеніне және идеяны өз жұмыс істейтін сайтыңызға айналдыра алатыныңызға сенеміз.

    Қорытынды

    Бүгін біз екі үлкен тақырыпты қарастырдық: сайтты үлкейту және қорғау. Негізгі ұғымдар:

    • сервер: өз ғимаратыңызда не бұлтта; тік (күштірек сервер) және көлденең (көбірек сервер) масштабтау;
    • жүктеме бөлгіш және оның әдістері: кездейсоқ, кезекпен, ең аз қосылым; сессия мәселесі: жабысқақ, дерекқордағы, клиент жағындағы;
    • автомасштабтау, жалғыз ақаулы нүкте және жүрек соғысы;
    • дерекқорды масштабтау: тік және көлденең бөлу; репликация (бір бастапқылы мен көп бастапқылы) және қақтығыстары;
    • кэштеу: Cache-Control, ETag, Django-ның кэш фреймворкі;
    • қауіпсіздік: коммитке құпия салмау, фишинг, HTTPS, құпия және ашық кілтті шифрлау;
    • парольдерді хэштеу (және тұз), ақпарат ағуы, SQL-инъекция және параметрленген сұраулар;
    • API қорғанысы: кілттер, сұрау жиілігін шектеу, аутентификация; кілттерді орта айнымалыларында сақтау;
    • XSS (қолданушы мәтінін экрандау) және CSRF (токен, POST).

    Өзіңізді тексеріңіз

    1. Сайтқа келетін сұрау бірнеше есе көбейді. «Бұл серверді екі есе қуатты серверге ауыстырамыз» деген шешім қай масштабтауға жатады және оның басты шектеуі қандай?

    Бір серверді күшейту - тік масштабтау. Оның шегі бар, сондықтан көбіне көлденең масштабтау қажет болады.

    2. Жүктеме бөлгіш үш серверге сұрауларды A, B, C, A, B, C... тәртібімен жібереді. Бұл қай әдіс?

    Round-robin серверлерді кезекпен ауыстырады. Ең аз қосылым әдісі әр серверде қанша сұрау барын санау үшін қосымша уақыт жұмсайды.

    3. Қолданушы сайтқа кірді, ал келесі сұрауы басқа серверге түскенде жүйе оны «танымай» қалды. Қай шешімнің кемшілігі - әр сұраумен cookie жіберу және жалған cookie жасау қаупі?

    Мәліметті браузерде cookie ретінде сақтасақ, ол әр сұраумен бірге жүреді, ал қолданушы оны жалғандауы мүмкін. Жабысқақ сессияда басты қауіп - бір серверге қолданушылар тым көп жиналуы.

    4. Көп бастапқылы (multi-primary) репликацияда қай мәселе туындауы мүмкін, бірақ бір бастапқылыда ол болмайды?

    Көп бастапқыда жазу бірнеше дерекқорға мүмкін, сондықтан жаңарту, бірегейлік және жою қақтығыстары болады. Бір бастапқыда жазу тек біреуіне ғана жасалады.

    5. Қолданушы парольді ұмытып, «Парольді қалпына келтір» батырмасын басты. Қауіпсіз жүйе не істейді?

    Хэш-функция бір бағытты, сондықтан жүйе нақты парольді білмейді және оны қайтара алмайды. Ескі парольді жіберетін сайт оны ашық мәтінмен сақтап отыр.

    6. query = f"SELECT * FROM users WHERE name = '{name}'" кодында name орнына ' OR '1'='1 жазылса, не болады?

    Қолданушы мәтіні сұраудың бөлігіне айналып, мағынасын өзгертті. Шешім: параметрленген сұрау (?).

    7. Django-сыз жазылған бетте div.innerHTML = "Сәлем, " + name бар, ал name URL-ден алынады. Қандай шабуыл мүмкін және қалай қорғанамыз?

    Қолданушы мәтінін HTML ретінде қою - XSS-тің классикалық жолы. textContent мәтінді жай мәтін ретінде көрсетеді.

    8. Нағыз банк сайты /transfer үшін тек POST қабылдайды, бірақ CSRF-токені жоқ. Шабуылшының беті сізді қалай алдай алады?

    POST-тың өзі жеткіліксіз. Басқа сайттың беті форманы жасырып, onload кезінде жібере алады, ал браузер банктің cookie-ін қосып жібереді. Токен осыны тоқтатады.

    Жаттығулар: қауіпсіздік коды

    Сайттың өз жаттығулары, ресми тапсырма емес

    Бұл аптаның ресми problem set-і жоқ: оның орнына қорытынды жоба келеді. Дегенмен лекцияны бекіту үшін осы сайтқа арнап екі шағын жаттығу қостық. Екеуі де таза Python, браузерде тексеріледі. Бұл - ресми CS50 тапсырмасы емес.

    Оңай

    Парольді хэштеу және тексеру

    passwd.py файлында екі функция жазыңыз. hash_password(password, salt) тұзды парольдің алдына қосып (salt + password), SHA-256 хэшін 16-лық жол (hexdigest()) ретінде қайтарсын. verify(password, salt, stored) енгізілген парольді сол тұзбен хэштеп, сақталған хэшке тең болса True, әйтпесе False қайтарсын.

    Кеңес

    hashlib.sha256(жол.encode()).hexdigest() екенін еске түсіріңіз: хэш-функцияға жол емес, байттар керек, сондықтан алдымен .encode(). verify ішінде hash_password-ты қайта қолданыңыз.

    Тексеру
    • hash_password тұз бен парольді біріктіріп, SHA-256 hexdigest қайтарады.
    • verify парольді салыстырмай, хэшті салыстырады.

    Орташа

    escape_html: XSS-тен қорғану

    escape.py файлында escape_html(text) функциясын жазыңыз. Ол жолдағы бес арнайы таңбаны HTML-мнемоникаларына ауыстырып, жаңа жолды қайтарсын: & → &amp;, < → &lt;, > → &gt;, " → &quot;, ' → &#x27;.

    Кеңес

    Ауыстыру ретіне назар аударыңыз! & таңбасын бірінші ауыстырмасаңыз, басқа ауыстырулардың шығарған & белгілері қайтадан өзгертіліп кетеді (< → &lt; → &amp;lt;).

    Тексеру
    • Бес таңба да ауыстырылады, & бірінші.
    • Функция жаңа жолды қайтарады (print емес).

    Қорытынды жоба

    Курстың соңғы кезеңі - қорытынды жоба (final project). Лекциялар мен алдыңғы жобалардың бәрі осыған дайындық болды. Ресми сипаттама: cs50.harvard.edu/web/project. Мұнда толық емес, негізгі талаптарды қысқаша айтамыз. Дәл нақты талаптар мен тапсыру жолын ресми беттен міндетті түрде тексеріңіз, себебі олар өзгеруі мүмкін.

    Компьютерде орындалады

    Қорытынды жоба Django, жергілікті дерекқор, GitHub және бейне жазбаны қажет етеді, сондықтан ол сайттағы автотексеруші жасай алатын нәрсе емес. Оны өз компьютеріңізде (не cs50.dev-те) жасап, ресми нұсқаулық бойынша тапсырасыз.

    Негізгі талаптар

    • Өз идеяңыздан шығатын веб-қосымша: ұқсас курстық жобалардан (іздеу жүйесі, вики, электрондық сауда, пошта, әлеуметтік желі) айтарлықтай ерекше болуы керек. Яғни жай ғана олардың көшірмесі болмауы тиіс.
    • Серверде кемінде бір Django қосымшасы (кемінде бір модельмен), клиентте JavaScript қолданылады.
    • Мобильді бейімделгіш (mobile-responsive): телефонда да ыңғайлы көрінуі керек.
    • Жоба қалтасында README.md файлы болуы керек. Онда жобаның не екенін, неге ол ерекше және күрделі (distinctiveness and complexity) екенін, әр файлда не бар екенін және қосымшаны қалай іске қосу керегін жазасыз.
    • Жобаңызды көрсететін қысқа бейне. Ұзақтығы мен жариялау жолын ресми беттен қараңыз.

    Идеялар (Қазақстан контексінде)

    Қайдан бастарыңызды білмесеңіз, өз өміріңізден бастаңыз: ең жақсы жоба - нақты мәселені шешетін жоба. Бірнеше идея (бәрін өзіңіз өзгертіп, күрделендіріңіз):

    • Тоғызқұмалақ онлайн ойыны: екі ойыншы, ойын күйі дерекқорда, JavaScript-пен тақта анимациясы.
    • Қазақ тілі сөз үйрену карточкалары: аралық қайталау (spaced repetition) алгоритмімен, пайдаланушы прогресі модельде сақталады.
    • Қазақстан тарихының уақыт сызығы: оқиғаларды қосу, санаттау, картада көрсету.
    • Қала көлігінің кестесі (автобус тоқтайтын жерлері мен уақыты): іздеу, таңдаулылар, мобильді интерфейс.
    • Ұлттық тағам рецептері: дәмдеуіштер мен адам санына қарай мөлшерді автоматты қайта есептеу (JavaScript).
    • Экоакция/еріктілер картасы (мысалы, сенбілік ұйымдастыру): іс-шара қосу, қатысуға жазылу.
    • Домбыра сабағы не спорт жаттығуының трекері: жаттығу журналы, статистика графигі.
    • Мектеп кітапханасы каталогы: кітап беру, қайтару, мерзімі өту ескертуі.
    Қауіпсіздік - жобаңыздың бөлігі

    Осы апта үйренгеніңізді жобаңызда қолданыңыз: SECRET_KEY мен басқа құпияларды орта айнымалыларында сақтаңыз, {% csrf_token %} ұмытпаңыз, қолданушы мәтінін экрандаңыз, ORM немесе параметрленген сұрау қолданыңыз, ал қажет жерде кэштеуді қарастырыңыз. Бұл README-дегі «күрделілік» бөліміне де қосымша дәлел болады.

    • Жоба идеясы бұрынғы курстық жобалардан ерекше екеніне сенімдімін.
    • Django қосымшасы бар, кемінде бір модель қолданылады.

    • README.md жазылды: жоба сипаттамасы, ерекшелігі мен күрделілігі, файлдар тізімі, іске қосу жолы.
    • Жобаны көрсететін бейне жазылды.
