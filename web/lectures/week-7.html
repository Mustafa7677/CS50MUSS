    7-апта

    Тестілеу, CI/CD

    Кодымыздың дұрыс жұмыс істейтінін қалай білеміз? Тесттерді жазамыз, оларды өздігінен жүргізетін жүйе (CI/CD, GitHub Actions) құрамыз және Docker арқылы ортаны бірдей етеміз.

    ▶ Түпнұсқа бейнежазба мен материалдар (ағылшынша)
    Бұл апта не туралы

    Алдыңғы апталарда сайт жасауды үйрендік: HTML, CSS, Git, Django, JavaScript, React. Бірақ жазған кодымыздың дұрыс жұмыс істейтінін қалай білеміз? Бүгін біз кодты тексеретін код жазамыз, тесттерді өздігінен іске қосатын жүйе құрамыз (CI/CD, GitHub Actions) және «менде жұмыс істейді, серверде істемейді» дейтін мәселені Docker арқылы жоямыз. Таза Python мысалдарын бетте-ақ «▶» батырмасымен іске қосып көре аласыз; ал Django, Selenium, GitHub Actions және Docker сіздің компьютеріңізде жұмыс істейді.

    Бұл бет сөзбе-сөз аударма емес. Лектор аудиторияда қалай түсіндірсе, біз де солай баяндаймыз: мағынасы мен кодтың бәрі түпнұсқадағыдай, тек әңгіме ана тілімізде жүреді.

    Кіріспе

    Қысқаша қайталап өтейік. Біз HTML мен CSS арқылы қарапайым веб-беттер жасауды үйрендік. Git пен GitHub арқылы кодтағы өзгерістерді қадағалап, басқалармен бірге жұмыс істеуді білдік. Python-мен танысып, Django арқылы веб-қосымшалар жаздық, Django модельдерінде мәліметті сақтадық. Сосын JavaScript-ті қосып, беттерді интерактивті еттік, анимация мен React арқылы интерфейсті одан сайын жақсарттық.

    Бүгін біз сәл басқа сұраққа жауап іздейміз: үлкен жобамен жұмыс істегенде және оны жұртқа шығарғанда қандай әдістер көмектеседі? Шағын үй тапсырмасын «жүгіріп тұр ма, жоқ па» деп қолмен тексеруге болады. Ал он адам жұмыс істейтін, мыңдаған жолы бар жобада мұндай әдіс істемейді.

    Тестілеу

    Бағдарламалық жасақтама жасау процесінің маңызды бөлігі - жазған кодымыздың біз күткендей жұмыс істейтініне көз жеткізу. Мұны тестілеу (testing) дейді. Үйдің құрылысын елестетіңіз: кірпішті қалап, соңында «құлап қалмас па екен» деп күтпейміз ғой, әр кезеңде тексеріп отырамыз. Код та сондай.

    Бүгін кодты тексеру жолдарын қарапайымынан бастап, барған сайын күрделілеуіне қарай қарастырамыз: алдымен Python-ның өзінде, сосын Django-да, сосын браузердегі интерфейсте.

    Assert

    Python-да тест жүргізудің ең қарапайым жолдарының бірі - assert командасы. Оның соңынан бір өрнек жазамыз, ол True болуы тиіс. Егер өрнек True болса, ештеңе болмайды, бағдарлама үнсіз жалғаса береді. Ал False болса, ерекше жағдай (exception) көтеріледі. Яғни assert интерпретаторға: «Мен мынаның ақиқат екеніне сенімдімін. Олай болмай шықса, дереу айқайла» дейді.

    Python-ды алғаш үйренгенде жазған square функциямызға қолданып көрейік. Функция дұрыс жазылғанда assert ақиқат, сондықтан ештеңе болмайды (батырманы басыңыз, шығыс бос болады):

    def square(x):
    return x * x

assert square(10) == 100

"""

    def square(x):

    Test-Driven Development (Тест арқылы әзірлеу)

    Жобаңыз үлкейген сайын мына тәсілді қолданғаныңыз жөн: тест арқылы әзірлеу (test-driven development). Мұнда әдіс қарапайым: әр қатені түзеткен сайын сол қатені ұстайтын тест қосасыз, ал тесттер жиыны кодты өзгерткен сайын қайта-қайта іске қосылады. Нәтижесінде жаңа мүмкіндік қосқанда ескі мүмкіндіктердің бұзылмағанына сенімді боласыз. Бұл бір рет жиналған қателер «ескі қателер кітапшасы» сияқты: сол қателерге екінші рет түспейміз.

    Енді сәл күрделірек функцияны алып, тесттер қатені табуға қалай көмектесетінін көрейік. is_prime деген функция жазамыз: ол сан жай болса ғана True қайтарады. Бұл функция prime.py файлында тұрсын:

    import math

def is_prime(n):

    # We know numbers less than 2 are not prime
    if n < 2:
        return False

    # Checking factors up to sqrt(n)
    for i in range(2, int(math.sqrt(n))):

        # If i is a factor, return false
        if n % i == 0:
            return False

    # If no factors were found, return true
    return True

    Ал мынау - осы функцияны тексеру үшін жазған функциямыз. Ол prime.py файлынан is_prime-ды әкеліп, нәтижесі күткенге сәйкес келмесе, қате туралы хабар шығарады:

    from prime import is_prime

def test_prime(n, expected):
    if is_prime(n) != expected:
        print(f"ERROR on is_prime({n}), expected {expected}")

    Енді Python интерпретаторына кіріп, бірнеше мәнді сынап көрейік:

    >>> test_prime(5, True)
>>> test_prime(10, False)
>>> test_prime(25, False)
ERROR on is_prime(25), expected False

    Көріп тұрғанымыздай, 5 жай, 10 жай емес деп дұрыс анықталды. Ал 25 қате түрде жай деп танылды, демек функциямызда бірдеңе дұрыс емес. Бірақ қатенің неде екенін іздеуден бұрын, тестілеуді автоматтандырудың жолын көрейік. Екі файлды бір жерге жинап, браузерде өзіңіз де іске қосып көре аласыз:

    import math

def is_prime(n):
    if n < 2:
        return False
    for i in range(2, int(math.sqrt(n))):
        if n % i == 0:
            return False
    return True

def test_prime(n, expected):
    if is_prime(n) != expected:
        print(f"ERROR on is_prime({n}), expected {expected}")

test_prime(5, True)
test_prime(10, False)
test_prime(25, False)

    2. -c: «команданы орындау» белгісі;
    3. жол түріндегі команданың өзі.
    python3 -c "from tests0 import test_prime; test_prime(1, False)"

    Модульдік тестілеу

    Жоғарыдағы әдіспен тесттерді автоматты түрде жүргізе алдық, бірақ әр тестті жеке жолмен жазу әлі де жалықтырады. Бақытымызға орай, Python-да unittest деген кітапхана бар, ол бұл процесті жеңілдетеді. is_prime функциямыз үшін тест бағдарламасы мынадай көрінеді:

    # Import the unittest library and our function
import unittest
from prime import is_prime

# A class containing all of our tests
class Tests(unittest.TestCase):

    def test_1(self):
        """Check that 1 is not prime."""
        self.assertFalse(is_prime(1))

    def test_2(self):
        """Check that 2 is prime."""
        self.assertTrue(is_prime(2))

    def test_8(self):
        """Check that 8 is not prime."""
        self.assertFalse(is_prime(8))

    def test_11(self):
        """Check that 11 is prime."""
        self.assertTrue(is_prime(11))

    def test_25(self):
        """Check that 25 is not prime."""
        self.assertFalse(is_prime(25))

    def test_28(self):
        """Check that 28 is not prime."""
        self.assertFalse(is_prime(28))


# Run each of the testing functions
if __name__ == "__main__":
    unittest.main()

    Әр функцияның бір заңдылыққа бағынатынын байқадыңыз ба:

    • Функция аты test_ деп басталады. Бұл міндетті: unittest.main() шақырылғанда тесттер дәл осы префикс арқылы автоматты түрде табылады.
    • Әр тест self аргументін алады. Бұл Python-дағы класс ішіндегі әдістер (methods) үшін стандарт.
    • Әр функцияның бірінші жолында үш тырнақшамен жазылған құжаттама жолы (docstring) тұр. Ол тек оқуға ыңғайлы болсын деп жазылмаған: тест құлағанда осы мәтін сипаттама ретінде көрсетіледі.
    • Келесі жолда self.assertSOMETHING түріндегі бекіту бар. Олардың көптеген түрі бар: assertTrue, assertFalse, assertEqual, assertGreater және т.б. Толық тізімін Python құжаттамасынан табасыз.

    Браузерде тесттерді іске қосып көрейік. Бір айырмашылық бар: бізде бөлек файлдар жоқ, сондықтан функция мен тесттерді бір жерге жинап, соңында unittest.main() орнына тесттерді қолмен іске қосатын екі жол жазамыз (компьютеріңізде әдеттегідей unittest.main() жазасыз):

    import math
import unittest

def is_prime(n):
    if n < 2:
        return False
    for i in range(2, int(math.sqrt(n))):
        if n % i == 0:
            return False
    return True

class Tests(unittest.TestCase):

    def test_1(self):
        """Check that 1 is not prime."""
        self.assertFalse(is_prime(1))

    def test_2(self):
        """Check that 2 is prime."""
        self.assertTrue(is_prime(2))

    def test_8(self):
        """Check that 8 is not prime."""
        self.assertFalse(is_prime(8))

    def test_11(self):
        """Check that 11 is prime."""
        self.assertTrue(is_prime(11))

    def test_25(self):
        """Check that 25 is not prime."""
        self.assertFalse(is_prime(25))

    def test_28(self):
        """Check that 28 is not prime."""
        self.assertFalse(is_prime(28))

# Браузерде unittest.main() орнына:
suite = unittest.defaultTestLoader.loadTestsFromTestCase(Tests)
unittest.TextTestRunner(verbosity=1).run(suite)

    Ойланып көріңіз: қатенің себебі неде болуы мүмкін?

    Алдымен болжап көріңіз: 8 мен 25 құлады, ал 11 мен 28 өтті. Не ортақ? 28-ді 2 бірден ұстайды, 11 шынымен жай. Ал 8-дің квадрат түбірі шамамен 2,83, оның бүтін бөлігі 2, сондықтан цикл ешқандай санды тексермейді. 25-тің квадрат түбірі дәл 5, бірақ 5-тің өзі тексерілмейді. Екі жағдайда да мәселе квадрат түбірге дейінгі шекарада. Төменде осыны нақтылаймыз.

    Енді функциядағы қатені түзетейік. Мәселе мынада: біз цикл ішінде тағы бір санды тексеруіміз керек екен. Мысалы, n 25 болса, квадрат түбірі 5. Бірақ 5-ті range функциясына шек ретінде берсек, цикл 4-те тоқтайды (range соңғы шекті қоспайды ғой). Сондықтан 25-тің 5-ке бөлінетінін ешқашан тексермейміз! Шешім қарапайым: for циклінің басын мынаған өзгертеміз:

    for i in range(2, int(math.sqrt(n)) + 1):

    Тесттерімізді қайта жүргізсек, түзетудің жұмыс істегенін көреміз:

    import math
import unittest

def is_prime(n):

        if n % i == 0:

        """Check that 2 is prime."""

suite = unittest.defaultTestLoader.loadTestsFromTestCase(Tests)

Болашақта осы функцияны жылдамдатқыңыз келуі мүмкін: мысалы, барлық бүтін сандарды емес, тек кіші жай сандарды бөлгіш ретінде тексеру (3-ке бөлінбесе, 6-ға, 9-ға, 12-ге де бөлінбейді), немесе одан да күрделі ықтималдық тесттерін қолдану: Ферма мен Миллер-Рабин тесттері. Функцияны жақсартқан сайын тесттерді қайта жүргізіп, оның әлі де дұрыс екеніне көз жеткізе аласыз. Тесттер жоқ болса, «жылдамдатамын деп бұзып алдым ба?» деген күдік жеп қояр еді.

    Қандай мәндерді тексеру керек?

    Selenium

    Осы уақытқа дейін Python мен Django арқылы жазған сервер жағындағы кодты тестіледік. Бірақ қосымшамыз өскен сайын клиент жағындағы кодты да тексергіміз келеді. Қайтадан бір кездегі counter.html бетін еске түсірейік және оған тесттер жазайық.

    <!DOCTYPE html>
<html lang="en">
    <head>
        <title>Counter</title>
        <script>
            
            // Wait for page to load
            document.addEventListener('DOMContentLoaded', () => {

                // Initialize variable to 0
                let counter = 0;

                // If increase button clicked, increase counter and change inner html
                document.querySelector('#increase').onclick = () => {
                    counter ++;
                    document.querySelector('h1').innerHTML = counter;
                }

                // If decrease button clicked, decrease counter and change inner html
                document.querySelector('#decrease').onclick = () => {
                    counter --;
                    document.querySelector('h1').innerHTML = counter;
                }
            })
        </script>
    </head>
    <body>
        <h1>0</h1>
        <button id="increase">+</button>
        <button id="decrease">-</button>
    </body>
</html>

Бірақ бір беттік қосымшалар (single page application) үлкейген сайын мұндай қолмен тексеру өте жалықтырарлық болады. Сондықтан браузердегі тестілеуге көмектесетін бірнеше құрал жасалған. Соның бірі - Selenium.

    Selenium арқылы Python-да тест файлын жазып, пайдаланушының браузерді ашып, бетке өтіп, онымен әрекеттесуін модельдеуге болады. Бұл кезде басты құралымыз - веб-драйвер (Web Driver): ол компьютеріңізде нағыз браузерді ашып, оны кодтан басқарады. Сіз жай ғана оның қасында отырып қарайсыз, ал тышқанды «көрінбейтін қол» басып жатқандай болады.

Selenium-ның жаңа нұсқаларында find_element_by_id("increase") орнына driver.find_element(By.ID, "increase") жазылады (from selenium.webdriver.common.by import By), ал логика сол күйінде қалады.

    CI/CD

    Тесттерді жаздық делік. Бірақ оларды кім іске қосады? Егер әр бағдарламашы «ұмытпай жүргіземін» деп уәде берсе, ерте ме, кеш пе біреу ұмытады. Бұл мәселені командалық жұмыс тәсілдері шешеді. CI/CD - үздіксіз интеграция және үздіксіз жеткізу (Continuous Integration and Continuous Delivery) дегенді білдіретін, бағдарламалық жасақтама әзірлеудің ең жақсы тәжірибелер жиынтығы. Ол екі нәрсені реттейді: кодты адамдар тобы қалай жазады және сол код соңында қолданушыларға қалай жетеді.

    Атынан көрініп тұрғандай, әдіс екі бөліктен тұрады:

    • Үздіксіз интеграция (Continuous Integration):
      • негізгі тармаққа (main branch) жиі біріктіру;
      • әр біріктіруде автоматты модульдік тесттер.
    • Үздіксіз жеткізу (Continuous Delivery):
      • қысқа шығарылым кестесі, яғни қосымшаның жаңа нұсқалары жиі шығарылады.

    Бұл схема кейінірек GitHub Actions бөлімінде нақты конфигурацияға айналады. Ал әзірше, CI/CD командалар арасында неге осыншалық танымал болғанына қарайық:

    • Әртүрлі адамдар әртүрлі мүмкіндіктермен жұмыс істегенде, оларды бір мезетте біріктіргенде үйлесімсіздік мәселелері көп туындайды. Үздіксіз интеграция шағын қайшылықтарды олар пайда болған сайын шешуге мүмкіндік береді.
    • Әр біріктіруде модульдік тесттер жүргізілетіндіктен, тест құлағанда мәселенің қай код бөлігінде екенін оқшаулау жеңіл.
    • Қосымшаның жаңа нұсқаларын жиі шығару іске қосылғаннан кейін туындаған мәселелерді оқшаулауға көмектеседі.
    • Шағын, біртіндеп енгізілетін өзгерістер қолданушыларға жаңа мүмкіндіктерге бірте-бірте үйренуге жағдай жасайды, оларды мүлдем басқа нұсқа қысып тастамайды.
    • Жаңа мүмкіндіктерді күттірмей шығару компанияларға бәсекелі нарықта алда жүруге көмектеседі.
    Ойланып көріңіз: екі апта бойы біріктірмей, жеке тармақта жұмыс істесеңіз не болады?

    Алдымен болжап көріңіз. Екі аптадан кейін сіздің кодыңыз бен басқалардың кодының арасында көптеген өзгеріс жиналады: Git біріктіру қайшылықтарын (merge conflicts) көрсетеді де, сіз бір сәтте жүзден астам жолды қолмен түзетесіз. Ал күн сайын шағын біріктіру жасасаңыз, қайшылықтар да шағын, оларды бірден шешесіз. Үздіксіз интеграция дәл осыны талап етеді: жиі біріктір, әр жолы тест жүргіз.

    GitHub Actions

    Үздіксіз интеграцияға көмектесетін танымал құралдардың бірі - GitHub Actions. Ол бізге жұмыс процестерін (workflows) жасауға мүмкіндік береді: біреу git репозиторийіне код жібергенде (push), белгілі әрекеттер өздігінен орындалады. Мысалы, әр push сайын код стиль нұсқаулығына сай екенін немесе модульдік тесттер жиынынан өтетінін тексертуге болады. Бұл сіздің орныңызға қарап отыратын, ешқашан ұмытпайтын және ешқашан шаршамайтын көмекші сияқты.

    GitHub Action баптау үшін YAML деп аталатын конфигурация тілін қолданамыз. YAML деректерін «кілт: мән» жұптарына құрады (JSON объектісі не Python сөздігі сияқты). Қарапайым YAML файлының мысалы:

    key1: value1
key2: value2
key3:
    - item1
    - item2
    - item3

    Ол Python сөздігіне ұқсайды: key3 кілтінің мәні - үш элементтен тұратын тізім. YAML-де шегініс (бос орындар) мағына береді: бір деңгей ішкі жазба сол кілттің ішінде екенін білдіреді.

    Енді GitHub Actions-пен жұмыс істейтін YAML файлын (аты name.yml не name.yaml болады) қалай баптайтынымызды көрейік. Репозиторийде .github қалтасын, оның ішінде workflows қалтасын, ал оның ішінде ci.yml файлын жасаймыз. Файлға мынаны жазамыз:

    name: Testing
on: push

jobs:
  test_project:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v2
    - name: Run Django unit tests
      run: |
        pip3 install --user django
        python3 manage.py test

    GitHub Actions-ты бірінші рет қолданып жатқандықтан, файлдың әр бөлігі не істейтінін қадам-қадаммен қарастырайық:

    • Алдымен жұмыс процесіне name (аты) береміз, біздің жағдайда ол Testing.
    • Содан кейін on кілтімен жұмыс процесінің қашан іске қосылатынын көрсетеміз. Біз әр push сайын тесттер жүргізілсін дейміз.
    • Файлдың қалған бөлігі jobs кілтінің ішінде. Ол әр push-тан кейін қандай жұмыстар (jobs) орындалатынын көрсетеді.
      • Біздің жағдайда жалғыз жұмыс - test_project. Әр жұмыста екі компонент болуы керек:
        • runs-on кілті кодымыз қай виртуалды машинада (GitHub-тың виртуалды машиналарының бірінде) жүретінін көрсетеді;
        • steps кілті осы жұмыс орындалғанда болатын қадамдарды (әрекеттерді) береді:
          • uses кілтімен қандай GitHub action қолданатынымызды көрсетеміз. actions/checkout@v2 - GitHub жазған дайын action, ол репозиторийдің кодын виртуалды машинаға жүктеп алады;
          • мұндағы name кілті біз жасайтын әрекетті сипаттауға мүмкіндік береді;
          • run кілтінен кейін GitHub серверінде орындалатын командаларды жазамыз. Біздің жағдайда Django-ны орнатып, тест файлын жүргіземіз.

    Енді репозиторийімізді GitHub-та ашып, беттің жоғарғы жағындағы бірнеше қойындыға қарайық:

    • Code: біз ең жиі қолданатын қойынды, директориядағы файлдар мен қалталарды көруге мүмкіндік береді.
    • Issues: мұнда issue-лерді ашып, жабуға болады. Бұл қате түзету не жаңа мүмкіндік қосу туралы өтініштер. Оны қосымшамыздың істер тізімі деп қарауға болады.
    • Pull Requests: бір тармақтағы кодты басқасына біріктіргісі келетін адамдардың сұраулары. Бұл өте пайдалы құрал: код негізгі тармаққа қосылмай тұрып, адамдар код шолуын (code review) жасап, түсініктеме мен ұсыныс қалдыра алады.
    • Actions (GitHub Actions): үздіксіз интеграциямен жұмыс істегенде қолданатын қойындымыз. Әр push-тан кейін орындалған әрекеттердің журналдарын (логтарын) көрсетеді.

    Енді былай елестетейік: біз airport жобасындағы models.py ішіндегі is_valid_flight қатесін түзетуден бұрын өзгерістерімізді push жасап қойдық. GitHub Actions қойындысына барып, соңғы push-ты басып, құлаған action-ды ашып, логты қарай аламыз. Тесттердің қай-қайсысы құлағанын сол жерден көреміз, дәл өз терминалымыздағыдай.

    Қатені түзетіп, қайта push жасасақ, нәтиже жақсарады: жұмыс процесі жасыл белгімен аяқталады. Түпнұсқа лекцияда бұл екі жағдай да гиф-анимациямен көрсетілген: алдымен қызыл крест, ал түзетуден кейін жасыл құсбелгі.

    GitHub Actions GitHub-та орындалады

    Жұмыс процестерін GitHub серверлері іске қосады, сондықтан оны бұл беттің ішінде орындай алмаймыз. Үйде өз репозиторийіңізде .github/workflows/ci.yml жасап, push жасап көріңіз. Апта соңындағы жаттығуда осыған арналған тексеру тізімі бар.

    Docker

    Бағдарламалық жасақтама әлемінде тағы бір мәселе жиі туындайды: сіздің компьютеріңіздің бапталымы қосымша іске қосылатын жердегі бапталымнан өзгеше болады. Сізде Python-ның басқа нұсқасы немесе қосымша пакеттер бар болуы мүмкін, сол себепті қосымша сізде жақсы жұмыс істейді де, серверде құлап қалады. «Менде жұмыс істейді!» дейтін әйгілі сөйлем осыдан шыққан. Мұндай мәселелердің алдын алу үшін жобада жұмыс істейтін әркімнің бірдей ортада жұмыс істеуіне кепілдік беретін жол керек.

    Осының бір жолы - Docker деп аталатын құрал. Docker - контейнерлеу (containerization) бағдарламасы, яғни компьютеріңіздің ішінде бірнеше әріптесіңіз бен сайт іске қосылатын сервер арасында стандарттауға болатын оқшауланған орта жасайды. Ыдыс-аяқ сияқты: ішіне не салсаңыз, қайда апарсаңыз да, сол күйінде қалады.

    Docker виртуалды машинаға (virtual machine) ұқсайды, бірақ олар әртүрлі технологиялар. Виртуалды машина (GitHub Actions-та қолданылатын немесе AWS серверін іске қосқанда пайда болатын) - өз операциялық жүйесі бар тұтас виртуалды компьютер, сондықтан ол тұрған жерде көп орын алады. Ал Docker бар компьютердің ішінде контейнер жасайды, сондықтан орынды аз алады.

    Docker контейнерін компьютерде қалай баптайтынымызды көрейік. Алғашқы қадам - Dockerfile деп аталатын Docker файлын жасау. Оның ішінде Docker образын (Docker image) қалай жасау керектігі жазылады: образ контейнерімізге қандай кітапханалар мен екілік файлдар кіретінін сипаттайды. Образ - тағам рецепті сияқты, ал контейнер - сол рецепт бойынша пісірілген нақты тағам. Біздің Dockerfile мынадай болуы мүмкін:

    FROM python:3
COPY .  /usr/src/app
WORKDIR /usr/src/app
RUN pip install -r requirements.txt
CMD ["python3", "manage.py", "runserver", "0.0.0.0:8000"]

    Жоғарыдағы файл нақты не істейтінін жолма-жол қарастырайық:

    • FROM python:3: бұл образды Python 3 орнатылған стандартты образдың негізінде жасайтынымызды білдіреді. Docker файлын жазғанда бұл өте жиі кездеседі, өйткені әр жаңа образда бір-ақ негізгі бапталымды қайта-қайта жазбай-ақ қоясыз.
    • COPY . /usr/src/app: ағымдағы директориядағы (.) барлығын жаңа контейнердің /usr/src/app директориясына көшіреміз.
    • WORKDIR /usr/src/app: контейнердің ішінде командаларды қай жерде іске қосатынымызды көрсетеді (терминалдағы cd сияқты).
    • RUN pip install -r requirements.txt: барлық қажетті пакеттерді requirements.txt файлына жинаған болсаңыз, олардың бәрі контейнердің ішіне орнатылады.
    • CMD ["python3", "manage.py", "runserver", "0.0.0.0:8000"]: ең соңында контейнер іске қосылғанда орындалатын команданы береміз.

    Осы курста біз әзірге тек SQLite қолданып келдік, себебі ол Django-ның әдепкі дерекқор басқару жүйесі. Бірақ нақты қолданушылары бар жұмыс істеп тұрған қосымшаларда SQLite-ты дерлік қолданбайды, өйткені ол басқа жүйелер сияқты оңай масштабталмайды. Бақытымызға орай, дерекқорға бөлек сервер қажет болса, жай ғана тағы бір Docker контейнерін қосып, оларды Docker Compose деп аталатын мүмкіндікпен бірге іске қоса аламыз. Бұл екі серверді бөлек контейнерлерде жүргізіп, бірақ бір-бірімен сөйлесе алатындай етеді. Мұны көрсету үшін docker-compose.yml деген YAML файлын қолданамыз:

    version: '3'

services:
    db:
        image: postgres

    web:
        build: .
        volumes:
            - .:/usr/src/app
        ports:
            - "8000:8000"

    Жоғарыдағы файлда біз мыналарды істеп жатырмыз:

    • Docker Compose-тың 3-нұсқасын қолданатынымызды көрсетеміз;
    • Екі қызметті (services) сипаттаймыз:
      • db Postgres жазып қойған дайын образ негізінде дерекқор контейнерін жасайды;
      • web сервер контейнерін жасайды және Docker-ға былай дейді:
        • ағымдағы директориядағы Dockerfile-ды қолдан (build: .);
        • контейнердің ішіндегі көрсетілген жолды компьютердегі директориямен байланыстыр (volumes);
        • контейнердің 8000 портын компьютеріміздің 8000 портымен байланыстыр (ports).

    Енді қызметтерімізді docker-compose up командасымен іске қосуға дайынбыз. Бұл екі серверді де жаңа Docker контейнерлерінде жүргізеді.

    Бір сәтте контейнердің ішінде команда орындағымыз келуі мүмкін: дерекқорға жазба қосу не тесттерді жүргізу үшін. Ол үшін алдымен docker ps командасымен жұмыс істеп тұрған барлық контейнерді көреміз. Сосын керекті контейнердің CONTAINER ID мәнін тауып, мынаны орындаймыз:

    $ docker ps
$ docker exec -it CONTAINER_ID bash -l

    Бұл сізді контейнердің ішінде баптаған /usr/src/app директориясына апарады. Енді сол контейнердің ішінде кез келген команданы орындап, шыққанда CTRL-D басасыз.

    Ойланып көріңіз: Docker не үшін виртуалды машинадан жеңіл?

    Алдымен болжап көріңіз. Виртуалды машина әр қосымша үшін толық операциялық жүйені (қонақ ОЖ) жүргізеді, яғни көп жад пен орын қажет. Контейнерлер болса, компьютердің бар операциялық жүйесін бөлісіп қолданады, олардың ішінде тек қосымша мен оған қажет кітапханалар ғана бар. Сондықтан контейнер секундтар ішінде іске қосылады, ал виртуалды машинаны жүктеу минуттарға созылуы мүмкін.

    Docker компьютеріңізде орындалады

    Docker оқшауланған орта жасау үшін операциялық жүйемен жұмыс істейді, сондықтан бұл беттің ішінде іске қосылмайды. Жоғарыдағы файлдарды өз жобаңызда сынап көру үшін Docker Desktop орнату керек.

    Қорытынды

    • assert өрнек False болса AssertionError көтереді: ең қарапайым тест;
    • тест арқылы әзірлеу: әр қатені түзеткенде оны ұстайтын тест қосып, тесттерді әр өзгерістен кейін іске қосу;
    • unittest: TestCase класы, test_ деп басталатын әдістер, assertTrue, assertFalse, assertEqual, құжаттама жолдары, ...F.F шығысы;
    • range(2, int(math.sqrt(n)) + 1): шеткі шекараға (off-by-one) мұқият болу;
    • Django: TestCase, setUp, тестілеуге арналған бөлек дерекқор, python manage.py test;
    • Client арқылы беттердің жауап кодтарын (200, 404) және контекстті тексеру;
    • Selenium: веб-драйвер браузерді басқарып, пайдаланушының әрекетін модельдейді;
    • CI/CD: жиі біріктіру, әр біріктіруде автоматты тесттер, жиі шығарылым;
    • GitHub Actions: .github/workflows/ci.yml файлындағы YAML жұмыс процесі (name, on, jobs, runs-on, steps);
    • Docker: Dockerfile (FROM, COPY, WORKDIR, RUN, CMD), образ бен контейнер, виртуалды машинадан айырмашылығы;
    • Docker Compose: docker-compose.yml арқылы бірнеше контейнерді (db және web) бірге жүргізу.

    Өзіңізді тексеріңіз

    1. assert is_prime(7) жолы орындалғанда is_prime(7) нәтижесі True болды. Не болады?

    assert шарт ақиқат болса үнсіз өтеді, жалған болғанда ғана AssertionError көтереді.

    2. Лекциядағы is_prime функциясында range(2, int(math.sqrt(n))) деп жазылған (соңында + 1 жоқ). Қай тест осы қатені ұстайды?

    25 үшін квадрат түбір 5, бірақ range(2, 5) 5-ті қоспайды, сондықтан 25 жай болып шығады. 11, 1 және 2 үшін қате білінбейді.

    3. Selenium-дағы веб-драйвер (webdriver.Chrome()) не үшін қажет?

    Веб-драйвер браузерді басқарады: бет ашады, driver.title оқиды, click() арқылы түймелерді басады. Сол арқылы клиент жағындағы кодты тексереміз.

    4. unittest шығысы ...F.F болды. Бұл нені білдіреді?

    Нүкте - өткен тест, F - құлаған тест; белгілер тесттер іске қосылған ретімен жазылады. Мұнда алты белгінің төртеуі нүкте, 4-ші және 6-шы белгі - F.

    5. Django TestCase тесттерді жүргізгенде неге нақты дерекқорды бұзып алу қаупі жоқ?

    Django әр тест іске қосылғанда жеке тестілеу дерекқорын жасайды («Creating test database...») және соңында жояды («Destroying test database...»).

    6. Модельде return self.origin != self.destination or self.duration > 0 жазылған. Қай рейс қате түрде «жарамды» (True) болып шығады?

    or болғанда екі шарттың біреуі ақиқат болса жетеді: бірдей аэропорттар жалған, бірақ 200 > 0 ақиқат, нәтиже True. Дұрыс нұсқа and қолданады. AAA → BBB, 100 дұрыстап True болады.

    7. on: push деп жазылған GitHub Actions жұмыс процесі қашан іске қосылады?

    on кілті жұмыс процесінің қашан іске қосылатынын көрсетеді; push болғанда әр push сайын тесттер автоматты түрде жүргізіледі.

    8. Docker контейнері виртуалды машинадан неге жеңіл?

    Виртуалды машина өз операциялық жүйесі бар тұтас виртуалды компьютер. Docker контейнері бар жүйенің ішінде оқшауланған орта жасайды, сондықтан орын аз алады.

    Жаттығу

    Бұл апта үшін ресми problem set жоқ

    CS50 Web-те 7-аптаға жеке тапсырмалар жинағы берілмейді. Сондықтан төмендегі жаттығулар сайттың өз жаттығулары, ресми емес. Оларда сіз лекциядағы идеяны іс жүзінде жаттықтырасыз: is_prime(n) функциясына тесттер жазасыз. Автотексеруші сіздің тестіңізді дұрыс prime.py-мен де, әдейі бұзылған бірнеше нұсқамен де жүргізеді: дұрысында барлығы өтуі, ал әр қате нұсқада кемінде бір тест құлауы керек. Дәл нағыз тест жиынынан күтілетіні осы. Соңғы жаттығуды үйде орындайсыз.

    Оңай

    Testing is_prime with assert (assert арқылы тестілеу)

    prime.py файлында мынадай функция бар (оны тексеруші өзі береді, сіз тек тест файлын жазасыз): is_prime(n) бүтін сан n алып, ол жай сан болса True, әйтпесе False қайтарады.

    test_prime.py файлын жазыңыз. Онда from prime import is_prime болсын, сосын кемінде үш функция жазыңыз. Әр функцияның аты test_ деп басталсын және ішінде кәдімгі assert қолданыңыз:

    from prime import is_prime


def test_small():
    ...
    Кеңес

    Тесттерді топтарға бөліңіз: кіші сандар (1, 2, 3), құрама сандар (4, 8, 9, 25), жай сандар (5, 11, 97). Бір ғана «ыңғайлы» санға сүйенбеңіз: is_prime(5) көптеген қате нұсқадан да өтіп кетеді. Лекциядағы 8 мен 25 неге құлағанын еске түсіріңіз.

    Қалай тексеру керек. Компьютерде pytest test_prime.py немесе жай python арқылы да жүргізуге болады. Бұл жерде тексеруші тесттеріңізді дұрыс және төрт қате нұсқамен жүргізеді: 1 санын жай деп санайтын, 2-ні жай емес деп санайтын, диапазонның соңғы шекарасын қоспайтын (4, 8, 9, 25) және 2-ге бөлінуін тексермейтін нұсқа.

    Тексеру
    • test_prime.py-да кемінде үш test_ функциясы бар, олар assert қолданады.
    • Тесттер 1 мен 2-ні, құрама сандардың квадраттарын (9, 25) және жұп сандарды қамтиды.
    • Дұрыс prime.py-мен барлық тест өтеді, әр қате нұсқада кемінде біреуі құлайды.

    Орташа

    Testing is_prime with unittest (unittest арқылы тестілеу)

    Енді сол функцияны unittest арқылы тестілеңіз. test_prime.py файлында unittest.TestCase-тан мұрагер класс жазыңыз, онда кемінде бес тест әдісі болсын (аттары test_ деп басталсын). Әр тестке лекциядағыдай құжаттама жолын жазыңыз, ал бекіту үшін assertTrue, assertFalse не assertEqual қолданыңыз:

    import unittest
from prime import is_prime


class Tests(unittest.TestCase):

    def test_1(self):
        """1 жай емес."""
        self.assertFalse(is_prime(1))


if __name__ == "__main__":
    unittest.main()
    Кеңес

    Бұл жолы қате нұсқалар қулық жасайды: біреуі тек 0 мен теріс сандарда қателеседі, біреуі тек үлкен құрама сандарда (49, 121, 143) қателеседі. 143 = 11 × 13: оның ең кіші бөлгіші 11. Сондықтан тек кіші сандарға сүйенген жиын жеткіліксіз. Бір әдістің ішінде бірнеше мәнді тексеру үшін for циклін қолдана аласыз; бірақ құлағанда қай мән екенін білу үшін self.assertFalse(is_prime(n), n) деп екінші аргумент беріңіз.

    Қалай тексеру керек. Тексеруші алты қате нұсқа жасайды (алдыңғы төртеу, жоғарыдағы кеңестегі екеуі). Тесттер жиыныңыз соның бәрін ұстауы керек. Жай test_ функциялары бұл жолы есепке кірмейді, тек TestCase әдістері.

    unittest.main() туралы

    Файлдың соңында if __name__ == "__main__": unittest.main() жазсаңыз да, жазбасаңыз да автотексеруші тесттеріңізді өзі іске қосады. Компьютеріңізде python test_prime.py дегенде тесттер лекциядағыдай жүреді.

    Тексеру
    • Класс unittest.TestCase-тан мұрагер, кемінде бес test_ әдісі бар.
    • Тесттер 0 мен теріс сандарды, жай сандардың квадраттарын (49, 121) және екі үлкен жай санның көбейтіндісін (143) қамтиды.
    • Әр тестте құжаттама жолы бар.

    Орташа

    Fix the prime (Жай санды түзету)

    Тест арқылы әзірлеу циклін толық жүріп өтейік: қате → тест → түзету → бәрі жасыл. Төмендегі prime.py бағдарламасында лекциядағы қате бар. main пайдаланушыдан n сұрап, 7 is prime немесе 25 is not prime деп шығарады; is_prime болса мән қайтарады (print тек main-де).

    import math


def main():
    n = int(input("n: "))
    if is_prime(n):
        print(f"{n} is prime")
    else:
        print(f"{n} is not prime")


def is_prime(n):
    if n < 2:
        return False
    for i in range(2, int(math.sqrt(n))):
        if n % i == 0:
            return False
    return True


if __name__ == "__main__":
    main()

    Алдымен жоғарыдағы екі жаттығудағыдай тесттерді жазып, қатені құлату арқылы көріңіз. Сосын қатені түзетіп, тесттердің жасылға айналғанын көріңіз. Түзетілген prime.py-ды төмендегі автотексерушіге қойыңыз.

    Кеңес

    Шекараға қараңыз: range(2, int(math.sqrt(n))) соңғы санды қоспайды. 25 үшін int(math.sqrt(25)) = 5, ал range(2, 5) тек 2, 3, 4 береді. Нені өзгерту керек?

    Қалай тексеру керек. Бағдарлама 7 және 25 үшін дұрыс жолды шығаруы керек, ал is_prime жай сандарға (2, 3, 5, 7, 11, 13, 97) True, құрама сандарға (4, 8, 9, 25, 49, 121) және 0, 1, -7 сандарына False қайтаруы керек.

    Тексеру
    • Қатені тестпен құлатып көрдім (қызыл), сосын түзеттім (жасыл).
    • is_prime мән қайтарады, print тек main-де.
    • Түзетілген қатені ұстайтын тест жиыннан (алдыңғы жаттығу) табылатынын түсіндіре аламын.

    Күрделі

    Your own CI (Өз үздіксіз интеграцияңыз)

    Бұл жаттығуды компьютеріңізде орындайсыз. GitHub Actions, Docker және Django жергілікті жұмыс істейді, сондықтан автотексеруші жоқ, тек тексеру тізімі бар.

    1. GitHub-та жаңа репозиторий жасаңыз және оған prime.py мен test_prime.py файлдарын салыңыз (алдыңғы жаттығулардан).
    2. .github/workflows/ci.yml жасаңыз. Лекциядағы мысал Django үшін жазылған; сіздікі unittest жүргізсін:
    name: Testing
on: push

jobs:
  test_project:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v2
    - name: Run unit tests
      run: |
        python3 -m unittest test_prime
    1. Өзгерістерді push жасаңыз және репозиторийдің Actions қойындысында жұмыс процесінің жасыл болғанын көріңіз.
    2. Енді prime.py-ға әдейі қате енгізіп (мысалы, + 1-ді алып тастап), қайта push жасаңыз. Actions қойындысында қызыл крестті ашып, логтан құлаған тест атын табыңыз.
    3. Қатені түзетіп, қайта push жасаңыз және жасыл нәтижені растаңыз.

    Қосымша: бұрынғы Django жобаңызға (flights) FlightTestCase тесттерін қосып, python manage.py test жүргізіңіз; сосын лекциядағы Dockerfile мен docker-compose.yml файлдарымен жобаны контейнерде іске қосып көріңіз.

    Тексеру
    • .github/workflows/ci.yml бар, on: push және runs-on: ubuntu-latest жазылған.
    • Дұрыс кодпен Actions қойындысында жасыл белгі көрінеді.
    • Әдейі қате енгізгенде процесс қызыл болады, ал логта құлаған тест аты бар.
    • Қосымша: python manage.py test өтеді және docker-compose up жобаны іске қосады.
