    4-апта

    SQL, модельдер, миграциялар

    Деректерді қалай тиімді сақтап, қалай тез тауып аламыз? Алдымен SQL тілінде дерекқормен тікелей сөйлесеміз, сосын Django модельдері арқылы сол жұмысты Python класстарына тапсырамыз.

    ▶ Түпнұсқа бейнежазба мен материалдар (ағылшынша)
    Бұл апта не туралы

    Бұрынғы аптада Django-да беттер жасадық, бірақ деректеріміз кодтың ішінде жатты: тізімдер мен сөздіктер. Нағыз сайттың деректері (қолданушылар, рейстер, тапсырыстар) дерекқорда сақталады. Бүгін SQL-дің негізін үйреніп, сосын Django-ның модель жүйесімен SQL жазбай-ақ дерекқормен жұмыс істеуді көреміз. Лекциядағы SQL мысалдарының көбін осы бетте-ақ «▶ Іске қосу» батырмасымен орындай аласыз.

    Бұл бет сөзбе-сөз аударма емес. Лектор аудиторияда қалай түсіндірсе, біз де солай баяндаймыз: мағынасы мен кодтың бәрі түпнұсқадағыдай, тек әңгіме ана тілімізде жүреді. Түпнұсқада ұшақ рейстері Нью-Йорк, Лондон секілді қалалармен берілген; біз оларды Қазақстан әуежайларына ауыстырдық.

    Кіріспе

    Қысқаша еске түсірейік. Біз HTML мен CSS арқылы қарапайым беттер жасауды үйрендік, өзгерістерді қадағалау және бірге жұмыс істеу үшін Git пен GitHub-ты білдік, Python тілімен таныстық және Django арқылы алғашқы веб-қосымшаларымызды жасадық. Бүгін келесі үлкен қадам: деректерді тиімді сақтау және алу. Ол үшін SQL тілін және Django модельдерін қарастырамыз.

    SQL

    SQL (Structured Query Language, құрылымдық сұраныстар тілі) - дерекқорларды жаңартуға және сұрауға арналған бағдарламалау тілі. Атауындағы «сұрау» (query) сөзі маңызды: біз дерекқорға «маған мынандай деректерді көрсет» деп сұрақ қоямыз, ол жауап қайтарады.

    Дерекқорлар

    SQL-ді қалай қолданатынымызды көрмес бұрын, деректеріміз қайда жататынын түсінейік. SQL-мен жұмыс істегенде біз реляциялық деректер базасымен (relational database) істейміз. Онда барлық деректер бірнеше кестеде (table) сақталады. Әр кестенің бағандары (column) саны бекітілген, ал жолдары (row) саны икемді: қанша қаласаңыз, сонша қоса беруге болады. Excel кестесін елестетіңіз: бағандар - тақырыптар, жолдар - жазбалар.

    SQL-ді көрсету үшін авиакомпания сайтының мысалын аламыз: ол рейстер мен жолаушыларды есепке алады. Бірінші кестеде бірнеше рейс бар, әр рейстің origin (қайдан ұшады), destination (қайда барады) және duration (ұзақтығы, минутпен) деген бағандары бар. Түпнұсқада Нью-Йорк пен Лондон тұр, ал біз Астана мен Париж сияқты қалаларды қолданамыз.

    Деректерді сақтайтын және SQL командаларымен оңай жұмыс істейтін бірнеше деректер базасын басқару жүйесі (relational database management system) бар:

    • MySQL
    • PostgreSQL
    • SQLite
    • және басқалары...

    Алғашқы екеуі, MySQL мен PostgreSQL, «ауыр» жүйелер: әдетте сайттың өзі жұмыс істейтін серверден бөлек, өз серверінде тұрады. Ал SQLite жеңіл: барлық деректерін бір ғана файлда сақтай алады. Біз бұл курста SQLite-ты қолданамыз, өйткені Django оны әдепкі бойынша пайдаланады. Бетіміздегі «Іске қосу» батырмалары да нағыз SQLite-ты браузеріңіздің ішінде жүргізеді.

    Баған типтері

    Python-да айнымалылардың түрлі типтері болатыны есіңізде шығар: int, str, float. SQLite-та да ақпараттың түрлі формаларына арналған типтер бар. Басқа жүйелерде атаулары өзгеше болуы мүмкін, бірақ бәрі өте ұқсас:

    • TEXT: мәтін жолдары үшін (мысалы, адамның аты);
    • NUMERIC: жалпырақ сандық деректер (мысалы, күні немесе логикалық мән);
    • INTEGER: ондық бөлшегі жоқ кез келген сан (мысалы, адамның жасы);
    • REAL: кез келген нақты сан (мысалы, адамның салмағы);
    • BLOB (Binary Large Object): дерекқорда сақтағымыз келетін кез келген басқа екілік деректер (мысалы, сурет).

    Кестелер

    Енді SQL арқылы дерекқормен шынымен жұмыс істеуді бастайық, ал бастау үшін жаңа кесте жасаймыз. Кесте жасау командасы мынадай болады:

    CREATE TABLE flights(
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    origin TEXT NOT NULL,
    destination TEXT NOT NULL,
    duration INTEGER NOT NULL
);

    Мұнда біз flights деп атаған жаңа кесте жасап, оған төрт баған қостық. Әрқайсысын жеке қарайық:

    1. id: кестедегі әр жолды бір мәнді түрде айыратын сан болғаны өте ыңғайлы. Мұнда біз id бүтін сан екенін, және ол біздің бастапқы кілтіміз (primary key) екенін, яғни бірегей идентификатор екенін көрсеттік. Сонымен қатар AUTOINCREMENT деп жаздық: жол қосқан сайын id-ні өзіміз жазбаймыз, ол автоматты түрде 1, 2, 3 болып өсе береді. Мектеп журналындағы реттік нөмір сияқты.
    2. origin: мәтіндік өріс. NOT NULL деп жазу арқылы оның міндетті түрде мәні болуын талап еттік.
    3. destination: тағы мәтіндік өріс және ол да бос болмайды.
    4. duration: бұл да бос бола алмайды, бірақ бұл жолы мәтін емес, бүтін сан.

    Жаңа ғана NOT NULL мен PRIMARY KEY шектеулерін (constraint) көрдік. Бірақ басқа шектеулер де бар:

    • CHECK: жол қосылмай немесе өзгертілмей тұрып, белгілі шарттардың орындалуын тексереді;
    • DEFAULT: мән берілмесе, әдепкі мәнді қояды;
    • NOT NULL: мәннің міндетті түрде берілуін талап етеді;
    • PRIMARY KEY: бұл баған жолды іздеудің негізгі жолы екенін көрсетеді;
    • UNIQUE: бұл бағандағы мән ешбір екі жолда қайталанбауын қамтамасыз етеді;
    • және басқалары...

    Кесте жасауды білдік, ендігі сұрақ: оған жолдарды қалай қосамыз? SQL-де ол үшін INSERT командасы бар:

    INSERT INTO flights
    (origin, destination, duration)
    VALUES ("Астана", "Лондон", 415);
SELECT * FROM flights;
    Түпнұсқадан бір ескерту

    Түпнұсқада тек INSERT жазылған. Біз бұл демо дерекқорда кесте дайын тұрғандықтан, нәтижені көру үшін соңына SELECT * FROM flights; қостық. Батырманы басқан сайт дерекқор жаңадан жасалады, сондықтан өзгерістер сақталмайды: өздігінше тәжірибе жасай беріңіз.

    Бұл командада алдымен қай кестеге қосатынымызды жаздық, сосын қандай бағандарды толтыратынымызды тізіп шықтық, содан кейін VALUES сөзінен соң сол жолдың мәндерін бердік. Мәндердің реті бағандар тізімінің ретімен бірдей болуы керек. id-ге мән бермедік, себебі ол өздігінен өседі.

    SELECT

    Кесте толған соң, біз ондағы деректерге қол жеткізгіміз келеді. Ол үшін SQL-дің SELECT сұрауы қолданылады. flights кестесіне жасалатын ең қарапайым сұрау мынадай:

    SELECT * FROM flights;

    Жұлдызша * «барлығын» білдіреді: бұл команда flights кестесіндегі барлық деректерді қайтарады. Ал көбіне бізге барлық бағандар керек емес, мысалы тек origin мен destination керек шығар. Онда жұлдызшаның орнына керекті бағандардың атын жазамыз:

    SELECT origin, destination FROM flights;

    Кестелер үлкейген сайын қайтарылатын жолдарды да тарылтқымыз келеді. Ол үшін WHERE сөзін және артынан шартты қосамыз. Мысалы, келесі команда тек id-і 3 болатын жолды таңдайды:

    SELECT * FROM flights WHERE id = 3;

    Тек id бойынша емес, кез келген баған бойынша сүзуге болады:

    SELECT * FROM flights WHERE origin = "Астана";

    Терминалда SQL-мен жұмыс

    Қарапайым командаларды білдік, енді оларды терминалда сынап көрейік. Өз компьютеріңізде SQLite-пен жұмыс істеу үшін алдымен оны жүктеп алу керек (түпнұсқада sqlite.org мен DB Browser аталады; DB Browser - SQL сұрауларын орындаудың ыңғайлырақ, графикалық жолы). Лекцияда ол қолданылмады.

    Дерекқорымыздың файлын қолмен жасауға болады, не терминалда touch flights.sql деп жаза аламыз. Сосын sqlite3 flights.sql деп жазсақ, SQLite шақыруына (prompt) түсеміз, онда SQL командаларын жүргізе аламыз. Төменде лектордың сеансы (комментарийлерді аудардық):

    # SQLite шақыруына кіру
(base) % sqlite3 flights.sql
SQLite version 3.26.0 2018-12-01 12:34:55
Enter ".help" for usage hints.

# Жаңа кесте жасау
sqlite> CREATE TABLE flights(
   ...>     id INTEGER PRIMARY KEY AUTOINCREMENT,
   ...>     origin TEXT NOT NULL,
   ...>     destination TEXT NOT NULL,
   ...>     duration INTEGER NOT NULL
   ...> );

# Қазіргі барлық кестені көрсету (әзірге тек flights)
sqlite> .tables
flights

# flights ішіндегінің бәрін сұрау (қазір ол бос)
sqlite> SELECT * FROM flights;

# Бір рейс қосу
sqlite> INSERT INTO flights
   ...>     (origin, destination, duration)
   ...>     VALUES ("New York", "London", 415);

# Жаңа ақпаратты тексеру: енді көрінеді
sqlite> SELECT * FROM flights;
1|New York|London|415

# Тағы бірнеше рейс қосу
sqlite> INSERT INTO flights (origin, destination, duration) VALUES ("Shanghai", "Paris", 760);
sqlite> INSERT INTO flights (origin, destination, duration) VALUES ("Istanbul", "Tokyo", 700);
sqlite> INSERT INTO flights (origin, destination, duration) VALUES ("New York", "Paris", 435);
sqlite> INSERT INTO flights (origin, destination, duration) VALUES ("Moscow", "Paris", 245);
sqlite> INSERT INTO flights (origin, destination, duration) VALUES ("Lima", "New York", 455);

# Жаңа ақпаратты сұрау
sqlite> SELECT * FROM flights;

2|Shanghai|Paris|760
3|Istanbul|Tokyo|700
4|New York|Paris|435
5|Moscow|Paris|245
6|Lima|New York|455

# Шығысты оқуға ыңғайлы ету үшін баптауды өзгерту
sqlite> .mode columns
sqlite> .headers yes

# Барлық ақпаратты қайта сұрау
sqlite> SELECT * FROM flights;

----------  ----------  -----------  ----------
1           New York    London       415
2           Shanghai    Paris        760
3           Istanbul    Tokyo        700
4           New York    Paris        435
5           Moscow      Paris        245
6           Lima        New York     455

# Тек New York-тан ұшатын рейстерді іздеу
sqlite> SELECT * FROM flights WHERE origin = "New York";
id          origin      destination  duration
----------  ----------  -----------  ----------
1           New York    London       415
4           New York    Paris        435

    Назар аударыңыз: .tables, .mode, .headers сияқты нүктемен басталатын командалар - SQL емес, SQLite бағдарламасының өз командалары. Сондықтан бұл блокты бетте іске қосу мүмкін емес. Ал біз сайттағы демо дерекқорда сол сұрауларды орындай беруге болады (рейстер сәл өзгеше, Қазақстан әуежайларымен).

    Тек теңдікпен шектелудің қажеті жоқ. Бүтін не нақты сандар үшін «үлкен» және «кіші» салыстыруларын қолдана аламыз:

    SELECT * FROM flights WHERE duration > 500;

    Python-дағыдай логикалық операторларды да (AND, OR) қолдана аламыз:

    SELECT * FROM flights WHERE duration > 500 AND destination = "Париж";
    SELECT * FROM flights WHERE duration > 500 OR destination = "Париж";
    Ойланып көріңіз: AND мен OR нәтижесі неге осыншалық өзгеше?

    Бірінші сұрауда екі шарт та бірдей орындалуы керек: ұзақтығы 500-ден асады және Парижге ұшады. Екіншісінде кем дегенде біреуі жеткілікті. Сондықтан OR әрқашан AND-тен көп (немесе тең) жол қайтарады. Мектептегі жиынтар сияқты: AND - қиылысу, OR - бірігу.

    Бірнеше нұсқаның бірін іздегіміз келсе, IN кілт сөзін қолданамыз:

    SELECT * FROM flights WHERE origin IN ("Астана", "Атырау");

    Сөздерді кеңірек іздеу үшін (түпнұсқада «тұрақты өрнектер» деп аталады, бірақ шын мәнінде қарапайым үлгі) LIKE бар. Төмендегі сұрау origin бағанында а әрпі бар барлық рейсті табады. Мұнда % - «кез келген таңбалар» дегенді білдіретін ұқсастық белгісі (wildcard):

    SELECT * FROM flights WHERE origin LIKE "%а%";
    Назар аударыңыз

    SQLite-тың LIKE операторы латын әріптерінде бас-кіші әріпті ажыратпайды, ал кириллицада ажыратады. Сондықтан %а% «Астана» сөзіндегі кіші а-ны табады, ал «Шымкент» табылмайды (онда а жоқ). Басқа регистрді де тапқыңыз келсе, %а% мен %А% екеуін де жазыңыз.

    Функциялар

    Сұрау нәтижесіне қолдануға болатын бірнеше SQL функциясы бар. Олар сұрау қайтарған барлық деректің керегі жоқ, тек қорытынды статистика (орташа, сан, ең үлкен) жеткілікті болғанда ыңғайлы:

    • AVG: орташа мән (түпнұсқада «AVERAGE» деп жазылған, бірақ SQL-де функция AVG деп аталады);
    • COUNT: жол саны;
    • MAX: ең үлкен мән;
    • MIN: ең кіші мән;
    • SUM: қосынды;
    • және басқалары...

    Түпнұсқада бұлардың мысалы жоқ, сондықтан өзіміз бір сұрауға бәрін жинап көрсетейік:

    SELECT COUNT(*), AVG(duration), MAX(duration), MIN(duration), SUM(duration)
FROM flights;

    UPDATE

    Кестеге жол қосуды және іздеуді білдік, ал бұрыннан бар жолды өзгерту керек болса ше? Ол үшін UPDATE командасы бар. Дауыстап оқысаңыз, мағынасы өзі түсінікті: команда Астанадан Алматыға ұшатын рейстерді тауып, олардың ұзақтығын 95-ке қояды.

    UPDATE flights
    SET duration = 95
    WHERE origin = "Астана"
    AND destination = "Алматы";
SELECT * FROM flights;

    (Түпнұсқада соңғы SELECT жоқ, өзгерісті көру үшін өзіміз қостық. Түпнұсқада Нью-Йорктен Лондонға дейінгі рейстің ұзақтығы 430 деп өзгертіледі.)

    DELETE

    Кейде жолдарды дерекқордан жою да керек. Ол үшін DELETE командасы бар. Мына код Токиоға қонатын барлық рейсті жояды:

    DELETE FROM flights WHERE destination = "Токио";
SELECT * FROM flights;
    Абай болыңыз

    WHERE-сіз жазылған DELETE FROM flights; кестедегі барлық жолды жояды, ал WHERE-сіз UPDATE барлық жолды өзгертеді. Нағыз дерекқорда мұндай қателік қымбатқа түседі, сондықтан алдымен сол шартты SELECT арқылы тексеріп алған жөн.

    Басқа сөйлемшелер

    Сұраудан қайтатын нәтижені басқаратын тағы бірнеше сөйлемше (clause) бар:

    • LIMIT: сұрау қайтаратын нәтиже санын шектейді;
    • ORDER BY: нәтижені көрсетілген баған бойынша реттейді;
    • GROUP BY: нәтижені көрсетілген баған бойынша топтайды;
    • HAVING: топтардың нәтижесіне қосымша шарт қосуға мүмкіндік береді.

    Бұлардың да мысалы лекцияда жоқ, сондықтан қысқа мысалдар келтірейік:

    SELECT * FROM flights ORDER BY duration DESC LIMIT 3;
    SELECT destination, COUNT(*) FROM flights
GROUP BY destination
HAVING COUNT(*) > 1;

    Екінші сұрау рейстерді баратын қаласы бойынша топтап, санын санайды, сосын тек екіден көп рейс баратын қалаларды қалдырады. Парижге үш рейс бар, сондықтан тек Париж шығады.

    Кестелерді біріктіру

    Осы уақытқа дейін бір мезгілде тек бір кестемен жұмыс істедік. Ал іс жүзінде дерекқорлар бір-бірімен қандай да бір жолмен байланысқан көптеген кестеден тұрады. Ұшақ мысалына оралайық: қаланың жанына әуежай кодын да қосқымыз келеді делік. Кестеміз қазіргідей болса, әр жолға екі баған қосуға тура келеді (шығу және баратын қала кодтары). Үстіне ақпарат қайталанады: «Алматының коды ALA» деген сөзді әр жолда қайта-қайта жазамыз. Базардағы сатушы бәріне бағаны әр жолы қайта жазбай, бір рет бағалар тізімінде жазып қойғаны сияқты, біз де қайталауды азайтқымыз келеді.

    Шешімдердің бірі: рейстерді есепке алатын бір кесте, ал әуежайларды есепке алатын екінші кесте жасау. Екінші кесте мынадай болады:

    SELECT * FROM airports;

    Енді қала атының толық мәтінін рейс кестесінде сақтаудың орнына, әуежайдың id-ін ғана сақтасақ, орынды үнемдейміз. Сондықтан flights кестесін соған сай қайта жазамыз. origin_id мен destination_id мәндері airports кестесінің id бағанынан алынатындықтан, оларды сыртқы кілттер (foreign key) деп атаймыз. Яғни бастапқы кілт - өз кестесінің жолын айыратын сан, ал сыртқы кілт - басқа кестенің жолына сілтеме:

    SELECT * FROM flights;

    Авиакомпания жолаушылар туралы да деректерді сақтағысы келуі мүмкін, мысалы, әр жолаушы қай рейске отырады. Реляциялық дерекқордың күшін пайдаланып, тағы бір кесте қосайық: онда аты, тегі және жолаушы отыратын рейске сыртқы кілт болады. Бұл қарапайым нұсқа (passengers: flight_id, first, last):

    SELECT * FROM passengers;

    Бірақ мұны да жақсартуға болады. Бір адам бірнеше рейсте ұша алады ғой: біздің кестеде Айдар Сейітов екі рейсте тұр, және оның аты-жөні екі рет қайталанды. Сондықтан адамдарды сақтайтын people кестесін (аты, тегі) және адамдарды рейстермен жұптайтын passengers кестесін жасаймыз:

    SELECT * FROM people;
    SELECT * FROM passengers;

    Төмендегі сұлбада төрт кестенің қалай байланысқаны көрсетілген. Көрсеткі «осы баған сол кестенің id-іне сілтейді» дегенді білдіреді:

    Бұл жағдайда бір адам көп рейсте ұша алады, ал бір рейсте көп адам болады. Мұндай байланысты көп-көпке (many-to-many) қатынасы дейді. Екі кестені (flights пен people) байланыстыратын passengers кестесі ассоциация кестесі (association table) деп аталады. Ол өзінде адамның да, рейстің де ақпаратын сақтамайды: тек «мына адам мына рейсте» деген жұптарды сақтайды. Мектептегі мысал: оқушылар мен үйірмелер. Бір оқушы бірнеше үйірмеге барады, бір үйірмеде көп оқушы бар, ал үйірмеге жазылу журналы - ассоциация кестесі.

    JOIN сұрауы

    Деректеріміз енді тиімдірек сақталды, бірақ оларды сұрау қиындап кеткен сияқты: ақпарат бірнеше кестеге таралып кетті ғой. Бақытымызға, SQL-де бір сұрау үшін екі кестені қосатын JOIN сұрауы бар.

    Мысалы, әр жолаушының бару жолындағы шығу қаласын, баратын қаласын және есімін табайық. Қарапайымдылық үшін flight_id, first, last бар «оңтайландырылмаған» passengers кестесін аламыз. Сұраудың алғашқы бөлігі таныс көрінеді:

    SELECT first, origin, destination
FROM ...

    Бірақ мұнда мәселе туады: first passengers кестесінде, ал origin мен destination flights кестесінде тұр. Мұны екі кестені біріктіру арқылы шешеміз: passengers кестесіндегі flight_id мәні flights кестесіндегі id-ге сәйкес келеді дегенді ON сөзінен кейін айтамыз:

    SELECT first, origin, destination
FROM flights JOIN passengers
ON passengers.flight_id = flights.id;

    Нәтижеге қараңыз: әр жолаушының жанында оның рейсі тұр. Назар аударсаңыз, Шымкенттен Токиоға ұшатын 3-рейс тізімде жоқ, өйткені оған ешкім отырмаған. Біз қолданған - INNER JOIN (ішкі біріктіру): ол екі кестенің арасында сәйкестігі жоқ жолдарды елемейді. LEFT JOIN, RIGHT JOIN, FULL OUTER JOIN сияқты басқа түрлері де бар, лекцияда оларды егжей-тегжейлі талқыламайды. Дегенмен салыстыру үшін LEFT JOIN-ды көріп қояйық, ол сол жақтағы кестенің барлық жолын сақтайды:

    SELECT first, origin, destination
FROM flights LEFT JOIN passengers
ON passengers.flight_id = flights.id;

    Енді 3-рейс бар, тек first бағанында NULL (мән жоқ). Ал егер толық, «қалыпқа келтірілген» кестелерімізбен жұмыс істесек, қалалардың атын алу үшін airports-ты екі рет біріктіруге тура келеді (бір рет шығу, бір рет баратын қала үшін), ол үшін кестеге қосымша ат (alias) береміз:

    SELECT f.id, o.city AS origin, d.city AS destination, f.duration
FROM flights f
JOIN airports o ON o.id = f.origin_id
JOIN airports d ON d.id = f.destination_id;

    Индекстеу

    Үлкен кестелермен жұмыс істегенде сұрауларымызды тиімдірек ету үшін индекс (index) жасауға болады. Бұл оқулықтың соңындағы пәндік көрсеткішке ұқсайды: керек сөзді іздегенде бүкіл кітапты парақтамай, көрсеткіштен бірден бетін табасыз. Мысалы, жолаушыларды көбіне тегі бойынша іздейтінімізді білсек, тегінен id-ге дейінгі индексті мына командамен жасаймыз:

    CREATE INDEX name_index ON passengers (last);

    Индекстің жұмыс істегенін көру үшін SQLite-тан сұрауды қалай орындайтынын сұрауға болады (бұл түпнұсқада жоқ, біздің қосымшамыз). Индекссіз SCAN (бүкіл кестені қарап шығу) шығады, ал индекспен SEARCH ... USING INDEX көрінеді:

    CREATE INDEX name_index ON passengers (last);
EXPLAIN QUERY PLAN
SELECT * FROM passengers WHERE last = "Омаров";

    Біздің кестеде жеті ғана жол бар, сондықтан айырмашылық білінбейді. Бірақ миллиондаған жолда индекс сұрауды жүздеген есе жылдамдатуы мүмкін. Тек индекс орын алады және жаңа жол қосқанда оны да жаңартуға тура келеді, сондықтан оны барлық бағанға жаппай қоймаймыз.

    SQL осалдықтары

    SQL-мен деректерді қалай жұмыс істететінімізді білдік. Енді онымен байланысты негізгі осалдықтарды атап өту маңызды. Алдымен SQL инъекциясы (SQL injection attack).

    SQL инъекциясы - зиянкес қолданушы сайттың қауіпсіздік шараларын айналып өту үшін енгізу өрісіне SQL кодын жазатын шабуыл. Мысалы, бізде қолданушы аттары мен құпиясөздері сақталған кесте және сайттың басты бетінде кіру формасы бар делік. Қолданушыны іздейтін сұрау былай болуы мүмкін:

    SELECT * FROM users
WHERE username = username AND password = password;

    Гарри есімді қолданушы сайтқа кіріп, атына harry, құпиясөзіне 12345 жазса, сұрау былай болады:

    SELECT * FROM users
WHERE username = "harry" AND password = "12345";

    Ал хакер аты ретінде harry" -- деп жазып, құпиясөзді бос қалдырады. SQL-де -- комментарийді білдіреді, яғни одан кейінгінің бәрі елеусіз қалады. Сонда сұрау былай болады:

    SELECT * FROM users
WHERE username = "harry"--" AND password = "12345";

    Сұрауды іске қосып көріңіз: құпиясөзді тексеру комментарийге айналып кеткендіктен, хакер Гарридің құпиясөзін білмей-ақ оның аккаунтына кіре алады! Қорғану үшін мыналарды қолданамыз:

    • Escape-таңбалар (escape characters): SQL енгізілген мәтінді код емес, қарапайым мәтін деп қабылдасын;
    • SQL үстіндегі абстракция қабаты, оның өз escape-реттілігі бар, сондықтан SQL сұрауларын өзіміз жазбаймыз. Дәл осыны Django модельдері бізге береді, оған жақында жетеміз.

    Екінші негізгі осалдық - жарыс жағдайы (race condition). Ол дерекқорға бір мезгілде бірнеше сұрау келгенде туады. Егер олар дұрыс өңделмесе, дерекқор жаңаратын нақты уақыт сәттерінде қателіктер шығады. Мысалы, банкте менің 150 доллар ақшам бар. Мен банк аккаунтыма телефоннан да, ноутбуктан да кіріп, екеуінен де 100 доллар алуға тырысамын. Банк бағдарламашылары жарыс жағдайын дұрыс өңдемесе, 150 доллары бар шоттан 200 доллар ала алып қалуым мүмкін. Мүмкін шешімнің бірі - дерекқорды құлыптау (locking): бір транзакция біткенше басқа әрекетке жол бермеу. Банк мысалында, компьютерде «Ақша алу» бетіне өтсем, банк телефоннан ол бетке өтуге рұқсат етпеуі мүмкін.

    Ойланып көріңіз: екі құрылғыдан 150-ден 100-ден алу не үшін қауіпті?

    Екі сұрау бір мезгілде «шотта қанша бар?» деп сұрайды да, екеуі де «150 бар, 100 алуға болады» деп жауап алады. Содан кейін екеуі де қалдықты 50 деп жазады. Нәтижесінде екі есе алынды, ал шоттан тек 100 шегерілді. Сұрау бірінен кейін бірі жүрсе, екіншісі 50 көріп, бас тартар еді. Құлып дәл осы ретті қамтамасыз етеді.

    Django модельдері

    Енді SQL-дің негізін білдік, Django-ға оралайық. Django модельдері (Django models) - SQL-дің үстіндегі абстракция деңгейі. Олар дерекқормен тікелей SQL сұрауларын емес, Python класстары мен объектілерін қолданып жұмыс істеуге мүмкіндік береді. Яғни INSERT INTO ... деп жазудың орнына, «ұшақ рейсі» деген Python класын сипаттап, сол класстың объектісін жасап, .save() деп жазамыз, ал SQL-ді Django өзі жазады. Бұл бізді жаңа ғана айтылған SQL инъекциясынан да қорғайды.

    Модельдерді қолдануды бастау үшін авиакомпанияға арналған Django жобасын және оның ішінде қолданба жасайық:

    django-admin startproject airline
cd airline
python manage.py startapp flights

    Енді қолданбаны әдеттегідей қосу процесінен өтеміз:

    1. settings.py ішіндегі INSTALLED_APPS тізіміне flights қосамыз;
    2. urls.py ішінде flights үшін жол қосамыз: 
      path("flights/", include("flights.urls")),
    3. flights қолданбасының ішінде urls.py файлын жасап, оны әдеттегі импорттармен және тізімдермен толтырамыз.

    Әдеттегідей нақты жолдар мен views.py жазуға асықпай, алдымен models.py файлында модельдер жасаймыз. Осы файлда қосымшамыз қандай деректерді сақтайтынын сипаттаймыз. Содан кейін Django әр модельдің ақпаратын сақтау үшін қажетті SQL синтаксисін өзі анықтайды. Бір рейстің моделі қандай болатынын қарайық:

    class Flight(models.Model):
    origin = models.CharField(max_length=64)
    destination = models.CharField(max_length=64)
    duration = models.IntegerField()

    Бұл анықтамада не болып жатқанын қарастырайық:

    • Бірінші жолда Django-ның Model класын кеңейтетін (extends, мұраланады) жаңа модель жасаймыз;
    • Төменде origin, destination және duration өрістерін қостық. Алғашқы екеуі CharField, яғни жолдарды сақтайды, ал үшіншісі IntegerField. Бұлар Django-ның көптеген кірістірілген өріс кластарының (built-in Field classes) екеуі ғана;
    • Екі CharField-ке ең үлкен ұзындық 64 деп көрсеттік. Қандай параметрлер бар екенін құжаттамадан қарап білуге болады.

    Сіз SQL-де жазған CREATE TABLE flights(...) командасын еске түсіріңіз: Django дәл соның баламасын осы кластан өзі шығарады. id бағанын жазудың да қажеті жоқ, Django оны автоматты түрде қосады.

    Миграциялар

    Модельді жасадық, бірақ оның ақпаратын сақтайтын дерекқор әлі жоқ. Модельдерден дерекқор жасау үшін жобаның басты қалтасына барып мына команданы жазамыз:

    python manage.py makemigrations

    Бұл команда миграцияларды (migrations) жасайды, яғни біздің модельдерде сипатталғанды сақтай алатындай дерекқорды жасайтын немесе өзгертетін бірнеше Python файлын. Шығыс төмендегідей болады, ал migrations қалтасында жаңа файл пайда болғанын көресіз:

    Migrations for 'flights':
  flights/migrations/0001_initial.py
    - Create model Flight

    Шығыс мәтінінің түпнұсқада суреті бар; оның мазмұны осы: Django «flights қолданбасы үшін 0001_initial.py файлы жасалды, ол Flight моделін жасайды» деп хабарлайды. Келесі қадамда осы миграцияларды дерекқорға қолданамыз:

    python manage.py migrate

    Енді әдепкі миграциялар (Django-ның өз қолданушылар, сессиялар кестелері) біздікімен бірге қолданылғанын көресіз, және жобамыз қалтасында db.sqlite3 деген жаңа файл пайда болды. Міне, SQLite дерекқорымыздың өзі.

    Бұл екі қадамды ажырату өте маңызды: makemigrations тек «қандай өзгеріс қажет» деген жоспарды Python файлы етіп жазады, ал migrate сол жоспарды дерекқорда орындайды.

    Python-нан SQL-ге

    Бұл жерде Flight.objects.all() шын мәнінде SELECT * FROM flights; дегенмен бірдей. Ал f.save() - INSERT. Django-ның осы қосымша қабаты арқылы біз SQL жазбай-ақ, бірақ SQL-дің барлық күшін қолданып жатырмыз.

    Бұл жақсы бастама. Бірақ біз сәл бұрын айтқандай, әр рейске қала атын қайта-қайта жазғымыз келмейді. Сондықтан рейс моделімен қандай да бір жолмен байланысты әуежай моделін жасайық:

    class Airport(models.Model):
    code = models.CharField(max_length=3)
    city = models.CharField(max_length=64)

    def __str__(self):
        return f"{self.city} ({self.code})"

class Flight(models.Model):
    origin = models.ForeignKey(Airport, on_delete=models.CASCADE, related_name="departures")
    destination = models.ForeignKey(Airport, on_delete=models.CASCADE, related_name="arrivals")
    duration = models.IntegerField()

    def __str__(self):
        return f"{self.id}: {self.origin} to {self.destination}"

    Жаңа Airport класындағы барлық нәрсені бұрын көрдік. Ал Flight класындағы origin және destination өрістерінің өзгерісі жаңа:

    • Екі өрісті де сыртқы кілт (ForeignKey) деп көрсеттік, яғни олар басқа объектіге сілтейді;
    • Бірінші аргумент ретінде Airport жазу арқылы бұл өріс қандай объектіге сілтейтінін айтамыз;
    • Келесі аргумент on_delete=models.CASCADE әуежай жойылса не болуы керек екенін айтады. Біздің жағдайда әуежай жойылғанда оған байланысты барлық рейс те жойылады. CASCADE-тен басқа да бірнеше нұсқа бар;
    • related_name береміз: бұл берілген әуежайды шығу немесе баратын орны ретінде алатын барлық рейсті іздеудің жолын ашады.

    Бұл атауды қолдану ыңғайлы: келесі қарапайым мысалда Астана әуежайы объектісінен astana.departures.all() деп, одан ұшатын барлық рейсті табуға болады.

    models.py-дағы әр өзгерістен кейін қайтадан миграция жасап, migrate жасауымыз керек. Назар аударыңыз, Нью-Йорктен Лондонға ұшатын бұрынғы рейсті жоюға тура келуі мүмкін, өйткені ол жаңа құрылымға сәйкес келмейді:

# Migrate

    Көп-көпке қатынастары

    Енді модельдерімізге жолаушыларды қосайық. Бастау үшін жолаушы моделін жасаймыз:

    class Passenger(models.Model):
    first = models.CharField(max_length=64)
    last = models.CharField(max_length=64)
    flights = models.ManyToManyField(Flight, blank=True, related_name="passengers")

    def __str__(self):
        return f"{self.first} {self.last}"
    • Жоғарыда айтқандай, жолаушылардың рейстермен көп-көпке қатынасы бар, оны Django-да ManyToManyField арқылы сипаттаймыз;
    • Бұл өрістің бірінші аргументі - онымен байланысатын объектілер класы;
    • blank=True аргументі жолаушының ешбір рейсі болмауы мүмкін екенін білдіреді;
    • related_name қосамыз, ол жоғарыдағыдай қызмет атқарады: берілген рейстегі барлық жолаушыны табуға мүмкіндік береді.

    Бұл өзгерістерді енгізу үшін тағы да makemigrations пен migrate жасаймыз. Содан кейін Passenger моделін admin.py-да тіркеп, әкімшілік бетінде жолаушылар жасай аламыз. Назар аударыңыз: SQL-де біз ассоциация кестесін өзіміз жасадық, ал Django ManyToManyField көргенде оны өзі жасап береді.

    Жолаушылар қосқан соң, рейс бетіміз рейстегі барлық жолаушыны көрсететіндей жаңартайық. Алдымен views.py-дағы flight көрінісін жолаушылар тізімін контекст ретінде беретін етіп өзгертеміз. Тізімге жоғарыда анықтаған related_name арқылы қол жеткіземіз:

    def flight(request, flight_id):
    flight = Flight.objects.get(id=flight_id)
    passengers = flight.passengers.all()
    return render(request, "flights/flight.html", {
        "flight": flight,
        "passengers": passengers
    })

    Сайтымызға келушілерге рейсті брондау мүмкіндігін де берейік. Ол үшін urls.py ішіне брондау жолын қосамыз:

    path("<int:flight_id>/book", views.book, name="book")

    Енді жолаушыны рейске қосатын book функциясын views.py-ға жазамыз:

    def book(request, flight_id):

    # POST сұрауы болса, жаңа рейс қосамыз
    if request.method == "POST":

        # Рейске қол жеткізу
        flight = Flight.objects.get(pk=flight_id)

        # Жіберілген форма деректерінен жолаушының id-ін табу
        passenger_id = int(request.POST["passenger"])

        # id бойынша жолаушыны табу
        passenger = Passenger.objects.get(pk=passenger_id)

        # Жолаушыны рейске қосу
        passenger.flights.add(flight)

        # Қолданушыны рейс бетіне бағыттау
        return HttpResponseRedirect(reverse("flight", args=(flight.id,)))

    Келесі қадам: рейс шаблонына әлі осы рейсте жоқ барлық жолаушыны беру. Ол үшін Django-ның сұраудан белгілі объектілерді exclude (шығарып тастау) мүмкіндігін қолданамыз:

    def flight(request, flight_id):
    flight = Flight.objects.get(id=flight_id)
    passengers = flight.passengers.all()
    non_passengers = Passenger.objects.exclude(flights=flight).all()
    return render(request, "flights/flight.html", {
        "flight": flight,
        "passengers": passengers,
        "non_passengers": non_passengers
    })

    Енді рейс бетінің HTML-ына select енгізу өрісі бар форма қосамыз:

    {% csrf_token %}
    <select name="passenger" id="">
        {% for passenger in non_passengers %}
            <option value="{{ passenger.id }}">{{ passenger }}</option>
        {% endfor %}
    </select>
    <input type="submit">
</form>

    Рейс бетіне кіріп, жолаушыны қосқанда не болатынын қарайық: бетте жолаушылар таңдалатын ашылмалы тізім мен жіберу түймесі тұр; таңдап жібергенде жолаушы «Passengers» тізіміне өтеді де, ашылмалы тізімнен жоғалады (түпнұсқада екі скриншот).

    Django admin-ның тағы бір артықшылығы - оны өзгертуге болады. Мысалы, рейстің барлық аспектісін әкімшілік интерфейсінде көргіміз келсе, admin.py ішінде жаңа класс жазып, оны Flight моделін тіркегенде аргумент ретінде береміз:

    Бүгінгі лекцияда талқылайтын соңғы нәрсе - аутентификация (authentication) идеясы, яғни қолданушыларға сайтқа кіріп-шығуға мүмкіндік беру. Бақытымызға, Django мұны өте оңай етеді; мысал арқылы қарастырайық. users деген жаңа қолданба жасаудан бастаймыз. ]

    # Қажет болатын қосымша импорттар:
from django.contrib.auth import authenticate, login, logout

def login_view(request):
    if request.method == "POST":
        # Форма деректерінен username мен password алу
        username = request.POST["username"]
        password = request.POST["password"]

        # username мен password дұрыс па екенін тексеру, дұрыс болса User объектісін қайтарады
        user = authenticate(request, username=username, password=password)

        # User объектісі қайтса, кіргізіп, басты бетке бағыттау:
        if user:
            login(request, user)
            return HttpResponseRedirect(reverse("index"))
        # Әйтпесе, жаңа контекстпен кіру бетін қайта көрсету
        else:
            return render(request, "users/login.html", {
                "message": "Invalid Credentials"
            })
    return render(request, "users/login.html")

    Қорытынды

    Бүгін біз деректерді сақтау мен басқарудың негізін үйрендік. Негізгілері:

    • SQL және реляциялық дерекқорлар: кестелер, бағандар, жолдар, SQLite және баған типтері (TEXT, INTEGER, REAL, NUMERIC, BLOB);
    • CREATE TABLE мен шектеулер (PRIMARY KEY, NOT NULL, UNIQUE, DEFAULT, CHECK), INSERT;
    • SELECT, WHERE, AND/OR, IN, LIKE, функциялар (COUNT, AVG, MAX, MIN, SUM), UPDATE, DELETE, LIMIT, ORDER BY, GROUP BY, HAVING;
    • бастапқы және сыртқы кілттер, көп-көпке қатынасы мен ассоциация кестесі, JOIN және индекс;
    • SQL инъекциясы мен жарыс жағдайы және олардан қорғану;
    • Django модельдері: models.Model, CharField, IntegerField, ForeignKey (on_delete, related_name), ManyToManyField;
    • миграциялар: makemigrations (жоспар) және migrate (орындау);
    • Django shell: save(), objects.all(), filter, get, exclude, __str__;
    • Django admin: createsuperuser, admin.site.register, ModelAdmin және list_display;
    • аутентификация: authenticate, login, logout, request.user.

    Өзіңізді тексеріңіз

    1. flights кестесінде origin, destination, duration бағандары бар. Қай сұрау ұзақтығы 500-ден асатын рейстердің тек шығу қалаларын қайтарады?

    Қай бағанды алатынымызды SELECT-тен кейін, қай кестеден алатынымызды FROM-нан кейін, ал жолдарды сүзу шартын WHERE-нан кейін жазамыз. Жұлдызша барлық бағанды қайтарар еді.

    2. Мына команда нені жояды?
    DELETE FROM flights;

    WHERE болмаса, команда кестедегі барлық жолға қолданылады. Сондықтан DELETE және UPDATE алдында шартты SELECT арқылы тексерген жөн.

    3. Бір адам көп рейсте ұша алады, бір рейсте көп адам болады. Мұндай байланыс қалай жүзеге асады?

    Көп-көпке қатынасы бір ғана сыртқы кілтпен сипатталмайды: ортада жұптарды сақтайтын ассоциация кестесі керек. Django-да мұны ManyToManyField өзі жасайды.

    4. flights JOIN passengers ON passengers.flight_id = flights.id сұрауында ешқандай жолаушысы жоқ рейс нәтижеде қалай болады?

    INNER JOIN екі жақта да сәйкестігі бар жолдарды ғана қалдырады. Сәйкестіксіз рейсті де көру үшін LEFT JOIN қолдану керек.

    5. Login формасына хакер harry" -- деп жазды. Не себепті ол құпиясөзсіз кіре алады?

    SELECT * FROM users
WHERE username = "harry"--" AND password = "12345";

    Енгізілген мәтін код ретінде қабылданды. Қорғану: escape-таңбалар немесе Django модельдері сияқты абстракция қабаты.

    6. Django-да models.py өзгертілді. Дерекқор жаңаруы үшін қай ретпен команда беру керек?

    makemigrations өзгеріс жоспарын (миграция файлын) жасайды, ал migrate оны дерекқорда орындайды. Біріншісінсіз екіншісінің орындайтыны жоқ.

    7. Flight моделінде origin = models.ForeignKey(Airport, on_delete=models.CASCADE, related_name="departures") бар. astana - Airport объектісі. Астанадан ұшатын рейстерді қалай аламыз?

    related_name кері бағытта іздеудің атын береді: әуежай объектісінен оны шығу орны ретінде алатын рейстерге departures арқылы жетеміз.

    8. Банк шотында 150 бар. Екі құрылғыдан бір мезгілде 100 алуға тырыстық, ал екеуі де сәтті болды. Бұл қандай осалдық және оған қарсы қандай шара бар?

    Екі сұрау бір мезгілде қалдықты оқып, екеуі де «жеткілікті» деп шешті. Бұл жарыс жағдайы. Бір транзакция біткенше екіншісін күттіру (құлып) оны болдырмайды.

    Түсіну

    Таратылатын кодта auctions деген бір ғана қолданбасы бар commerce Django жобасы бар. Алдымен auctions/urls.py ашыңыз: онда қолданбаның URL конфигурациясы жазылған. Біз сізге бірнеше URL-ды дайындап қойдық: әдепкі index жолы, /login, /logout және /register.

    auctions/views.py ішінде осы жолдардың әрқайсысына сәйкес көріністерді қараңыз. index көрінісі әзірге бос дерлік index.html шаблонын қайтарады. login_view қолданушы бетке GET сұрауымен келгенде кіру формасын көрсетеді; форма POST сұрау әдісімен жіберілгенде қолданушы аутентификацияланады, жүйеге кіреді және басты бетке бағытталады. logout_view қолданушыны жүйеден шығарып, басты бетке бағыттайды. Соңында, register жолы тіркелу формасын көрсетеді және форма жіберілгенде жаңа қолданушы жасайды. Мұның бәрі таратылатын кодта дайын, сондықтан қосымшаны қазір-ақ іске қосып, бірнеше қолданушы жасай аласыз.

    python manage.py runserver командасымен Django веб-серверін іске қосып, сайтты браузерде ашыңыз. «Register» басып, аккаунт тіркеңіз. Енді «Signed in as» деп сіздің есіміңіз көрсетіліп, жоғарғы сілтемелер өзгергенін көресіз. HTML қалай өзгерді? Қолданбаның HTML макеті auctions/templates/auctions/layout.html ішінде. Шаблонның бірнеше бөлігі user.is_authenticated тексерісімен қоршалғанына назар аударыңыз: қолданушы кірген-кірмегеніне қарай әртүрлі мазмұн көрсетіледі. Қаласаңыз, бұл файлды өзгертіп, макетке бірдеңе қосуға немесе өзгертуге болады.

    Ақырында, auctions/models.py файлын қараңыз. Веб-қосымшаңыздың кез келген моделін осында анықтайсыз; әр модель дерекқорда сақтағыңыз келетін деректің бір түрін білдіреді. Ол AbstractUser-ден мұралатындықтан, онда қолданушы аты, email, құпиясөз және т.б. өрістер бар; бірақ қолданушы туралы қосымша ақпарат сақтағыңыз келсе, User класына жаңа өрістер қоса аласыз. Сондай-ақ аукцион лоттары, бәстер, пікірлер және аукцион санаттарының мәліметтерін сипаттау үшін осы файлға қосымша модельдер қосуыңыз керек.     • Модельдер (Models): қосымшада User моделінен басқа кемінде үш модель болуы керек: аукцион лоттарына, бәстерге және лоттарға жазылған пікірлерге арналған. Әр модельде қандай өрістер және қандай типтер болатынын өзіңіз шешесіз. Қаласаңыз, қосымша модельдер де қоса аласыз.
    • Лот жасау (Create Listing): қолданушылар жаңа лот жасайтын бетке кіре алуы керек. Олар лоттың атауын, мәтіндік сипаттамасын және бастапқы бәсті көрсете алуы тиіс. Сонымен қатар қолданушылар міндетті емес түрде лоттың суретінің URL-ын және/немесе санатты (мысалы, Fashion, Toys, Electronics, Home және т.б.) бере алуы керек.
    • Ашық лоттар беті (Active Listings Page): веб-қосымшаның әдепкі жолы қазір ашық барлық аукцион лотын көрсетуі керек. Әр ашық лот үшін бұл бет (кемінде) атауын, сипаттамасын, ағымдағы бағасын және суретін (бар болса) көрсетуі тиіс.
    • Лот беті (Listing Page): лотты басқанда қолданушы сол лотқа арналған бетке өтуі керек. Бетте қолданушы лот туралы барлық мәліметті, соның ішінде лоттың ағымдағы бағасын көре алуы керек.
      • Қолданушы жүйеге кірген болса, ол затты өзінің «Watchlist»-іне қоса алуы керек. Зат бақылау тізімінде бұрыннан бар болса, оны алып тастай алуы керек.
      • Қолданушы жүйеге кірген болса, ол затқа бәс сала алуы керек. Бәс кемінде бастапқы бәстей үлкен болуы және басқа салынған бәстердің (болса) бәрінен үлкен болуы тиіс. Бәс бұл шарттарға сәйкес келмесе, қолданушыға қате көрсетілуі керек.
      • Қолданушы жүйеге кірген және лотты өзі жасаған болса, ол осы беттен аукционды «жабу» мүмкіндігіне ие болуы керек: бұл ең жоғары бәс салушыны аукцион жеңімпазы етеді және лотты енді ашық емес етеді.
      • Қолданушы жүйеге кіріп, жабылған лот бетінде тұрса және сол аукционды жеңген болса, бетте солай деп жазылуы керек.
      • Жүйеге кірген қолданушылар лот бетіне пікір қоса алуы керек. Лот беті сол лотқа жазылған барлық пікірді көрсетуі керек.
    • Бақылау тізімі (Watchlist): жүйеге кірген қолданушылар Watchlist бетіне кіре алуы керек; ол бетте қолданушы бақылау тізіміне қосқан барлық лот көрсетілуі тиіс. Осы лоттардың кез келгенін басқанда қолданушы сол лоттың бетіне өтуі керек.
    • Санаттар (Categories): қолданушылар лоттардың барлық санатының тізімі көрсетілетін бетке кіре алуы керек. Кез келген санаттың атын басқанда қолданушы сол санаттағы барлық ашық лот көрсетілетін бетке өтуі керек.
    • Django әкімшілік интерфейсі (Django Admin Interface): Django admin арқылы сайт әкімшісі сайттағы кез келген лотты, пікірді және бәсті көре, қоса, өзгерте және жоя алуы керек.
    Кеңес
    • Django admin интерфейсіне кіре алатын супер-қолданушы жасау үшін python manage.py createsuperuser орындаңыз.
    • Модель өрістерінің мүмкін типтері үшін Django-ның «Model field reference» құжаттамасын қараңыз.
    • Қосымшаның әртүрлі бөліктері үшін Django формаларын (Django forms) жасау керек болуы мүмкін.
    • Кез келген көрініс үстіне @login_required декораторын қойсаңыз, оған тек жүйеге кірген қолданушы кіре алады.
    • CSS-ті қалағаныңызша өзгерте беріңіз, сайтты өзіңіздікі етіңіз. Беттің басында көрсетілген скриншоттар тек мысал: қосымшаңыз олармен бірдей көрінуге міндетті емес (шығармашыл болыңыз!).
    Тапсыру (қысқаша)

    Тапсыру үшін жобаның файл құрылымы таратылған кодпен бірдей болуы керек (қосымша қалта ішінде емес): auctions, commerce қалталары және manage.py. GitHub-тағы web50/projects/2020/x/commerce тармағына жібересіз, не submit50 орнатсаңыз, мына команданы орындайсыз:

    submit50 web50/projects/2020/x/commerce

    Содан кейін 5 минуттан аспайтын скринкаст жазып, YouTube-қа (жариялы не «тізімде жоқ», бірақ жеке емес) жүктейсіз. Бейне басында edX және GitHub пайдаланушы аттарыңыз бар слайд болуы, қосымшаның жұмысын тірідей көрсетуі (кодты түсіндірмеңіз), спецификацияның жеті тармағын да көрсетуі, сипаттамасында әр тармақтың уақыт белгісі болуы керек. Соңында ресми форманы толтырасыз.

    Тексеру
    • User-ден басқа кемінде үш модель бар: лоттар, бәстер, пікірлер; makemigrations және migrate жасалған.
    • Лот жасау беті: атауы, сипаттамасы, бастапқы бәс міндетті; сурет URL-ы мен санат міндетті емес.
    • Басты бет барлық ашық лотты көрсетеді (атауы, сипаттамасы, ағымдағы баға, сурет).
    • Лот беті: бақылау тізіміне қосу/алу, бәс салу (бастапқы бәстен кем емес және басқа бәстерден жоғары, әйтпесе қате), иесі аукционды жабады, жеңімпазға хабар көрсетіледі, пікір жазу және барлық пікірді көрсету.
    • Watchlist беті және Categories беті (санат бойынша ашық лоттар) жұмыс істейді.
    • Django admin-нан лоттарды, бәстер мен пікірлерді көру, қосу, өзгерту және жою мүмкін.
    • Жоба файл құрылымы таратылған кодпен бірдей; submit50 web50/projects/2020/x/commerce жіберілді, скринкаст жазылды.

    Қосымша: сайттың өз SQL жаттығуы

    Бұл - сайттың өз жаттығуы, ресми Commerce тапсырмасы емес. Commerce-тің модельдері дерекқорда қандай кестелерге айналатынын сезіну үшін, төмендегі демо дерекқорға (users, categories, listings, bids, comments, watchlist) SQL сұрауларын жазып көріңіз. Мысалы, ағымдағы баға - бұл жоба үшін де қажет есеп.
