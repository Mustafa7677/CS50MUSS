    5-апта

    Оңтайландыру

    Сұрауды дұрыс жазу аз: оны жылдам жазу керек. Индекс, B-ағаш және EXPLAIN QUERY PLAN арқылы сұрауды жылдамдатып, транзакциялар мен құлыптардың көмегімен көп адам қатынайтын дерекқорды қауіпсіз ұстауды үйренеміз.

    ▶ Түпнұсқа конспект (ағылшынша)
    Бұл апта не туралы

    Осы уақытқа дейін біз SQL-де сұрауды дұрыс жазуды үйрендік. Енді сұрауды жылдам жазуды үйренеміз. Дерекқорда миллиондаған жол болса, дәл сол сұрау бір сәтте де, бір минутта да орындалуы мүмкін, ал айырмасын жасайтын нәрсе - индекс. Сайттағы мысалдарда EXPLAIN QUERY PLAN арқылы SQLite-тың сұрауды қалай орындайтынын өз көзіңізбен көресіз: «▶ Іске қосу» батырмасын басыңыз.

    Бұл бет сөзбе-сөз аударма емес. Лектор аудиторияда қалай түсіндірсе, біз де солай баяндаймыз: мағынасы мен кодтың бәрі түпнұсқадағыдай, тек әңгіме ана тілімізде жүреді.

    Секундомер жоқ, жоспар бар

    Лекцияда Картер .timer on командасын қосып, сұрау қанша уақыт алатынын өлшейді. Браузерде мұндай командасы жоқ, және біз 200 жолдық шағын демо дерекқормен жұмыс істейміз, онда уақыт айырмасы көрінбейді. Сондықтан уақыттың орнына жоспардың өзгеруін қараймыз: SCAN (бәрін қарап шығу) сөзі SEARCH ... USING INDEX (индекспен іздеу) болып өзгерсе, нақты дерекқорда сұрау жылдамдайды деген сөз. Нақты уақытты өлшегіңіз келсе, sqlite3-ті компьютеріңізге орнатып, .timer on деп жазыңыз. Ескерту: sql.js-тың нұсқасына қарай жоспар жолдары сәл өзгеше жазылуы мүмкін (мысалы, SCAN TABLE movies немесе SCAN movies), мағынасы бірдей.

    Кіріспе

    Бүгін біз сұрауларды уақыт бойынша да, орын (дерекқор файлы алатын жад) бойынша да оңтайландыруды үйренеміз. Сонымен қатар, бір мезгілде бірнеше сұрауды қалай қатар орындауға болатынын көреміз. Мұны қатарлас орындау (concurrency) дейді.

    Мұның бәрін жаңа дерекқорда көреміз: Internet Movies Database, яғни көпшілік біліп жүрген IMDb. Біздің SQLite дерекқоры сіз imdb.com сайтынан білетін фильмдердің үлкен онлайн базасынан құралған. Лекцияда көрсетілген статистикаға қарасақ, бұл дерекқор біз осы уақытқа дейін қолданған барлық дерекқорлардан әлдеқайда үлкен: миллиондаған жол бар. Дәл осындай үлкен деректе оңтайландырудың не екені шынымен сезіледі.

    Кестелер арасындағы байланыс ER-диаграммада көрсетілген: адамдар (people), фильмдер (movies) және рейтингтер (ratings). Адам мен фильм арасында «көптен көпке» байланыс бар (бір актер көп фильмде ойнайды, бір фильмде көп актер ойнайды), сондықтан оларды stars деген біріктіруші кесте жалғайды.

    Төмендегі мысалдарда сіз нақты IMDb емес, соның шағын демо үлгісін (200 фильм, 100 адам) іске қосасыз. Кестелердің аттары мен бағандары лекциядағыдай, ал деректер ойдан шығарылған (лекциядағы Tom Hanks және Cars сияқты бірнеше танымал атау ғана қосылған).

    Индекс

    Дерекқорды sqlite3-те ашып, .schema деп жазсақ, кестелердің құрылымы шығады. Байқаңыз: Person мен Movie арасындағы «көптен көпке» байланысты іске асыру үшін stars деген біріктіруші кесте бар, ол people мен movies кестелерінің ID бағандарына сілтейтін шетелдік кілттерден тұрады.

    .schema

    Кестеге көз тастау үшін алғашқы бес жолды алайық:

    SELECT * FROM "movies" LIMIT 5;

    Енді «Cars» фильмі туралы ақпаратты тауып көрейік:

    SELECT * FROM "movies"
WHERE "title" = 'Cars';

    Сұрау қанша уақыт алғанын білгіміз келсе, SQLite-тың .timer on деген командасы бар. Оны қосқаннан кейін сол сұрауды қайта жүргізсек, нәтижемен бірге үш түрлі уақыт көрсеткіші шығады. Бізге керегі - real, яғни секундомермен өлшегендей уақыт: сұрауды іске қосқаннан нәтиже алғанға дейінгі аралық. Лекцияда бұл сұрау шамамен секундтың оннан бірін алды.

    .timer on

    Бұл уақытта сахна сыртында не болды? «Cars» іздегенде SQLite movies кестесін сканерледі (scan): жоғарыдан төменге, жолды-жолдан қарап, атауы «Cars» болатындарын іздеді. Мұны сіз базарда бір затты іздеп, барлық сөрені бастан-аяқ аралап шығуға ұқсатуға болады. Заттың орны белгісіз болса, басқа амал жоқ.

    Бірақ бұдан жақсырақ жол бар. Оқулықтың соңында әрдайым индекс (алфавиттік көрсеткіш) болады ғой: «Абай - 15, 47 беттер». Бүкіл кітапты парақтап шықпай, индекстен тауып, тура сол бетке барасыз. Дерекқор кестелерінде де дәл осындай нәрсе бар. Дерекқор терминологиясында индекс (index) - кестеден жолдарды алуды жылдамдату үшін қолданылатын құрылым.

    Міне, movies кестесінің "title" бағанына индекс құратын команда:

    CREATE INDEX "title_index" ON "movies" ("title");

    Индекс құрылған соң «Cars» сұрауын қайта жүргіздік. Лекцияда ол алғашқыдан шамамен сегіз есе жылдам орындалды! Бірақ осы жерде бір сұрақ туады: біз жай ғана «SQL индексті өзі пайдаланар» деп болжадық қой. Оны қалай көзбен көруге болады? Бұған SQLite-та EXPLAIN QUERY PLAN деген команда бар: оны кез келген сұраудың алдына жазсақ, сұрау орындалмайды, орнына SQLite оны қалай орындауды жоспарлап отырғанын айтады.

    Төмендегі блокты іске қосыңыз. Онда үш қадам бар: индекссіз жоспар, индекс құру, индекспен жоспар. Нәтижеде үш кесте шығады (екеуі жоспар, ортасы бос, себебі CREATE INDEX жол қайтармайды) - жоспарларды салыстырыңыз:

    EXPLAIN QUERY PLAN
SELECT * FROM "movies"
WHERE "title" = 'Cars';

CREATE INDEX "title_index" ON "movies" ("title");

EXPLAIN QUERY PLAN
SELECT * FROM "movies"
WHERE "title" = 'Cars';

    Байқадыңыз ба? Алғашқы жоспар SCAN movies дейді: кестені түгел қарап шығады. Екіншісі SEARCH movies USING INDEX title_index (title=?): индекс бойынша іздейді. Міне, «SCAN» сөзі «SEARCH»-ке айналса, біз жеңдік.

    Индексті алып тастау үшін:

    DROP INDEX "title_index";

    Индексті жойғаннан кейін EXPLAIN QUERY PLAN-ды қайта жүргізсек, жоспар тағы да бүкіл кестені сканерлеуге қайтады. Мұны өзіңіз көріңіз:

    CREATE INDEX "title_index" ON "movies" ("title");
DROP INDEX "title_index";

EXPLAIN QUERY PLAN
SELECT * FROM "movies"
WHERE "title" = 'Cars';
    Ойланып көріңіз: 10 миллион жолы бар кестеде «Cars» атауын индекссіз іздегенде, SQLite ең нашар жағдайда қанша жолды қарайды?

    Ең нашар жағдайда барлық 10 миллион жолды. Атау кестеде реттелмеген, сондықтан SQLite «Cars» дәл қайда жатқанын білмейді, тіпті бірінші табылған жолдан кейін де басқа «Cars» болуы мүмкін (атаулар бірегей деп ешкім кепілдік берген жоқ), сондықтан әдетте соңына дейін барады. Индекспен болса, реттелген тізімде екілік іздеу сияқты бірнеше ондаған қадам жеткілікті. Жол саны 10 есе өссе, сканерлеу 10 есе баяулайды, ал индекспен іздеу тек бір-екі қадамға ғана ұзарады.

    Сұрақтар

    Дерекқорларда іздеуді жылдамдататын өз алгоритмдері жоқ па? Кейбір бағандар үшін бар. SQLite-та да, көптеген басқа дерекқор жүйелерінде де, бағанды бастапқы кілт (primary key) деп жариялайтын болсақ, бастапқы кілт бойынша іздеуге арналған индекс автоматты түрде құрылады. Ал "title" сияқты қарапайым бағандарға ондай автоматты оңтайландыру болмайды.

    Болашақта керек болып қалар деп әр баған үшін бөлек индекс құрып қоя берсек ше? Қарасақ, жақсы идея сияқты, бірақ тегін емес: индекс жадты көп алады, және индекс бар кестеге кейін деректі қосу ұзағырақ уақыт алады. Бұл туралы келесі бөлімдерде толығырақ айтамыз.

    Бірнеше кестедегі индекс

    Енді күрделірек сұрау жазайық: Том Хэнкс ойнаған барлық фильмдерді табу керек. Үш кесте қатысады, сондықтан ішкі сұраулармен жазамыз:

    SELECT "title" FROM "movies"
WHERE "id" IN (
    SELECT "movie_id" FROM "stars"
    WHERE "person_id" = (
        SELECT "id" FROM "people"
        WHERE "name" = 'Tom Hanks'
    )
);

    Қандай индекс бұл сұрауды жылдамдата алады? Мұны болжап отырмай, алдына EXPLAIN QUERY PLAN қойып қарайық. Жоспар сұрауға екі сканерлеу қажет екенін көрсетеді: people және stars кестелері түгел қаралады. Ал movies кестесі сканерленбейді, себебі біз оны id бойынша іздеп отырмыз, ал оған SQLite индексті автоматты түрде құрған (жоспарда SEARCH movies USING INTEGER PRIMARY KEY).

    EXPLAIN QUERY PLAN
SELECT "title" FROM "movies"
WHERE "id" IN (
    SELECT "movie_id" FROM "stars"
    WHERE "person_id" = (
        SELECT "id" FROM "people"
        WHERE "name" = 'Tom Hanks'
    )
);

    Екі сканерлеуді жою үшін екі индекс құрайық: біреуі stars-тағы person_id үшін, екіншісі people-дағы name үшін.

    CREATE INDEX "person_index" ON "stars" ("person_id");
CREATE INDEX "name_index" ON "people" ("name");

    Енді жоспарды қайта қараймыз. Төмендегі блокта индекстерді құру мен жаңа жоспар қатар тұр, іске қосып көріңіз:

    CREATE INDEX "person_index" ON "stars" ("person_id");
CREATE INDEX "name_index" ON "people" ("name");

EXPLAIN QUERY PLAN
SELECT "title" FROM "movies"
WHERE "id" IN (
    SELECT "movie_id" FROM "stars"
    WHERE "person_id" = (
        SELECT "id" FROM "people"
        WHERE "name" = 'Tom Hanks'
    )
);

    Екі жаңалық бар:

    • барлық сканерлеулер енді индекс бойынша іздеуге (SEARCH ... USING INDEX) айналды, бұл керемет;
    • people кестесіндегі іздеу COVERING INDEX деген нәрсені қолданады.

    Жабық индекс (covering index) деген не? Бұл - сұрауға қажетті барлық ақпарат индекстің өзінде бар дегенді білдіреді. Жай индекспен жұмыс екі қадамнан тұрады: 1) индекстен қажетті жазбаны табу, 2) сол сілтеме арқылы кестеге барып, қалған бағандарды алу. Жабық индексте екінші қадам керек емес: бәрін бірінші қадамда-ақ индекстен аламыз. Мұны кітап индексімен салыстырсақ: егер индекстің өзінде сіз іздеген сөздің анықтамасы жазылып тұрса, кітаптың ішіне барудың қажеті жоқ.

    people кестесінде бізге тек id керек, ал іздейтініміз name. id бастапқы кілт болғандықтан, ол индекстің ішінде әрқашан бар, сондықтан name_index өздігінен жабық индекс болды.

    Ал stars кестесіндегі іздеуді де жабық индекске айналдыру үшін индекске "movie_id" бағанын қосу керек. Сонда іздеп отырған мән (person_id) және қайтарылатын мән (movie_id) екеуі де индекстің ішінде болады. Алдымен ескі индексті жоямыз:

    DROP INDEX "person_index";

    Содан кейін жаңасын құрамыз:

    CREATE INDEX "person_index" ON "stars" ("person_id", "movie_id");

    Ал мынаны іске қосыңыз: енді екі жабық индекс көрінуі тиіс, яғни іздеу әлдеқайда жылдам болуы керек:

    CREATE INDEX "person_index" ON "stars" ("person_id");
CREATE INDEX "name_index" ON "people" ("name");
DROP INDEX "person_index";
CREATE INDEX "person_index" ON "stars" ("person_id", "movie_id");

EXPLAIN QUERY PLAN
SELECT "title" FROM "movies" WHERE "id" IN (
    SELECT "movie_id" FROM "stars" WHERE "person_id" = (
        SELECT "id" FROM "people" WHERE "name" = 'Tom Hanks'
    )
);

    Жоспарда stars үшін SEARCH stars USING COVERING INDEX person_index (person_id=?) шықты, ал бұған дейін COVERING сөзі жоқ еді. Лекцияда .timer on қосып тұрып, осы сұрауды (Том Хэнкс ойнаған фильмдерді) қайта орындаған кезде, ол индекссіз нұсқадан бір ретке жылдам болды. Нәтижені бірге көрейік:

    CREATE INDEX "person_index" ON "stars" ("person_id", "movie_id");
CREATE INDEX "name_index" ON "people" ("name");

SELECT "title" FROM "movies"
WHERE "id" IN (
    SELECT "movie_id" FROM "stars"
    WHERE "person_id" = (
        SELECT "id" FROM "people"
        WHERE "name" = 'Tom Hanks'
    )
);
    Ойланып көріңіз: stars кестесіне индексті ("movie_id", "person_id") тәртібімен құрсақ, бұл сұрауға көмектесер ме еді?

    Көмектеспейді. Біз person_id бойынша іздейміз, ал B-ағаш (төменде көреміз) индекстің бірінші бағаны бойынша реттелген. Бірінші баған movie_id болса, SQLite әр фильмнің ішінен адамды іздеуге мәжбүр болады. Телефон анықтамалығын «аты бойынша» реттегенде, тек тегін біліп отырсаңыз, іздеу қиын болатынына ұқсас. Бағандардың реті маңызды: іздейтін баған алда, қосымша қайтарылатын баған соңында тұрады.

    Орынға байланысты айырбас

    Индекстер керемет көрінеді, бірақ тегін ештеңе жоқ. Индекс дерекқордың ішінде қосымша орын алады, яғни сұраудың жылдамдығын ұтып, жадты жоғалтамыз.

    Индекс дерекқорда B-ағаш (B-tree, «balanced tree», яғни теңдестірілген ағаш) деген құрылым түрінде сақталады. Алдымен жай ағаш деген не, соны еске түсірейік. Ағашта көп түйін (node) бар, олар бір-бірімен көрсеткілер арқылы жалғанған. Ағаш басталатын түйінді тамыр (root) дейді; лекциядағы суретте тамырдың үш ұрпақ түйіні (children) бар. Ағаштың шетіндегі, ешқайда сілтемейтін түйіндерді жапырақ (leaf) дейді.

    Енді movies кестесінің "title" бағанына жасалған индекс қалай құралатынын қарайық. Фильм атаулары әліпби бойынша реттеліп тұрса, белгілі бір фильмді екілік іздеу (binary search) арқылы табу әлдеқайда оңай болар еді: ортасына қарап, керек жағын таңдап, қайта жартылай бөле беру. Дәл осы жасалады: "title" бағанының көшірмесі жасалады, ол реттеледі, сосын әр атау түпнұсқа жолға (фильм ID-і арқылы) сілтейді. Төмендегі сызба осыны көрсетеді.

    Бұл сызба индексті түсінуге ыңғайлы, бірақ шындығында индекс бір ұзын баған емес. Деректер көп болса (біздің IMDb сияқты), бір бағанды түгелімен жадқа сыйдыру мүмкін болмауы мүмкін. Сондықтан индекс көптеген түйіндерге бөлінген, әрқайсысында индекстің бір бөлігі ғана бар.

    Бірақ индекстің бөліктері әртүрлі түйіндерде жатса, дұрыс бөлікке апаратын «бағыттаушы» түйіндер де керек болады. Мысалы, төмендегі сызбадағы жоғарғы түйін мынаны айтады: атау «Frozen»-нен бұрын келсе - сол жаққа, «Frozen» мен «Soul» арасында болса - ортаға, «Soul»-дан кейін болса - оң жаққа бар. Бұл дәл жол көрсеткіш тақтайшаға ұқсайды.

    Міне, осы - B-ағаш. SQLite-та индекстер дәл осылай сақталады. Мысалы, «Moana» іздесек: тамырда «Frozen мен Soul арасында» екенін көреміз, ортаңғы жапыраққа барамыз, ішінен тауып аламыз. Миллион атау болса да, бұл бірнеше қадамға ғана сияды, себебі әр қадам іздеу аймағын бірден бірнеше есе қысқартады.

    Уақытқа байланысты айырбас

    Орынмен қатар, уақыт бойынша да айырбас бар. Бағанға индекс жасалған болса, кестеге жаңа мән қосқан сайын оны индекске де қосу керек. Мән индексте қай жерге түсетінін анықтау үшін B-ағаш бойымен тамырдан жапыраққа дейін жүріп өту керек. Яғни іздеу жылдамдайды, ал деректі қосу баяулайды. Индекс көп болған сайын, әр INSERT сайын жаңартылатын ағаш та көп болады.

    Дәл осы себептен «әр бағанға индекс құра салайық» деген ұсынысты орындамаймыз. Индексті тек шынымен жиі қолданылатын іздеулерге құрамыз.

    Ойланып көріңіз: жүйе әр секунд сайын мың рет жаңа жазба қосады, ал іздеу тәулігіне бір рет жасалады. Индекс керек пе?

    Көбіне керек емес. Мұндай жүйеде индекс тек баяулатады: әр мың жазба сайын B-ағаштар жаңартылады, ал оның пайдасын тәулігіне бір-ақ рет көреміз. Индекс іздеу көп, жазу аз кестелерде тиімді. Ереже қарапайым: оңтайландыру алдында дерекқорыңыз көбіне нені істейтінін біліңіз.

    Ішінара индекс

    Орынды үнемдеудің бір жолы бар: ішінара индекс (partial index). Бұл - кестенің барлық жолдарын емес, тек бір бөлігін қамтитын индекс. Толық индекс алатын орынның біразын үнемдейміз.

    Бұл біз пайдаланушылар кестенің тек белгілі бір бөлігін сұрайтынын білетін жағдайда өте ыңғайлы. IMDb мысалында адамдар жаңа ғана шыққан фильмді 15 жыл бұрынғы фильмнен гөрі жиі іздейтіні рас қой. Сондықтан тек 2023 жылы шыққан фильмдердің атауларын сақтайтын ішінара индекс құрып көрейік:

    CREATE INDEX "recents" ON "movies" ("title")
WHERE "year" = 2023;
    Түзету

    Ресми конспектте бағанның аты "titles" деп қате жазылып кеткен (жекеше түрі "title" болуы керек). Біз дұрыс жазылуын қолданамыз.

    Жаңа индекстің қолданылатынын тексерейік. Алдымен жоспар индекссіз, сосын индекспен шығады. Содан кейін 2023 емес жылды іздеп көріңіз: ішінара индекс оған көмектеспейді, себебі индексте басқа жылдардың жолдары жоқ.

    EXPLAIN QUERY PLAN
SELECT "title" FROM "movies"
WHERE "year" = 2023;

CREATE INDEX "recents" ON "movies" ("title")
WHERE "year" = 2023;

EXPLAIN QUERY PLAN
SELECT "title" FROM "movies"
WHERE "year" = 2023;

EXPLAIN QUERY PLAN
SELECT "title" FROM "movies"
WHERE "year" = 1994;

    Екінші жоспар movies кестесі ішінара индекс арқылы сканерленетінін көрсетеді (SCAN movies USING COVERING INDEX recents). Индексте тек 2023 жылғы жолдар болғандықтан, сканерлеу де қысқа. Ал соңғы жоспар (1994 жыл) бұрынғыдай SCAN movies: индекс бұл сұрауға жарамайды.

    Ойланып көріңіз: recents индексі WHERE "year" = 2023 AND "title" = 'Soul' сұрауына көмектеше ме?

    Иә, көмектеседі: сұрау жылды 2023 деп шектейді, яғни бізге керек жолдар міндетті түрде индексте. Ал одан кейін атау бойынша индексте екілік іздеу жасалады. Көмектеспейтіні - жылды көрсетпейтін немесе басқа жылды көрсететін сұрау.

    Сұрақтар

    Индекстер схемада сақтала ма? Иә, SQLite-та сақталады. Тексеру үшін .schema деп жазсақ, құрылған индекстердің барлығы дерекқор схемасында тізімделіп тұрады.

    Вакуум

    Дерекқордағы пайдаланылмай жатқан орынды тазалаудың жолы бар. SQLite деректі «вакуумдауға» (vacuum) мүмкіндік береді. Бұл - бұрын «жойылған» деректі тазалау. «Жойылған» деп тырнақшаға алып отырмыз: шындығында ол жойылмайды, тек «бұл орын бос, келесі INSERT келіп жазып кете берсін» деп белгіленеді. Кітапханада кітапты сөреден алып тастағанда, сөрені бірден қысқартпай, бос орнын қалдыра салуға ұқсайды.

    Дерекқор файлының өлшемін терминалда Unix командасымен білуге болады:

    $ du -b movies.db

    Лекцияда бұл команда дерекқордың өлшемін шамамен 158 миллион байт, яғни 158 мегабайт деп көрсетті. Енді дерекқорға қосылып, бұрын құрған индекстердің бірін жоямыз:

    DROP INDEX "person_index";

    Unix командасын қайта жүргізсек, файл өлшемі кішірейген жоқ. Неге? Себебі индекс «жойылды», бірақ оның орны бос деп белгіленді ғана. Шынымен босатып, файлды кішірейту үшін дерекқорды вакуумдау керек. SQLite-та:

    VACUUM;

    Бұл бір-екі секунд алуы мүмкін. Содан кейін өлшемді қайта тексерсек, файл кішірейгенін көреміз. Барлық индекстерді жойып, тағы вакуумдасақ, дерекқор 158 МБ-тан едәуір аз болады (лекцияда шамамен 100 МБ).

    Браузерде файлды өлшеу командасы жоқ, бірақ SQLite-тың өзі файлдың неше «бетке» (page) бөлінгенін және соның қаншасы бос екенін айтып береді (PRAGMA page_count және PRAGMA freelist_count). Төмендегі блокты іске қосыңыз және кестелерде 1) бастапқы бет саны, 2) индекс құрған соң, 3) жойған соң бос беттер саны, 4) вакуумнан кейінгі бет саны қалай өзгеретінін қараңыз:

    PRAGMA page_count;

CREATE INDEX "person_index" ON "stars" ("person_id", "movie_id");
CREATE INDEX "name_index" ON "people" ("name");
PRAGMA page_count;

DROP INDEX "person_index";
DROP INDEX "name_index";
PRAGMA page_count;
PRAGMA freelist_count;

VACUUM;
PRAGMA page_count;
PRAGMA freelist_count;

    Байқадыңыз ба? Индексті жойған соң page_count азаймады, бірақ freelist_count (бос беттер) өсті. Ал VACUUM-нан кейін бос беттер жоғалып, жалпы бет саны бастапқы шамаға қайта оралды.

    Сұрақтар

    Вакуумды жылдамырақ жасауға бола ма? Әр вакуум әртүрлі уақыт алады. Бұл қанша орынды тазалау керегіне және босатылатын байттарды табудың қаншалықты оңай екеніне байланысты.

    «Жою» сұрауы жолдарды шынымен жоймай, тек белгілесе, оларды қайтарып алуға бола ма? Криминалистика маманы жойылды деп ойлайтын деректі де компьютерден табып алуы мүмкін. Ал SQLite-та VACUUM жасағаннан кейін жойылған жолдарды қайта табу мүмкін емес.

    Қатарлас орындау

    Осы уақытқа дейін біз жеке сұрауларды оңтайландырып келдік. Енді бір сұрауды емес, бір мезгілде бірнеше сұрауды қалай өңдеуге болатынын қараймыз.

    Қатарлас орындау (concurrency) дегеніміз - дерекқордың бірнеше сұрауды немесе әрекетті бір мезгілде өңдеуі. Көп адам кіретін веб-сайттың немесе қаржы қызметінің дерекқорын елестетіңіз. Бір сәтте жүздеген адам оған жазады және одан оқиды. Сондай жағдайларда қатарлас орындау аса маңызды.

    Кейбір дерекқор әрекеттері бірнеше бөліктен тұрады. Банк дерекқорын алайық. Төмендегі accounts кестесінде шоттардағы қалдық сақталады:

    SELECT * FROM "accounts";

    Бір әрекет - бір шоттан екіншісіне ақша аудару. Мысалы, Алиса Бобқа 10 доллар жібергісі келеді. Ол үшін екі нәрсе істеу керек: Бобтың шотына 10 қосу және Алисаның шотынан 10 алу. Біреу дерекқорды бірінші жаңартудан кейін, бірақ екіншісінен бұрын қараса, банктің қолындағы ақшаның жалпы сомасы туралы қате көрініс алады: 10 доллар «ауада ілініп» тұр.

    Транзакциялар

    Сырттан бақылаушыға транзакцияның барлық бөліктері бір мезгілде болып өткендей көрінуі керек. Дерекқор тілінде транзакция (transaction) - бөлшектеуге болмайтын жеке жұмыс бірлігі.

    Транзакциялардың қасиеттерін ACID аббревиатурасымен есте сақтауға болады:

    • атомарлық (atomicity): кішірек бөліктерге бөлінбейді, не толық орындалады, не мүлде орындалмайды;
    • үйлесімділік (consistency): дерекқордың шектеулерін бұзбауы керек;
    • оқшаулау (isolation): дерекқорға бірнеше пайдаланушы қатынаса, олардың транзакциялары бір-біріне кедергі жасамауы керек;
    • беріктік (durability): дерекқорда қандай да бір ақау болса да, транзакциялар өзгерткен деректер сақталып қалуы керек.

    Енді bank.db-ны терминалда ашып, Алисадан Бобқа ақша аудару транзакциясын жазайық. Алдымен accounts кестесіндегі деректі қарадық (жоғарыдағы блок): Бобтың ID-і 2, Алисаныкі 1, сұрауымызға бұл керек болады. Алисадан Бобқа 10 доллар көшіру үшін мынадай транзакция жазамыз:

    BEGIN TRANSACTION;
UPDATE "accounts" SET "balance" = "balance" + 10 WHERE "id" = 2;
UPDATE "accounts" SET "balance" = "balance" - 10 WHERE "id" = 1;
COMMIT;

SELECT * FROM "accounts";

    Назар аударыңыз: екі UPDATE транзакцияны бастайтын және оны бекітетін командалардың арасында тұр. Егер UPDATE-терді жазып, бірақ COMMIT жасамасақ, екеуі де орындалмаған болып қалады. Дәл осы транзакцияны атомарлы етеді: ортаңғы қадамдарды біреу көре алмайды. Мұны өзіңіз көріңіз: транзакция ішінде өзіңіз өзгеріс көресіз, ал ROLLBACK жасасақ, ол жоғалып кетеді (төмендегі блок осыны көрсетеді):

    BEGIN TRANSACTION;
UPDATE "accounts" SET "balance" = "balance" + 10 WHERE "id" = 2;
SELECT * FROM "accounts";
ROLLBACK;
SELECT * FROM "accounts";

    Алғашқы SELECT-те Бобта 30 бар, ал ROLLBACK-тен кейін қайтадан 20.

    Алиса Бобқа тағы 10 доллар жібермек болса, не болады? Бұл транзакция орындалмауы керек, себебі Алисаның қалдығы нөлде. (accounts кестесінің "balance" бағанында теріс емес мән болуын талап ететін CHECK шектеуі бар; оны .schema арқылы көруге болады.) Төмендегі блокта бірінші аударым сәтті өтеді, екіншісі шектеуге соғылып, қате береді:

    UPDATE "accounts" SET "balance" = "balance" + 10 WHERE "id" = 2;
UPDATE "accounts" SET "balance" = "balance" - 10 WHERE "id" = 1;

UPDATE "accounts" SET "balance" = "balance" + 10 WHERE "id" = 2;
UPDATE "accounts" SET "balance" = "balance" - 10 WHERE "id" = 1;

    Қатені көрдіңіз: CHECK constraint failed. Бірақ екінші аударымның бірінші жартысы (Бобқа +10) орындалып қойған болуы мүмкін, және бұл жағдай дәл біз қаламайтын нәрсе. Транзакцияны қайтару үшін ROLLBACK бар. Транзакцияны бастап, бірнеше команда жазғаннан кейін, олардың бірі сәтсіз болса, транзакцияны ROLLBACK арқылы аяқтаймыз, сонда барлық мән транзакцияға дейінгі күйіне қайтады. Мұндай жолмен транзакциялар үйлесімді болып қалады.

    BEGIN TRANSACTION;
UPDATE "accounts" SET "balance" = "balance" + 10 WHERE "id" = 2;
UPDATE "accounts" SET "balance" = "balance" - 10 WHERE "id" = 1; -- Шектеу қатесін шығарады
ROLLBACK;
    Ойланып көріңіз: екі UPDATE-ті транзакциясыз жазсақ, екіншісі қатемен құлағанда банк қандай күйде қалады?

    Бобтың шотына 10 доллар қосылып қойған, ал Алисадан алынбаған болады: банкте ақша жоқтан пайда болды. Транзакция мен ROLLBACK дәл осындай жартылай жағдайдың алдын алады: екі қадамның екеуі де орындалады немесе екеуі де жоққа шығарылады.

    Жарыс жағдайлары

    Транзакциялар жарыс жағдайларынан қорғайды. Жарыс жағдайы (race condition) - бірнеше тарап бір мезгілде ортақ мәнге қатынасып, соның негізінде шешім қабылдағанда пайда болатын жағдай; бұл дерекқорда сәйкессіздікке әкелуі мүмкін. Шешілмеген жарыс жағдайларын хакерлер дерекқорды өз пайдасына өзгерту үшін пайдалана алады.

    Лекцияда мұндай жарыс жағдайының мысалы қарастырылады: бірге әрекет ететін екі пайдаланушы дерекқордағы уақытша сәйкессіздікті пайдаланып, банкті тонай алады. Идеясын былай елестетуге болады: шотта 10 доллар бар делік. Екі құрдас бір мезгілде екі түрлі жерден «10 доллар жібер» деп сұрау жібереді. Екі сұрау да шоттағы қалдықты, яғни 10 долларды көреді, екеуі де «жететін ақша бар екен» деп шешеді, ал сонан соң әрқайсысы 10 доллар жібереді. Нәтижесінде бар болғаны 10 доллары бар шоттан 20 доллар шығып кетті. Мұның бәрі қалдықты тексеру мен оны өзгертудің арасындағы кішкентай үзілісте болады.

    Алайда транзакциялар оқшауланған түрде өңделеді, сондықтан мұндай сәйкессіздіктің өзі пайда болмайды. Бір деректермен жұмыс істейтін транзакциялар біртіндеп, кезекпен өңделеді. Бұл қарсылас шабуылы пайдалана алатын сәйкессіздіктердің алдын алады.

    Транзакцияларды біртіндеп орындату үшін SQLite және басқа дерекқор жүйелері дерекқорда құлыптарды (lock) қолданады. Дерекқор бірнеше күйде болуы мүмкін:

    • UNLOCKED (құлыпсыз): дерекқорға ешкім қатынаспағанда әдепкі күй;
    • SHARED (ортақ): транзакция дерекқордан деректі оқып жатқанда ол ортақ құлып алады, және бұл басқа транзакцияларға да сол мезгілде оқуға мүмкіндік береді;
    • EXCLUSIVE (айрықша): транзакция деректі жазуы немесе жаңартуы керек болса, ол дерекқорда айрықша құлып алады, ал бұл басқа транзакциялардың бір мезгілде орындалуына жол бермейді (тіпті оқуға да).

    Сұрақтар

    Транзакцияның айрықша құлып алуына қашан болатынын қалай шешеміз? Әртүрлі транзакцияларға басымдықты қалай береміз? Бұл үшін әртүрлі алгоритмдер қолдануға болады. Мысалы, әрдайым бірінші келген транзакцияны таңдау. Айрықша транзакция керек болса, сол кезде басқа ешқандай транзакция жүре алмайды; бұл кестенің үйлесімділігін сақтау үшін міндетті кемшілік.

    Құлыптау қаншалықты ұсақ? Біз дерекқорды, кестені немесе кестенің жолын құлыптаймыз ба? Бұл дерекқор жүйесіне байланысты. SQLite-та мұны айрықша транзакция іске қосу арқылы көруге болады:

    BEGIN EXCLUSIVE TRANSACTION;

    Осы транзакцияны аяқтамай, басқа терминалдан дерекқорға қосылып, кестеден оқып көрсек, дерекқор құлыптаулы деген қате шығады. Әрине, бұл құлыптаудың өте дөрекі тәсілі, себебі бүкіл дерекқор құлыпталады. SQLite осындай дөрекі болғандықтан, оның транзакцияларға басымдық беретін және айрықша құлыпты тек ең қысқа қажетті уақытқа ғана алуды қамтамасыз ететін модулі бар.

    Ойланып көріңіз: екі терминалда бір bank.db ашылған. Біріншісі BEGIN EXCLUSIVE TRANSACTION; жазып, тоқтап тұр. Екіншісі SELECT жазса, не болады?

    Екіншісі «database is locked» (дерекқор құлыпталған) деген қате алады: айрықша құлып оқуға да жол бермейді. Біріншісі COMMIT не ROLLBACK жасап, құлыпты босатқанша кезек күту керек.

    Қорытынды бөлім: оңтайландыру жайлы

    Осымен 5-лекция, яғни SQL-ді оңтайландыру, аяқталды. Қазір біз сұрауды тек дұрыс емес, жылдам да жаза аламыз, және бір мезгілде көп адам қатынайтын дерекқорды қауіпсіз ұстай аламыз.

    Қорытынды

    • Индекс сұрауды жылдамдатады: EXPLAIN QUERY PLAN жоспарында SCAN (бәрін қарау) орнына SEARCH ... USING INDEX шығады. Индексті CREATE INDEX-пен құрып, DROP INDEX-пен жоямыз.
    • Бастапқы кілт бойынша индекс автоматты құрылады, ал қалған бағандар үшін оны өзіміз құрамыз.
    • Жабық индекс (covering index) сұрауға қажет барлық деректі индекстің өзінде сақтайды, сондықтан кестеге бару керек емес. Көп бағанды индексте іздейтін баған алда тұрады.
    • Индекс B-ағаш түрінде сақталады: тамыр бағыттайды, жапырақтарда реттелген мәндер жатыр.
    • Айырбастар: индекс орын алады және деректі қосуды баяулатады. Сондықтан әр бағанға индекс құрмаймыз.
    • Ішінара индекс кестенің тек бір бөлігін (мысалы, 2023 жылғы фильмдерді) қамтып, орынды үнемдейді.
    • DROP INDEX файлды кішірейтпейді: бос орын тек белгіленеді. Нағыз тазалау үшін VACUUM керек.
    • Транзакция (BEGIN TRANSACTION, COMMIT, ROLLBACK) бірнеше қадамды бөлінбейтін бірлікке біріктіреді. ACID: атомарлық, үйлесімділік, оқшаулау, беріктік.
    • Жарыс жағдайларын оқшаулау арқылы болдырмаймыз; SQLite-та мұны құлыптар (UNLOCKED, SHARED, EXCLUSIVE) қамтамасыз етеді.

    Өзіңізді тексеріңіз

    1. "email" бағанында индекс жоқ. EXPLAIN QUERY PLAN SELECT * FROM "users" WHERE "email" = 'a@b.kz'; қандай жоспар шығарады?

    Бағанда индекс болмаса, SQLite-тың басқа амалы жоқ: кестені сканерлейді. Сұрау орындалады, тек баяу болуы мүмкін.

    2. SELECT * FROM "movies" WHERE "id" = 100; сұрауы үшін индексті өзіміз құрмасақ та, жоспарда SEARCH ... USING INTEGER PRIMARY KEY шығады. Неге?

    Бастапқы кілт бойынша іздеуге арналған индексті SQLite кесте құрылғанда өзі жасайды. Қарапайым бағандарға (мысалы, title) ондай индекс болмайды.

    3. stars кестесінде ("person_id", "movie_id") индексі бар. Қай сұрау үшін ол жабық индекс болады?

    Бірінші сұрауда іздейтін (person_id) және қайтаратын (movie_id) мәндер екеуі де индекстің ішінде, сондықтан кестеге бару керек емес. Екінші сұраудың басты бағаны movie_id емес, үшіншісі басқа кестеге қатысты.

    4. Әріптесіңіз «кестенің әр бағанына индекс құрайық, сонда ешқашан баяу болмайды» дейді. Басты қарсы дәлел қандай?

    Индекс іздеуді жылдамдатады, бірақ орын алады және деректі қосуды баяулатады: жаңа мән әр B-ағашқа орналасуы тиіс.

    5. CREATE INDEX "recents" ON "movies" ("title") WHERE "year" = 2023; индексі бар. Қай сұрау бұл индексті қолдана алады?

    Ішінара индексте тек 2023 жылғы жолдар бар, сондықтан тек сол шартты қамтитын сұрау оны қолдана алады.

    6. Үлкен индексті DROP INDEX арқылы жойдыңыз, бірақ du -b movies.db файл өлшемі кішірейгенін көрсетпейді. Не істеу керек?

    DROP INDEX орынды тек «бос» деп белгілейді. VACUUM файлды қайта жинап, бос орынды қайтарады.

    7. Транзакция ішінде екі UPDATE бар; екіншісі CHECK шектеуін бұзады. Орындалған бірінші UPDATE мен ROLLBACK-тен кейін кестедегі деректер қандай болады?

    ROLLBACK транзакция басталғаннан бергі барлық өзгерісті қайтарады. Бұл транзакцияны атомарлы және үйлесімді етеді.

    8. Бір терминалда BEGIN EXCLUSIVE TRANSACTION; орындалды және аяқталмады. Екінші терминал сол дерекқордан оқып көрсе, не болады?

    Айрықша (EXCLUSIVE) құлып басқа транзакцияларға оқуға да тыйым салады. SQLite-та бұл бүкіл дерекқорды құлыптайды.

    Орташа

    In a Snap (Бір сәтте)

    Шешілетін мәселе

    Баспа станогынан, пошта қызметінен және телеграфтан кейін хабарласу қосымшалары келді. Бүгін сіз қандай да бір хабарласу қосымшасын (Facebook Messenger, iMessage, Instagram, Signal, Snapchat және басқалар) қолданған боларсыз. Ертедегі әріптестері байланыс жылдамдығын апталармен, күндермен немесе сағаттармен өлшесе, қазіргі хабарласу қосымшалары миллисекундтармен өлшенетін жылдамдыққа тәуелді: кешіккен хабар - жіберіп алған байланыс.

    Бұл тапсырмада сіз ойдан шығарылған қосымша үшін SQL сұрауларын жазасыз. Қосымша пайдаланушыларға суреттер жіберуге мүмкіндік береді, ал суреттер алушы көргеннен кейін 30 секундтан соң жойылады (бұл идеяны Snapchat танымал етті). Сіз жазатын сұраулар қосымшаның негізгі мүмкіндіктерін іске асырады. Қосымшада бірнеше мың пайдаланушы лезде хабарласуға сүйенетіндіктен, сұраулар тек дұрыс емес, жылдам да болуы өте маңызды. Сіз индекстерді пайдаланатын сұрауларды жазуды жаттығасыз, осының бәрі пайдаланушыларға бір сәтте байланыста болуға көмектесу үшін.

    Таратылатын код

    Бұл тапсырмаға snap.db дерекқоры және SQL сұрауларыңызды жазатын бірнеше .sql файлы керек. cs50.dev-ке кіріп, терминалда жалғыз cd жазыңыз, сосын мынаны орындаңыз:

    $ wget https://cdn.cs50.net/sql/2024/x/psets/5/snap.zip
$ unzip snap.zip
$ rm snap.zip
$ cd snap
$ ls

    rm файлды жою үшін растауды сұрағанда «y» жазып, Enter басыңыз. ls нәтижесінде snap.db дерекқорын және бір топ .sql файлын көруіңіз керек. Көрмесеңіз, қадамдарды қайталаңыз.

    Схема

    snap.db ішінде үш кесте бар, олар төмендегі ER-диаграммада сипатталған қатынастарды іске асырады: пайдаланушылар бір-бірімен достас (User мен User арасында көптен көпке байланыс), пайдаланушы хабар жібереді және хабарды көреді (бір пайдаланушыда көп хабар болады).

    users кестесі
    • id - пайдаланушының ID-і;
    • username - пайдаланушының аты;
    • phone_number - телефон нөмірі;
    • joined_date - қосымшаға тіркелген күні;
    • last_login_date - соңғы рет кірген күні.
    friends кестесі
    • user_id - берілген пайдаланушының ID-і;
    • friend_id - берілген пайдаланушымен достас пайдаланушының ID-і;
    • friendship_date - достық басталған күні.

    Әр жолда user_id бағанындағы пайдаланушы friend_id бағанындағы пайдаланушыны өз достарының қатарына санайды, бірақ керісінше болуы міндетті емес. Екі пайдаланушы бір-бірін дос санаса, екі жол қосылады:

    user_idfriend_idfriendship_date
    122024-01-01
    212024-01-01
    messages кестесі
    • id - хабардың ID-і;
    • from_user_id - хабарды жіберген пайдаланушының ID-і;
    • to_user_id - хабар жіберілген пайдаланушының ID-і;
    • picture - жіберілген суреттің файл аты;
    • sent_timestamp - хабар жіберілген уақыт;
    • viewed_timestamp - хабар көрілген уақыт;
    • expires_timestamp - хабардың мерзімі бітетін уақыт.

    Талаптар

    Әр .sql файлына төменде сипатталған мүмкіндікті іске асыратын SQL сұрауын жазыңыз. Жылдамдық шешуші болғандықтан, сұрауыңыз көрсетілген индексті қолдануы керек. Мұны тексерудің ең жақсы жолы - EXPLAIN QUERY PLAN нәтижесін қарау.

    1.sql. Қосымшаның белсенділік тобына белсенді пайдаланушыларды анықтау керек. 2024-01-01 күнінен бері жүйеге кірген барлық пайдаланушылардың username-дерін табыңыз. Сұрауыңыз мына түрде анықталған search_users_by_last_login индексін қолдансын:

    CREATE INDEX "search_users_by_last_login"
ON "users"("last_login_date");

    2.sql. Пайдаланушыларға мерзімі бітіп қалған хабарды қайта ашуға жол бермеу керек. ID-і 151 хабардың мерзімі қашан бітетінін табыңыз. Сұрауда хабардың ID-ін тікелей жазуға болады. Сұрауыңыз messages кестесінің бастапқы кілт бағанында автоматты түрде құрылған индексті қолдансын.

    3.sql. Қосымша пайдаланушының «үздік достарын» саралауы керек, бұл Snapchat-тың «Friend Emojis» мүмкіндігіне ұқсайды. creativewisdom377 ең жиі хабар жіберетін алғашқы 3 пайдаланушының ID-ін табыңыз. ID-лерді creativewisdom377 оларға жіберген хабарлар санына қарай, көптен азға қарай реттеңіз. Сұрауыңыз мына search_messages_by_from_user_id индексін қолдансын:

    CREATE INDEX "search_messages_by_from_user_id"
ON "messages"("from_user_id");

    4.sql. Қосымша пайдаланушыларға олардың белсенділігінің қысқаша есебін жіберуі керек. Ең танымал пайдаланушының username-ін табыңыз: ол - оған ең көп хабар жіберілген пайдаланушы. Сұрауыңыз мына search_messages_by_to_user_id индексін қолдансын:

    CREATE INDEX "search_messages_by_to_user_id"
ON "messages"("to_user_id");

    5.sql. Кез келген екі пайдаланушының ортақ достарының тізімін тез көрсету керек. Екі username берілген: lovelytrust487 және exceptionalinspiration482. Олардың ортақ достарының ID-ін табыңыз. Ортақ дос - екеуі де өз достары деп санайтын пайдаланушы. Сұрауыңыз friends кестесінің бастапқы кілт бағандарында автоматты түрде құрылған индексті қолдансын; бұл индекс sqlite_autoindex_friends_1 деп аталады.

    Кеңес

    SQL-де кейбір кілт сөздер арқылы екі топтың қиылысуын табуға болады. Еске түсіру үшін 1-аптаның конспектісіндегі «Sets» бөлімін (біздің сайтта 1-апта лекциясын) қараңыз.

    Кеңестер

    EXPLAIN QUERY PLAN сұрау қадамдарын көрсетеді. Нәтижесін көру үшін сұрауыңыздың алдына EXPLAIN QUERY PLAN қосыңыз. Мысал ретінде мына блокты іске қосыңыз (демо snap.db-де):

    EXPLAIN QUERY PLAN
SELECT "username"
FROM "users"
WHERE "id" = 151;

    EXPLAIN QUERY PLAN нәтижесін қалай оқимыз. Бұл команда SQLite-тың сұрауды орындау қадамдарын көрсетеді, ал нәтиже сұраудың индексті қолданғанын-қолданбағанын білдіреді:

    • USING INDEX қадамы сұрау сол қадамда индексті қолданып жатқанын білдіреді;
    • USING COVERING INDEX - сол қадамда жабық индекс қолданылады. Жабық индекс сұрауға қажет барлық бағанды қамтиды, сондықтан дерекқор кестеге қосымша қарамай-ақ сұрауды орындай алады;
    • USING INTEGER PRIMARY KEY - сұрау бастапқы кілт бағанының индексін қолданып жатыр. Бастапқы кілттің типі INTEGER болса, SQLite бұл индексті автоматты түрде береді. Сұраудың шарты кестенің бастапқы кілтіне қатысты болса, жолға тікелей жетудің тиімді жолы осы.

    Төменде индексті кемінде бір қадамда қолданатын сұрауларға арналған EXPLAIN QUERY PLAN нәтижелерінің бес мысалы келтірілген.

    1-мысал. Сұрау бір қадамда орындалады: search_users_by_last_login индексі бойынша іздеу.

    QUERY PLAN
`--SEARCH users USING INDEX search_users_by_last_login (last_login_date>?)

    2-мысал. Екі қадам: 1) search_messages_by_to_user_id индексінде іздеу; 2) ішкі сұрауды шешу үшін sqlite_autoindex_users_1 индексінде іздеу.

    QUERY PLAN
|--SEARCH messages USING COVERING INDEX search_messages_by_to_user_id (to_user_id=?)
`--SCALAR SUBQUERY 1
   `--SEARCH users USING COVERING INDEX sqlite_autoindex_users_1 (username=?)

    3-мысал. Бірнеше қадам, және көбінде индекс қолданылады: 1) search_messages_by_from_user_id индексінде іздеу; 2) sqlite_autoindex_users_1 индексінде іздеу; 3) соңғы қадамдар топтау мен реттеу үшін уақытша B-ағаштарды қолданады.

    QUERY PLAN
|--SEARCH messages USING INDEX search_messages_by_from_user_id (from_user_id=?)
|--SCALAR SUBQUERY 1
|  `--SEARCH users USING COVERING INDEX sqlite_autoindex_users_1 (username=?)
|--USE TEMP B-TREE FOR GROUP BY
`--USE TEMP B-TREE FOR ORDER BY

    4-мысал. 1) бастапқы кілт индексін автоматты түрде іздеу; 2) search_messages_by_to_user_id индексі бойынша жолдарды сканерлеу; 3) реттеу үшін уақытша B-ағаш.

    QUERY PLAN
|--SEARCH users USING INTEGER PRIMARY KEY (rowid=?)
`--SCALAR SUBQUERY 1
   |--SCAN messages USING COVERING INDEX search_messages_by_to_user_id
   `--USE TEMP B-TREE FOR ORDER BY

    5-мысал. Көп қадам, және көбінде индекс қолданылады. Әсіресе sqlite_autoindex_friends_1 индексіне жиі қатынау көрінеді.

    QUERY PLAN
`--COMPOUND QUERY
   |--LEFT-MOST SUBQUERY
   |  |--SEARCH friends USING COVERING INDEX sqlite_autoindex_friends_1 (user_id=?)
   |  `--SCALAR SUBQUERY 1
   |     `--SEARCH users USING COVERING INDEX sqlite_autoindex_users_1 (username=?)
   `--INTERSECT USING TEMP B-TREE
      |--SEARCH friends USING COVERING INDEX sqlite_autoindex_friends_1 (user_id=?)
      `--SCALAR SUBQUERY 3
         `--SEARCH users USING COVERING INDEX sqlite_autoindex_users_1 (username=?)

    Енді өз бетіңізше көріңіз: демо дерекқорда телефон нөмірі бойынша іздеуге индекс жоқ. Жоспар қалай өзгеретінін қараңыз (бұл ресми тапсырманың жауабы емес):

    EXPLAIN QUERY PLAN
SELECT "username" FROM "users"
WHERE "phone_number" = '+7 700 000 00 00';

CREATE INDEX "search_users_by_phone" ON "users"("phone_number");

EXPLAIN QUERY PLAN
SELECT "username" FROM "users"
WHERE "phone_number" = '+7 700 000 00 00';
