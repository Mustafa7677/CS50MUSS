    Жазу

    Дерекқорға деректі қосуды, өзгертуді және өшіруді үйренеміз: INSERT, UPDATE, DELETE, CSV импорты, сыртқы кілттер, триггерлер және жұмсақ жою.

    ▶ Түпнұсқа бейнежазба мен материалдар (ағылшынша)
    Бұл апта не туралы

    Өткен аптада дерекқордың қаңқасын (схеманы) жасауды үйрендік. Енді сол қаңқаға ет бітіреміз: деректі қосамыз, өзгертеміз, өшіреміз. Мысалдардың бәрін осы беттің өзінде «▶ Іске қосу» батырмасымен жүргізе аласыз. Бір ерекшелікке назар аударыңыз: әр басқан сайын дерекқор жаңадан құрылады, сондықтан қателесуден қорықпаңыз, ештеңе бұзылмайды. Тек өзгерістің нәтижесін көру үшін көп блоктың соңына SELECT қостым.

    Бұл бет сөзбе-сөз аударма емес. Лектор аудиторияда қалай түсіндірсе, біз де солай баяндаймыз: мағынасы мен кодтың бәрі түпнұсқадағыдай, тек әңгіме ана тілімізде жүреді.

    Кіріспе

    Өткен аптада өз дерекқорымыздың схемасын қалай жасау керегін үйрендік. Бүгін сол дерекқорларға деректі қалай қосуға, өзгертуге және өшіруге болатынын қарастырамыз. Яғни қазірге дейін біз негізінен «оқып» келдік (SELECT), ал бүгін «жазамыз».

    Мысалға Бостондағы MFA, яғни Бейнелеу өнері мұражайын (Museum of Fine Arts) алайық. Ол жүз жылдан астам тарихы бар мұражай, оның қорында тарихи және қазіргі заманғы көптеген жәдігер мен өнер туындысы сақталады. Олар өз коллекциясы туралы деректі қандай да бір дерекқорда ұстайтыны анық. Бізге таныс бір мысал: ауылдағы мектеп кітапханасында да әр кітап дәптерге тіркеледі ғой.

    Мұражайға жаңа туынды келгенде, оның деректері дерекқорға енгізіледі. Сол сияқты деректі кейде оқу, өзгерту немесе өшіру керек болады. Бүгін ең алдымен деректі құруға (қосуға, insert) назар аударамыз, яғни Бостон MFA дерекқорына жаңа жолдарды қалай қосатынымызды қарастырамыз.

    Дерекқор схемасы

    MFA өз коллекциясы үшін мынадай схема қолданады деп елестетейік. Мұнда сурет аттары, мұражайдың ішкі бірегей нөмірі (accession_number) және туындының қашан түскені көрсетілген:

    idtitleaccession_numberacquired
    1Profusion of flowers56.2571956-04-12
    2Farmers working at dawn11.61521911-08-03
    3Spring outing14.761914-01-08
    4Imaginative landscape56.496NULL
    5Peonies and butterfly06.18991906-01-01

    Әр жолда бір туындының аты, accession_number (мұражай ішінде қолданатын бірегей идентификатор) және оның түскен күні бар. Кестеде бастапқы кілт (primary key) қызметін id атқарады.

    Мұражайдың дерекқор әкімшісі осы суреттердің әрқайсысын кестеге INSERT сұрауымен қосқан деп елестете аламыз. Қалай жұмыс істейтінін көру үшін алдымен mfa.db деген дерекқор жасап алайық. Содан кейін дайын берілген schema.sql файлын оқытамыз, ол бізге collections кестесін жасап береді. (Сайтта бұл автоматты түрде жасалады: «▶ Іске қосу» батырмасын басқанда әлі бос, дайын кесте тұрады.)

    Кестенің шынымен жасалғанын тексеру үшін оған SELECT жасап көрейік:

    SELECT * FROM "collections";

    Нәтиже бос шығады. Дұрыс та, кестеде әлі бірде-бір жол жоқ.

    Деректі қосу

    Кестеге жол қосу үшін INSERT INTO деген SQL операторы қолданылады. Міне, бірінші суретімізді қосайық:

    INSERT INTO "collections" ("id", "title", "accession_number", "acquired")
VALUES (1, 'Profusion of flowers', '56.257', '1956-04-12');

SELECT * FROM "collections";

    Бұл команда екі нәрсені сұрайды: деректі қабылдайтын бағандардың тізімін және әр бағанға түсетін мәндерді, дәл сол ретпен. Бірінші бағанға бірінші мән, екіншіге екінші мән және т.с.с. Сөйтіп, дәптерге жол жазғандай ештеңені шатастырмаймыз.

    INSERT INTO өзі ештеңе қайтармайды: ол жай ғана жұмысты орындайды. Сондықтан нәтижесін білу үшін қайта SELECT жасаймыз (жоғарыдағы блокта екеуі қатар тұр, жолдың шынымен қосылғанын көресіз).

    Тағы бірнеше жол қосамыз. Бірақ id-ді қолмен жазып отыру (1, 2, 3, ...) қателікке жетелейді: ұмытып кетесіз, қайталап жібересіз. Бақытымызға орай, SQLite бастапқы кілт мәндерін өзі толтыра алады. Ол үшін id бағанын INSERT-тен мүлде алып тастаймыз:

    INSERT INTO "collections" ("id", "title", "accession_number", "acquired")
VALUES (1, 'Profusion of flowers', '56.257', '1956-04-12');

INSERT INTO "collections" ("title", "accession_number", "acquired")
VALUES ('Farmers working at dawn', '11.6152', '1911-08-03');

SELECT * FROM "collections";

    Нәтижеден екінші жолдың id-і 2 болғанын көресіз. Байқадыңыз ба, SQLite мұны қалай істейді? Ол алдыңғы бастапқы кілтті, бұл жағдайда 1-ді, бір санға арттырады.

    Сұрақтар

    Егер бастапқы кілті 1 болатын жолды өшірсек, келесі қосылатын жолға SQLite автоматты түрде 1-ді бере ме?

    Жоқ. SQLite кестедегі ең үлкен бастапқы кілтті тауып, оны бірге арттырады. Мұны өз көзіңізбен көріңіз: 5 жолы бар кестеден 1-жолды өшіріп, жаңасын қосамыз.

    DELETE FROM "collections" WHERE "id" = 1;

INSERT INTO "collections" ("title", "accession_number", "acquired")
VALUES ('Steppe at sunset', '70.100', '1970-05-09');

SELECT * FROM "collections";

    Жаңа жол id = 1 емес, id = 6 алды. Әйтсе де нақтылай кетейік: бұл ереже «ең үлкенін алып, бірге арттыру». Сондықтан ең соңғы жолды өшірсек, оның нөмірі қайта қолданылуы мүмкін. Мұны төмендегі блоктан көре аласыз; сонымен бірге кесте жасағанда AUTOINCREMENT сөзін қоссақ не болатынын салыстырамыз:

    CREATE TABLE "plain" ("id" INTEGER PRIMARY KEY, "t" TEXT);
CREATE TABLE "auto" ("id" INTEGER PRIMARY KEY AUTOINCREMENT, "t" TEXT);

INSERT INTO "plain" ("t") VALUES ('a'), ('b'), ('c');
INSERT INTO "auto" ("t") VALUES ('a'), ('b'), ('c');

DELETE FROM "plain" WHERE "id" = 3;
DELETE FROM "auto" WHERE "id" = 3;

INSERT INTO "plain" ("t") VALUES ('d');
INSERT INTO "auto" ("t") VALUES ('d');

SELECT 'plain' AS "table", "id", "t" FROM "plain" WHERE "t" = 'd'
UNION ALL
SELECT 'auto', "id", "t" FROM "auto" WHERE "t" = 'd';
    Түпнұсқадағы бір дәлсіздік

    Лекция конспектісінде «AUTOINCREMENT жойылған id-ді қайта қолдануға мүмкіндік береді» деп жазылған. Шындығында керісінше: AUTOINCREMENT бар кестеде бұрын берілген нөмір ешқашан қайталанбайды, ал онсыз (жоғарыда plain) ең соңғы жол өшірілсе, оның нөмірі қайта берілуі мүмкін. Блокты іске қосып, екі кестенің d жолы әртүрлі id алғанын өзіңіз тексеріңіз.

    Басқа шектеулер

    Енді schema.sql файлын ашып, схеманың өзіне қарайық:

    CREATE TABLE "collections" (
    "id" INTEGER,
    "title" TEXT NOT NULL,
    "accession_number" TEXT NOT NULL UNIQUE,
    "acquired" NUMERIC,
    PRIMARY KEY("id")
);

    Назар аударыңыз: accession_number бірегей (UNIQUE) деп көрсетілген. Яғни мұражайда екі бірдей нөмір болмауы керек. Егер әдейі бір нөмірді қайталап қосып көрсек, мынадай қате шығады: Runtime error: UNIQUE constraint failed: collections.accession_number (19). Қайталап көрейік:

    INSERT INTO "collections" ("title", "accession_number", "acquired")
VALUES ('Copy of the flowers', '56.257', '2000-01-01');

    Бұл қате қосқалы тұрған жолдың схемадағы шектеуді (constraint), нақтырақ айтқанда UNIQUE шектеуін бұзып тұрғанын білдіреді.

    Тура сол сияқты title бағанына NULL қоюға тырыссақ, NOT NULL шектеуі бұзылады:

    INSERT INTO "collections" ("title", "accession_number", "acquired")
VALUES(NULL, NULL, '1900-01-10');

    Бұл жолы қате мынадай: Runtime error: NOT NULL constraint failed: collections.title (19).

    Осылайша схемадағы шектеулер біздің «қоршауымыз» болады: олар дерекқор құрылымына сәйкес келмейтін жолдарды ішке кіргізбейді. Қақпадағы күзетші сияқты.

    Бірнеше жолды қосу

    Дерекқорға жазғанда көбіне бірден бірнеше жол қосу керек болады. Бір әдіс: жолдарды үтірмен бөліп, бір INSERT INTO командасына жазу.

    Түпнұсқада слайд бар

    Слайдта бір INSERT INTO командасынан кейін VALUES сөзінен соң жақшаға алынған жолдар үтірмен бөлініп тізіледі. Төмендегі нақты мысалда дәл осы көрсетілген.

    Бұлай бірден көп жол қосу ыңғайлы ғана емес, жылдамырақ та әрі тиімдірек. Енді коллекцияға екі жаңа сурет қосайық:

    INSERT INTO "collections" ("title", "accession_number", "acquired")
VALUES
('Imaginative landscape', '56.496', NULL),
('Peonies and butterfly', '06.1899', '1906-01-01');

SELECT * FROM "collections";

    Мұражай суреттің қашан түскенін әрдайым дәл біле бермеуі мүмкін. Сондықтан бірінші суреттің acquired мәні NULL. Бұл толық заңды: бағанда NOT NULL жоқ.

    CSV файлынан импорттау

    Деректеріміз жиі үтірмен бөлінген мәндер (CSV, comma-separated values) форматында келеді. Әр жолдағы мәндер үтірмен бөлініп жазылады, дәл Excel кестесін мәтін етіп сақтағандай:

    id,title,accession_number,acquired
1,Profusion of flowers,56.257,1956-04-12
2,Farmers working at dawn,11.6152,1911-08-03
3,Spring outing,14.76,1914-01-08
4,Imaginative landscape,56.496,
5,Peonies and butterfly,06.1899,1906-01-01

    SQLite CSV файлын дерекқорға тікелей импорттай алады. Бірақ ол үшін бәрін басынан бастаймыз: mfa.db дерекқорынан шығып, оны өшіреміз. Бізде mfa.csv деген файл дайын тұр, онда керек деректердің бәрі бар. Файлды ашсақ, бірінші жолда баған атаулары екенін көреміз, олар схемадағы collections баған атауларымен дәл сәйкес.

    Сонымен, mfa.db дерекқорын қайта жасап, схема файлын бұрынғыдай оқытамыз. Содан кейін CSV-ді SQLite командасымен импорттаймыз:

    .import --csv --skip 1 mfa.csv collections
    Бұл команда SQL емес

    .import нүктемен басталады, яғни бұл sqlite3 бағдарламасының өз командасы, SQL тілінің операторы емес. Сондықтан оны браузердегі «Іске қосу» орындай алмайды; компьютеріңіздегі sqlite3-те (немесе cs50.dev-те) жүргізесіз.

    Бірінші аргумент --csv SQLite-қа «бұл CSV файлы» деп айтады, сонда ол файлды дұрыс талдайды. Екінші аргумент --skip 1 бірінші жолды (тақырып жолын) өткізіп жіберуді, яғни оны кестеге қоспауды білдіреді.

    Енді collections кестесінен барлығын таңдап, mfa.csv-дегі әр сурет шынымен импортталғанын көреміз.

    Бірақ осы CSV-дегі әр жолда бастапқы кілт мәндері (1, 2, 3, ...) болды. Іс жүзінде CSV файлдарында мұндай id болмайтыны жиірек. Сонда SQLite оларды өзі қойып отыруы үшін не істейміз?

    Байқап көрейік. Codespace-те mfa.csv файлын ашып, тақырып жолынан id бағанын және әр жолдағы id мәндерін өшіреміз. Нәтижесінде mfa.csv былай болуы керек:

    title,accession_number,acquired
Profusion of flowers,56.257,1956-04-12
Farmers working at dawn,11.6152,1911-08-03
Spring outing,14.76,1914-01-08
Imaginative landscape,56.496,
Peonies and butterfly,06.1899,1906-01-01

    Сонымен қатар collections кестесіндегі бұрынғы жолдардың бәрін өшіреміз:

    DELETE FROM "collections";

    Нәтиже блогы қанша жол өзгергенін айтады: бес жол өшті. Енді осы CSV-ді кестеге импорттағымыз келеді. Бірақ схема бойынша collections-тың әр жолында төрт баған болуы керек, ал жаңа CSV-де тек үшеу. Сондықтан алдыңғыдай импорттай алмаймыз.

    Идентификаторсыз CSV-ді сәтті импорттау үшін уақытша кесте (temporary table) қолданамыз:

    .import --csv mfa.csv temp

    Бұл жолы --skip 1 жоқ екенін байқаңыз. Себебі SQLite CSV-дің ең бірінші жолын тақырып жолы деп өзі таниды да, оларды жаңа temp кестесінің баған атаулары етеді. Деректі көру үшін оны сұрау жеткілікті:

    SELECT * FROM "temp";

    (Бұл демо дерекқорда temp кестесі дайын тұр, дәл .import жасайтындай.)

    Бастапқы мақсатымыз: temp-тан деректі (бастапқы кілтсіз) таңдап, collections-қа көшіру. Мұны мына команда істейді:

    INSERT INTO "collections" ("title", "accession_number", "acquired")
SELECT "title", "accession_number", "acquired" FROM "temp";

SELECT * FROM "collections";

    Бұл процесте SQLite id бағанына бастапқы кілт мәндерін өзі қосады. Сөйтіп INSERT пен SELECT сұраулары тізбектеліп, бір кестеден екіншісіне деректі тасыды. Соңында дерекқорымызды жинап қою үшін temp кестесін өшіреміз:

    INSERT INTO "collections" ("title", "accession_number", "acquired")
SELECT "title", "accession_number", "acquired" FROM "temp";

DROP TABLE "temp";

SELECT name FROM sqlite_master WHERE type = 'table';

    Соңғы SELECT дерекқорда енді тек collections қалғанын көрсетеді. Осы екі қадамды есіңізде ұстаңыз (уақытша кестеге импорттау, сосын INSERT ... SELECT және DROP): бұл апталық тапсырмада да керек болады.

    Сұрақтар

    Кестеге жол қосқанда бағандарды белгілі бір орынға қоюға бола ма?

    Мәндердің ретін INSERT INTO ішінде өзгертуге болады (тек бағандар тізімімен үйлесіп тұрса болғаны). Бірақ баған атауларының өзінің ретін, әдетте, өзгерте алмаймыз: ол кесте жасалғандағы ретпен жүреді.

    Бірнеше жолды қосқанда біреуі кестенің шектеуін бұзса, не болады?

    Қысқа жауап: ешқайсысы қосылмайды. Көп жол қосқанда бірі шектеуді бұзса да, команда қатемен аяқталады және жолдардың бірде-бірі кестеге түспейді. Бүкіл топтама не түгел қосылады, не түгел қайтарылады. Мысалы, 1 мен 2-жолдың дұрыс, бірақ 3-жолдың accession_number-і қайталанса, бастапқы екі жол да қосылмай қалады.

    Ойланып көріңіз: мұндай «не бәрі, не ешқайсысы» ережесі неге пайдалы?

    Елестетіңіз: 100 жол қосып жатырсыз да, 57-жолда қате шықты. Егер алғашқы 56 жол кестеде қалып қойса, не қосылғанын, не қосылмағанын білмей дал боласыз, қайта жіберсеңіз қайталанулар шығады. «Не түгел, не ешқайсысы» ережесі кестені әрқашан таза, түсінікті күйде қалдырады: қатені түзеп, команданы тұтас қайта жүргізсеңіз болады.

    CSV-ден импорттағаннан кейін бір ұяшық бос болды, бірақ NULL емес. Неге?

    CSV-ден импорттағанда acquired мәндерінің бірі жоқ болатын. SQLite оны бос мәтін ('') деп оқыды, сондықтан кестеге бос мәтін болып түсті, NULL емес. Керек болса, импорттан кейін сұрау жазып, бос мәндерді NULL-ға айналдыра аламыз. Мысалы:

    INSERT INTO "collections" ("title", "accession_number", "acquired")
SELECT "title", "accession_number", "acquired" FROM "temp";

SELECT "title", "acquired", "acquired" IS NULL AS "is_null", "acquired" = '' AS "is_empty_text"
FROM "collections";

UPDATE "collections" SET "acquired" = NULL WHERE "acquired" = '';

SELECT "title", "acquired", "acquired" IS NULL AS "is_null"
FROM "collections";

    (Нәтиже блогы тек бірінші SELECT-тің нәтижесін көрсетеді: Imaginative landscape үшін is_empty_text = 1 екенін көресіз. UPDATE-тен кейінгі нәтижені көру үшін бірінші SELECT-ті алып тастап қайта жүргізіп көріңіз.) Бұл дәл апта соңындағы метеориттер тапсырмасында керек болатын әдіс.

    Деректі өшіру

    Жоғарыда DELETE FROM "collections"; кестедегі барлық жолды өшіретінін көрдік. (Шын дерекқорда мұны өте сақтықпен жасаңыз, әйтпесе бүкіл деректен айырыласыз!)

    Сонымен қатар белгілі бір шартқа сәйкес жолдарды ғана өшіруге болады. Мысалы, «Spring outing» суретін өшіру үшін:

    DELETE FROM "collections"
WHERE "title" = 'Spring outing';

    Нәтиже «1 жол өзгерді» дейді. Ал acquired мәні NULL суреттердің бәрін өшіру үшін, = емес, IS NULL қолданамыз:

    DELETE FROM "collections"
WHERE "acquired" IS NULL;

    Әдеттегідей, өшіру дұрыс орындалғанын кестеден барлығын таңдап тексереміз. Мұнда әр басқан сайын дерекқор жаңа болғандықтан, екі өшіруді қатар жазып, сосын SELECT жасайық:

    DELETE FROM "collections"
WHERE "title" = 'Spring outing';

DELETE FROM "collections"
WHERE "acquired" IS NULL;

SELECT * FROM "collections";

    Кестеден «Spring outing» мен «Imaginative landscape» суреттері жоғалғанын көресіз.

    1909 жылдан бұрын түскен суреттерді өшіру үшін мынаны жазамыз:

    DELETE FROM "collections"
WHERE "acquired" < '1909-01-01';

SELECT * FROM "collections";

    < операторы арқылы 1909 жылдың 1 қаңтарынан бұрын түскен суреттерді табамыз. Дәл солар өшеді. Назар аударыңыз: NULL күні бар сурет өшпей қалды, себебі NULL ешбір санмен салыстырғанда «кіші» болмайды.

    Сыртқы кілттер және өшіру

    Кейде деректі өшіру дерекқордың бүтіндігіне нұқсан келтіруі мүмкін. Классикалық мысал: сыртқы кілттер (foreign key). Сыртқы кілт бағаны басқа кестенің бастапқы кілтіне сілтеме жасайды. Егер сол бастапқы кілтті өшірсек, сыртқы кілт бағанының сілтейтін ештеңесі қалмайды. Қағаз мысалы: сыныпта оқушы тізімінен баланы сызып тастап, бірақ журналда оның бағалары қала берсе, сол бағалардың иесі жоқ болып шығады.

    MFA дерекқорының жаңартылған схемасын қарайық. Онда енді тек туындылар емес, суретшілер де бар. Artist пен Collection мәндері (entity) арасында көп-көпке байланыс бар: бір суретті бірнеше суретші салуы мүмкін, ал бір суретші көптеген туынды жасай алады.

    Мына дерекқор осы ER-диаграмманы жүзеге асырады: үш кесте, artists, created, collections. Мазмұнын қарайық:

    SELECT "artists"."id", "artists"."name", "collections"."title"
FROM "artists"
JOIN "created" ON "created"."artist_id" = "artists"."id"
JOIN "collections" ON "collections"."id" = "created"."collection_id"
ORDER BY "artists"."id";

    artists және collections кестелерінде бастапқы кілттер (id бағандары) бар. created кестесі сол id-ларға өзінің екі сыртқы кілт бағаны арқылы сілтейді.

    Енді сұрақ: id-і 3 болатын белгісіз суретшіні өшірсек, created кестесінде artist_id = 3 болатын жолдарға не болады? Тікелей байқап көрейік.

    mfa.db-ны ашып, .schema командасымен жаңартылған схеманы көреміз. created кестесінде шынымен екі сыртқы кілт шектеуі бар: біреуі суретші id-і үшін, екіншісі коллекция id-і үшін.

    .schema

    Енді artists кестесінен өшіріп көрейік:

    DELETE FROM "artists"
WHERE "name" = 'Unidentified artist';

    Біз бұған дейін көріп келген қателерге өте ұқсас хабар шығады: Runtime error: FOREIGN KEY constraint failed (19). Бұл «өшіру created кестесінде орнатылған сыртқы кілт шектеуін бұзады» дегенді білдіреді.

    Сайттағы демо туралы

    SQLite-та сыртқы кілттерді тексеру әдепкіде өшірулі болуы мүмкін, сондықтан бұл сайттағы демо дерекқорлардың басында PRAGMA foreign_keys = ON; бар (cs50.dev-тегі sqlite3-те мұны қолмен қосу керек емес). Өз жобаңызда сыртқы кілттер қызмет етпей жатса, алдымен осы жолды тексеріңіз.

    Шектеуді бұзбау үшін не істейміз? Бір жол: суретшіні өшірмес бұрын created кестесіндегі сәйкес жолдарды өшіру.

    DELETE FROM "created"
WHERE "artist_id" = (
    SELECT "id"
    FROM "artists"
    WHERE "name" = 'Unidentified artist'
);

SELECT * FROM "created";

    Бұл сұрау суретшінің өз туындыларымен байланысын өшіреді. Байланыс жоқ болғаннан кейін суретшінің өз деректерін шектеуді бұзбай-ақ өшіре аламыз:

    DELETE FROM "created"
WHERE "artist_id" = (
    SELECT "id"
    FROM "artists"
    WHERE "name" = 'Unidentified artist'
);

DELETE FROM "artists"
WHERE "name" = 'Unidentified artist';

SELECT * FROM "artists";
    Ойланып көріңіз: екі өшіруді ауыстырып жазсақ не болады?

    Егер алдымен artists-тан өшірсек, created әлі сол суретшіге сілтеп тұрады, сондықтан FOREIGN KEY constraint failed шығады. Тәртіп маңызды: алдымен «сілтеме жасаушыны» (created), содан кейін «сілтеме жасалатынды» (artists) өшіреміз. Журнал мен оқушы тізімі мысалындағыдай: алдымен бағаларды, содан кейін оқушыны алып тастаймыз.

    ON DELETE әрекеттері

    Екінші мүмкіндік: сыртқы кілт сілтейтін id өшірілгенде не істеу керегін схеманың өзінде алдын ала көрсету. Ол үшін ON DELETE деген сөз және одан кейін әрекет жазылады:

    • ON DELETE RESTRICT: сыртқы кілт шектеуі бұзылатын болса, id-ді өшіруге тыйым салады.
    • ON DELETE NO ACTION: сыртқы кілт сілтеп тұрған id-ді өшіруге рұқсат етеді де, ештеңе істемейді.
    • ON DELETE SET NULL: сыртқы кілт сілтеп тұрған id-ді өшіруге рұқсат етеді де, сыртқы кілт сілтемелерін NULL етіп қояды.
    • ON DELETE SET DEFAULT: алдыңғыдай, бірақ NULL орнына әдепкі мәнді қоюға мүмкіндік береді.
    • ON DELETE CASCADE: сыртқы кілт сілтеп тұрған id-ді өшіруге рұқсат етеді және оған сілтейтін сыртқы кілт жолдарын да тізбектей өшіреді (cascade). Мысалы, осымен суретші id-ін өшірсек, оның туындыларымен барлық байланысы да created кестесінен өшеді.

    Схема файлының соңғы нұсқасы дәл осы әдісті қолданады. Сыртқы кілт шектеулері енді былай көрінеді:

    FOREIGN KEY("artist_id") REFERENCES "artists"("id") ON DELETE CASCADE
FOREIGN KEY("collection_id") REFERENCES "collections"("id") ON DELETE CASCADE

    Енді сол DELETE қатесіз орындалады, ал өшіру artists-тан created-ке каскадпен жалғасады:

    DELETE FROM "artists"
WHERE "name" = 'Unidentified artist';

SELECT * FROM "created";

    Каскадты өшіру жұмыс істегенін тексеру үшін created-ті сұраймыз да, ешбір жолдың artist_id-і 3 емес екенін көреміз (3 деген өшірілген суретшінің id-і).

    Сұрақтар

    Біз енді ғана id-і 3 болатын суретшіні өшірдік. Келесі қосылатын жолға да 3 берілуін қамтамасыз етуге бола ма?

    Конспектте былай делінген: әдепкіде SQLite кестедегі ең үлкен id-ді алып, оны бірге арттырады; ал бағанды жасағанда AUTOINCREMENT сөзін қолдану нөмірлердің қалай берілетінін өзгертеді. Бұл жерде жоғарыда жазған ескертуді қайта еске салам: тәжірибеде AUTOINCREMENT бұрын берілген нөмірдің қайталанбауын қамтамасыз етеді (қараңыз: «Деректі қосу» бөліміндегі салыстыру блогы). Ал нақты қалаған нөмірді берудің кепілді жолы: id-ді INSERT-те қолмен жазу.

    Деректі жаңарту

    Дерекқордағы деректі өзгерту керек болатын жағдайларды елестету қиын емес. Мысалы, MFA дерекқорында «Farmers working at dawn» суреті бұрын «Белгісіз суретшіге» тіркелген еді, бірақ кейін оны шын мәнінде Li Yin салғаны анықталды делік.

    Мұндай өзгерісті UPDATE командасымен жасаймыз. Оның синтаксисі былай: UPDATE кесте атауы, SET бағанға жаңа мән, WHERE қай жолдар өзгеретінін анықтайтын шарт.

    Түпнұсқада слайд бар

    Слайдта UPDATE командасының үлгісі көрсетілген: «қай кестені», «қай бағанды», «қандай мәнге» және «қай жолдарға» жаңартамыз. Төмендегі нақты мысалда осы төрт бөлік бар.

    «Farmers working at dawn» суретінің created кестесіндегі байланысын осы синтаксиспен өзгертейік:

    UPDATE "created"
SET "artist_id" = (
    SELECT "id"
    FROM "artists"
    WHERE "name" = 'Li Yin'
)
WHERE "collection_id" = (
    SELECT "id"
    FROM "collections"
    WHERE "title" = 'Farmers working at dawn'
);

    Сұраудың бірінші бөлігі жаңартылатын кестені көрсетеді. Келесі бөлігі жаңа мән ретінде қойылатын Li Yin-нің id-ін алады. Соңғы бөлігі created кестесінің қай жолы жаңаратынын таңдайды: яғни «Farmers working at dawn» суретінің жолы. Нәтиже «1 жол өзгерді» дейді. Енді оны JOIN арқылы өз көзімізбен тексерейік:

    UPDATE "created"
SET "artist_id" = (
    SELECT "id"
    FROM "artists"
    WHERE "name" = 'Li Yin'
)
WHERE "collection_id" = (
    SELECT "id"
    FROM "collections"
    WHERE "title" = 'Farmers working at dawn'
);

SELECT "collections"."title", "artists"."name"
FROM "created"
JOIN "collections" ON "collections"."id" = "created"."collection_id"
JOIN "artists" ON "artists"."id" = "created"."artist_id"
ORDER BY "collections"."title";
    Ойланып көріңіз: UPDATE-те WHERE-ді ұмытып кетсек не болады?

    Сонда өзгеріс кестенің барлық жолына қолданылады. Жоғарыдағы мысалда created-тің әр жолындағы artist_id Li Yin-нікі болып шығар еді: барлық сурет бір адамға тіркеліп қалады. Сондықтан UPDATE мен DELETE жазғанда WHERE-ге ерекше назар аударыңыз. Әдет: алдымен сол WHERE-мен SELECT жасап, қай жолдар таңдалатынын көріп алыңыз.

    Триггерлер

    Триггер (trigger) - басқа SQL операторына (INSERT, UPDATE немесе DELETE) жауап ретінде өздігінен орындалатын SQL операторы. Қарапайым салыстыру: кіреберістегі жарық адам жақындағанда өзі жанады, ешкім қосып жатқан жоқ. Триггер де дәл сондай: белгілі бір оқиға болғанда ол өзі іске қосылады.

    Триггерлер байланысты кестелердегі деректердің үйлесімділігін сақтауға және қайталанатын жұмысты автоматтандыруға пайдалы.

    «Sell» (сату) триггерін жасау

    MFA дерекқорында collections кестесімен қатар жаңа transactions кестесі бар деп алайық:

    CREATE TABLE "transactions" (
    "id" INTEGER,
    "title" TEXT,
    "action" TEXT,
    PRIMARY KEY("id")
);

    Туынды сатылғанда (яғни collections-тан өшірілгенде) бұл оқиға transactions кестесіне автоматты түрде «sold» әрекетімен жазылса екен. Мынадай триггер жасаймыз:

    CREATE TABLE "transactions" (
    "id" INTEGER,
    "title" TEXT,
    "action" TEXT,
    PRIMARY KEY("id")
);

CREATE TRIGGER "sell"
BEFORE DELETE ON "collections"
BEGIN
    INSERT INTO "transactions" ("title", "action")
    VALUES (OLD."title", 'sold');
END;

DELETE FROM "collections"
WHERE "title" = 'Spring outing';

SELECT * FROM "transactions";

    Бұл блокта кесте мен триггерді жасадық, сосын триггердің жұмысын көру үшін бір суретті өшірдік. Нәтижеде transactions-қа қолмен ешнәрсе жазбасақ та, «Spring outing» мен «sold» жолы пайда болды.

    • Бұл триггер collections-тан жол өшірілмес бұрын (BEFORE DELETE) орындалады.
    • OLD - өшіріліп жатқан жолды білдіретін арнайы кілт сөз.
    • OLD."title" өшірілейін деп тұрған жолдың title бағанына жетеді.
    • Триггер transactions кестесіне «sold» әрекетімен жазбаны өзі қосады.

    «Buy» (сатып алу) триггерін жасау

    Туынды сатып алынғанда (collections-қа қосылғанда) оны transactions-қа «bought» әрекетімен жазғымыз келеді:

    CREATE TABLE "transactions" (
    "id" INTEGER,
    "title" TEXT,
    "action" TEXT,
    PRIMARY KEY("id")
);

CREATE TRIGGER "buy"
AFTER INSERT ON "collections"
BEGIN
    INSERT INTO "transactions" ("title", "action")
    VALUES (NEW."title", 'bought');
END;

INSERT INTO "collections" ("title", "accession_number", "acquired")
VALUES ('Steppe at sunset', '70.100', '1970-05-09');

SELECT * FROM "transactions";
    • Бұл триггер collections-қа жаңа жол қосылғаннан кейін (AFTER INSERT) орындалады.
    • NEW - қосылып жатқан жолды білдіретін арнайы кілт сөз.
    • NEW."title" жаңа қосылған жолдың title бағанына жетеді.

    Қорыта айтқанда: DELETE триггерінде OLD қолданамыз, себебі жаңа жол жоқ, бар жол ғана жоғалады. INSERT триггерінде NEW, себебі ескі жол жоқ, жаңа жол ғана пайда болады. (UPDATE триггерінде екеуі де қолжетімді: өзгергенге дейінгі жол OLD, кейінгісі NEW. Бұл «Don't Panic!» тапсырмасында кездеседі.)

    Ойланып көріңіз: неге «sell» триггері BEFORE DELETE, ал «buy» AFTER INSERT?

    Сату кезінде жол өшіріледі, сондықтан оның атын жол әлі кестеде тұрғанда, өшірілуден бұрын журналға алып қою ыңғайлы (BEFORE). Сатып алуда керісінше: жол алдымен нақты кестеге түсіп, бәрі сәтті болғаннан соң ғана журналға жазған дұрыс (AFTER).

    Сұрақтар

    Триггердің ішінде бірнеше SQL операторын жазуға бола ма?

    Иә. BEGIN мен END арасында бірнеше оператор жаза аласыз, оларды нүктелі үтірмен (;) бөлесіз.

    Жұмсақ жою

    Жұмсақ жою (soft deletion, soft delete) - деректі дерекқордан шын мәнінде алып тастамай, оны жай ғана «өшірілген» деп белгілеу. Қоқыс жәшігіне салып қойғандай: файл әлі де бар, тек көзге көрінбейді.

    Мысалы, collections кестесіне әдепкі мәні 0 болатын deleted бағанын қосамыз:

    ALTER TABLE "collections"
ADD COLUMN "deleted" INTEGER DEFAULT 0;

SELECT * FROM "collections";

    Қатарды «өшіру» үшін deleted бағанын 1-ге жаңартамыз:

    ALTER TABLE "collections"
ADD COLUMN "deleted" INTEGER DEFAULT 0;

UPDATE "collections"
SET "deleted" = 1
WHERE "title" = 'Farmers working at dawn';

SELECT * FROM "collections";

    Содан кейін тек өшірілмеген жолдарды сұраймыз:

    ALTER TABLE "collections"
ADD COLUMN "deleted" INTEGER DEFAULT 0;

UPDATE "collections"
SET "deleted" = 1
WHERE "title" = 'Farmers working at dawn';

SELECT * FROM "collections"
WHERE "deleted" != 1;

    Осылайша қажет болса, деректі қайта қалпына келтіруге болады, әрі толық тарихи жазба сақталады. Бірақ есте ұстайық: деректі шынымен өшіруді талап ететін жеке деректерді қорғау заңдарын (мысалы, ҚР-дағы дербес деректер туралы заң немесе GDPR сияқты ережелер) орындау да маңызды. Жұмсақ жою мұндай талапты орындамайды.

    Есіңізде болсын

    Жұмсақ жоюда барлық оқу сұрауларына WHERE "deleted" != 1 шартын қосуды ұмытпау керек. Әйтпесе «өшкен» деректер қайтадан көрінеді. Осыны жеңілдету үшін келесі аптада көріністерді (views) үйренеміз.

    Қорытындылай келе

    Бұл біздің 3-апта, SQL-де жазу лекциясының соңы. Енді деректі оқып қана қоймай, оны қосып, өзгертіп, өшіре аламыз; шектеулер мен сыртқы кілттер мұны қалай қорғайтынын, триггерлер қалай автоматтандыратынын білеміз.

    Қорытынды

    • INSERT INTO ... VALUES ... кестеге жол қосады. Бағандар тізімі мен мәндер тізімі бір ретпен жүреді.
    • id бағанын жазбасаңыз, SQLite бастапқы кілтті өзі береді (ең үлкен мәнге бірді қосып). AUTOINCREMENT бұрын берілген нөмірді қайта бермейді.
    • Схемадағы NOT NULL, UNIQUE және басқа шектеулер дерекқорды дұрыс емес жолдардан қорғайды. Бірнеше жол қосқанда бірі бұзылса, бірде-бірі қосылмайды.
    • Бірнеше жолды үтірмен бөліп бір INSERT-пен қосуға болады. CSV-ді .import --csv --skip 1 арқылы импорттаймыз. id жоқ CSV үшін уақытша кесте қолданамыз: .import --csv файл temp, сосын INSERT ... SELECT және DROP TABLE.
    • CSV-дегі бос ұяшық кестеге бос мәтін ('') болып түседі, NULL емес. Оны UPDATE ... SET ... = NULL WHERE ... = '' арқылы түзетеміз.
    • DELETE FROM кесте WHERE ... жолдарды өшіреді; WHERE болмаса, барлығы өшеді.
    • Сыртқы кілт сілтеп тұрған жолды өшіру FOREIGN KEY constraint failed қатесін береді. ON DELETE әрекеттері: RESTRICT, NO ACTION, SET NULL, SET DEFAULT, CASCADE.
    • UPDATE кесте SET баған = мән WHERE ... бар деректі өзгертеді; мәнді ішкі сұраумен алуға болады.
    • Триггер (CREATE TRIGGER ... BEFORE/AFTER INSERT/UPDATE/DELETE ON ... BEGIN ... END) басқа оператордың әсерінен өздігінен орындалады; OLD бар жолға, NEW жаңа жолға сілтейді.
    • Жұмсақ жою деректі шынымен өшірмей, deleted бағанымен белгілейді. Бірақ деректі шын өшіруді талап ететін заңдарды ұмытпаңыз.

    Өзіңізді тексеріңіз

    1. collections кестесінде бастапқы кілт id бар және қазір ең үлкен id = 5. Мына команданы орындасақ, жаңа жолдың id-і не болады?

    INSERT INTO "collections" ("title", "accession_number", "acquired")
VALUES ('Steppe at sunset', '70.100', '1970-05-09');

    id бағанын жазбасақ, SQLite бастапқы кілтті өзі береді: кестедегі ең үлкен мәнді тауып, бірге арттырады.

    2. DELETE FROM "collections"; командасы (WHERE жоқ) орындалса, не болады?

    Шарт болмаса, DELETE барлық жолға қолданылады. Кестенің өзін өшіру үшін DROP TABLE керек.

    3. Бір INSERT-пен үш жол қосып жатырмыз, бірақ екінші жолдың accession_number-і кестедегі барымен қайталанады (UNIQUE). Нәтиже қандай?

    Бір команда ретінде қосылатын топтамада шектеу бұзылса, бүкіл команда сәтсіз аяқталады.

    4. Суретші өшірілгенде, created кестесіндегі жолдар өшпей, тек artist_id бағаны NULL болып қалуын қаласақ, сыртқы кілтке не жазамыз?

    SET NULL өшіруге рұқсат береді, ал сілтеме жасаушы сыртқы кілтті NULL етеді. CASCADE жолдардың өзін өшірер еді, RESTRICT өшіруге тыйым салар еді.

    5. Кодтағы қатені табыңыз. Мақсат: тек «Spring outing» суретінің күнін NULL ету.

    UPDATE "collections"
SET "acquired" = NULL;

    WHERE жоқ UPDATE кестенің барлық жолын өзгертеді. Алдымен сол шартпен SELECT жасап тексеру - жақсы әдет.

    6. Мына триггерде NEW."title" нені білдіреді?

    CREATE TRIGGER "buy"
AFTER INSERT ON "collections"
BEGIN
    INSERT INTO "transactions" ("title", "action")
    VALUES (NEW."title", 'bought');
END;

    INSERT триггерінде NEW қосылып жатқан жолға сілтейді. Өшіру триггерінде оның орнына OLD қолданылады.

    7. Жұмсақ жою қолданған кестеден «өшірілмеген» жолдарды таңдау үшін қай сұрау дұрыс (deleted бағанының әдепкісі 0)?

    Жұмсақ жоюда жол жойылмайды, тек deleted = 1 деп белгіленеді. Сондықтан оқығанда deleted != 1 шартымен сүзгіден өткіземіз.

    8. CSV-ден импорттағаннан кейін acquired бос болған жолда "acquired" IS NULL шарты орындалмай жатыр. Себебі және түзету жолы қандай?

    Бос мәтін мен NULL - екі түрлі мән. Импорттан кейін бос мәтіндерді NULL-ға айналдыру - деректерді тазалаудың типтік қадамы.

Автотексеруші сол соңғы SELECT нәтижесін эталонмен салыстырады, сондықтан тапсырмада көрсетілген сұрауды дәл жазыңыз. Бұл жаттығу ресми check50-ті алмастырмайды.

    Орташа

    Don't Panic! (Үрейленбеңіз!)

    Сіз білікті «пентестерсіз» (pentester). Компаниялар көбіне өз деректер жүйелеріндегі осал жерлерді табу және хабарлау үшін сізді тергеу сынақтарын (penetration test) жүргізуге жалдайды. Жуырда шағын кәсіпорын сізден өз сайтын қуаттандыратын SQLite дерекқорында осындай сынақ жүргізуді сұрады.

    Бұл құпия операцияның сәтті болуы үшін сіз мыналарды орындауыңыз керек:

    • Өзгерту: сайттың әкімшілік аккаунтының құпиясөзін өзгерту.
    • Өшіру: дерекқор жазып қойған жоғарыдағы құпиясөз өзгерісінің барлық журналын өшіру.
    • Қосу: ізіңізді жасыру үшін жалған деректер қосу.

    Сәті түсті: сіз компания ғимаратына кіргенде, бағдарламашы өз үстелінен енді ғана тұрып кеткен екен. Инженердің дерекқорға қосылымы әлі ашық тұр. Ол қайтып келгенше сізде шамамен 5 минут бар. Дайынсыз ба?

    Дистрибутив коды

    cs50.dev-ке кіріп, терминалда cd деп жазыңыз (промпт $ болуы керек). Сосын:

    $ wget https://cdn.cs50.net/sql/2024/x/psets/3/dont-panic.zip
$ unzip dont-panic.zip
$ rm dont-panic.zip
$ cd dont-panic
dont-panic/ $ ls

    Схема

    Дерекқор схемасын түсіндіруге уақыт аз. Есте болсын, SQLite дерекқорының схемасын .schema командасымен көре аласыз.

    Талаптар (Specification)

    hack.sql файлында мына нәтижелерге жеткізетін SQL операторларының тізбегін жазыңыз:

    • Өзгерту: әкімшілік аккаунт admin-нің құпиясөзін «oops!» етіп өзгертіңіз.
    • Өшіру: жоғарыдағы құпиясөз өзгерісінің дерекқор жазған барлық журналын өшіріңіз.
    • Қосу: ізді шатастыру үшін жалған деректер қосыңыз. Нақтырақ айтқанда, emily33 пайдаланушысын «күйіп қалдыру» үшін, user_logs кестесінде admin аккаунтының құпиясөзі emily33-тің құпиясөзіне өзгертілгендей көрінетін жазба қалдырыңыз.

    hack.sql ішіндегі SQL операторларын дерекқордың жаңа данасында іске қосқанда, олар жоғарыдағы нәтижелерді беруі керек. Мақсаттардың берілу реті оларды орындаудың ең қолайлы реті болмауы мүмкін екенін есте ұстаңыз!

    Тағы бір ескертпе: құпиясөздер әдетте «ашық» күйде, яғни таза таңбалар түрінде сақталмайды. Олар құпиялылықты сақтау үшін хэштеледі (араластырылады). Сондықтан админ құпиясөзін ауыстыратын мәніңіз де хэштелген болуы керек. Бақытымызға орай, users кестесіндегі құпиясөздер MD5 хэштері түрінде сақталатыны белгілі. Қарапайым мәтіннен мұндай хэштерді md5hashgenerator.com сайтынан тез жасай аласыз.

    Сағат тықылдап тұр!

    Кеңес

    SELECT қайтарған жолдарды басқа кестеге INSERT ете аласыз, бағандар саны сәйкес болса болғаны.

    Ішкі сұрауды (subquery) тек WHERE ішінде емес, SQL операторының кез келген жерінде жасауға болады. Мысалы, жеңілдетілген user_logs кестесі үшін:

    INSERT INTO "user_logs" ("type", "password")
SELECT 'update', (
    SELECT "password"
    FROM "users"
    WHERE "username" = 'carter'
);

    Бұл сұрау user_logs кестесіне жаңа жол қосады: type бағанына «update», ал password бағанына carter пайдаланушысының қазіргі құпиясөзі жазылады.

    Жіберу:

    • Құпиясөзді ауыстырғанда триггер жазған user_logs жолы өшіріледі.
    • user_logs-қа жалған жол қосылады: admin-нің құпиясөзі emily33-тің хэшіне өзгергендей көрінеді (хэштерді ішкі сұраумен аласыз).

    • check50 cs50/problems/2024/sql/dont-panic өтеді.

    Күрделі

    Meteorite Cleaning (Метеориттерді тазалау)

    Сіз NASA-да деректер инженерісіз. Сіздің уақытыңыздың көбі метеориттерді «тазалауға» кетеді, дәлірек айтсақ, олар туғызатын деректерді тазалауға.

    Сізге жер бетіне түскен тарихи метеориттердің CSV файлы берілген, олар біршама көп! Сіздің міндетіңіз: деректі SQLite дерекқорына импорттап, жол-жөнекей оны тазалау. Сіз біткеннен кейін дерекқорды басқа инженерлер талдау үшін пайдаланады.

    Дистрибутив коды

    Сізге meteorites.csv файлын, сондай-ақ CSV-ді тазалайтын SQL операторларын жазатын import.sql файлын жүктеу керек. cs50.dev терминалында:

    Талаптар (Specification)

    import.sql файлында meteorites.csv деректерін meteorites.db дерекқорындағы meteorites кестесіне импорттап, тазалайтын SQL (және SQLite) операторларының тізбегін жазыңыз.

    • id: метеориттің бірегей идентификаторы.
    • name: метеориттің берілген аты.
    • class: метеориттің дәстүрлі классификация бойынша жіктелуі.
    • mass: метеориттің салмағы, грамммен.
    • discovery: «Fell» немесе «Found». «Fell» метеориттің Жерге құлап жатқаны көрінгенін білдіреді, ал «Found» оны құлағаннан кейін ғана тапқанын білдіреді.
    • year: метеорит табылған жыл.
    • lat: метеорит құлаған ендік (latitude).
    • long: метеорит құлаған бойлық (longitude).

    Ескеріңіз: CSV-дегі барлық бағандар соңғы кестеге түсуі шарт емес!

    meteorites кестесіндегі деректі «таза» деп санау үшін мыналарды қамтамасыз етіңіз:

    1. meteorites.csv-дегі бос мәндердің бәрі meteorites кестесінде NULL болып көрсетілсін. Есте болсын: mass, year, lat және long бағандарында CSV-де бос мәндер бар.
    2. Ондық бөлшегі бар барлық бағандар (мысалы, 70.4777) жүздікке дейін дөңгелектелсін (70.4777 → 70.48). Есте болсын: mass, lat, long бағандарында ондық бөлшектер бар.
    3. nametype мәні «Relict» болатын метеориттердің барлығы meteorites кестесіне кірмесін.
    4. Метеориттер year бойынша ескіден жаңаға қарай сұрыпталсын, ал екі метеорит бір жылы құласа, name бойынша әліпби ретімен.
    5. meteorites.csv-дегі метеориттердің id-лері №4 тармақта көрсетілген ретке сай жаңартылсын. Метеориттердің id-і 1-ден басталып, ең ескі жылы құлағаннан және сол жылдың ішінде әліпби бойынша бірінші келетін метеориттен бастау керек.

    Кеңестер (Advice)

    Мұндай үлкен деректі тазалауды неден бастарыңызды білмей, абдырап қалуыңыз мүмкін. Мәселені кішкентай бөліктерге бөлейік.

    1-қадам. meteorites.csv-ді уақытша кестеге импорттау

    Алдымен meteorites.csv ішіндегі барлық деректі meteorites_temp деп аталатын уақытша кестеге түсіріңіз. Уақытша кесте - ыңғайлы «орын ұстаушы»: деректі соңғы meteorites кестесіне лайық күйге келгенше осында тазалай аласыз.

    CSV-ді SQLite дерекқорына импорттамас бұрын, деректі қабылдайтын кестенің схемасын алдын ала анықтаған жөн. Сондықтан import.sql-да мынаны жазып көріңіз:

    CREATE TABLE "meteorites_temp" (
    -- TODO
);

    Баған атауларын өзіңіз таңдайсыз. Сосын CREATE TABLE операторынан кейін .import жазып, meteorites.csv деректерін meteorites_temp кестесіне импорттаңыз. Ақырында төмендегі «Қолдану» бөліміне сай import.sql операторларын іске қосып, meteorites.db жасап көріңіз.

    2-қадам. Импортталған деректі тазалау

    Деректер уақытша кестеде болғаннан кейін тазалау операторларын жаза беріңіз. Мысалы, mass бағанының мәндерін қалай жаңартуға болатынын ойлаңыз:

    UPDATE "meteorites_temp"
SET "mass" = ...
WHERE ...

    Тазаланатын әр баған үшін осындай бірнеше оператор (бір немесе бірнешеу) керек болуы мүмкін.

    3-қадам. Деректі уақытша кестеден meteorites кестесіне көшіру

    Бір кестедегі жолдарды SELECT арқылы таңдап, жаңа кестеге INSERT ете аласыз:

    INSERT INTO "table0" ("column0", "column1")
SELECT "column0", "column1" FROM "table1";

    Мұны істегенде деректің ретін ORDER BY арқылы өзгерте аласыз. Ал жаңа кестеде бастапқы кілт бағаны көрсетілген болса, id берілмеген жағдайда мұндай оператор қосылатын жолдарға жаңа id-лерді автоматты түрде береді. Уақытша кестемен жұмыс біткен соң оны өшіру (DROP) - жақсы дағды.

    Қолдану (Usage)

    Осы деректі тазалау кезінде көмектесуі мүмкін бірнеше терминал командасы:

    cat import.sql | sqlite3 meteorites.db

    Бұл команда екі бөліктен тұрады: cat import.sql файлдағы мәтінді шығарады (өздігінен жүргізіп көріңіз), ал sqlite3 meteorites.db файлды sqlite3 қозғалтқышымен ашады. Екеуі құбыр (|) арқылы біріккенде, import.sql ішіндегі операторлар meteorites.db дерекқорына қолданылады. Егер meteorites.db әлі жоқ болса, ол жасалып, import.sql операторлары соған қолданылады.

    import.sql мінсіз болмай, дерекқорды қайта жасағыңыз келсе, ағымдағы нұсқаны өшіріңіз (сұралса, «y» басып Enter):

    rm meteorites.db
cat import.sql | sqlite3 meteorites.db

    Процесті жеделдету үшін терминалда жоғары көрсеткіні басып, бұрынғы командаларды қайта шақыра аласыз.
